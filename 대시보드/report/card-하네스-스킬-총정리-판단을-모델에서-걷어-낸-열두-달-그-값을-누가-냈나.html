① 하네스라는 말이 편마다 다른 것을 가리킨다

하네스(모델을 감싸고 앉아 도구를 쥐여 주고 순서를 매기는 바깥 장치)라는 말은 열두 달 사이 여섯 곳에서 쓰였고, 여섯이 같은 것을 가리키지 않는다.

오픈AI의 빌 첸과 브라이언 피오카는 코딩 에이전트를 셋으로 나눴다 — 사람이 마주하는 화면, 모델, 하네스. 그리고 하네스를 「프롬프트와 도구를 한 고리 안에 모아 모델과 주고받게 하는 것」이라고 못 박았다. 앤스로픽의 랜스 마틴은 같은 말을 「모델을 감싸고 앉아 언제 무엇을 시킬지 바깥에서 정하는 장치」로 적었다. 앞엣것은 배관이고 뒤엣것은 지휘다.

SemiAnalysis 는 제품 이름을 붙여 정의한다 — 「모델을 감싸 코드를 읽고 도구를 쓰게 만드는 프로그램(코덱스 CLI, 클로드 코드 등)」이며, 같은 모델도 하네스가 다르면 체감 성능이 달라진다고 적었다. 여기서 하네스는 파는 물건이다. 어플라이드컴퓨트의 레이먼드 펑에게는 아예 다른 것이다 — 소스 코드조차 볼 수 없는 남의 하네스에 모델을 맞춰 훈련시켜야 한다고 말한다. 훈련하는 쪽에서 보면 하네스는 손댈 수 없는 검은 상자다.

가장 멀리 간 정의는 오픈AI의 비노스 고빈다라잔이 낸 한 줄이다. 「모델은 제안하고 하니스는 확정하며 영수증이 그것을 증명한다」. 영수증은 시스템이 실제로 무엇을 했는지 남긴 기록을 가리킨다. 여기서 하네스는 배관도 지휘도 제품도 아니고 권한을 쥔 주체다. 모델이 메시지·도구 호출·수정·명령을 제안할 수는 있어도 그 자체로는 프로덕션 경계가 아니며, 상태를 바꾸고 권한을 검사하고 순서대로 커밋하고 영수증을 남기는 것은 하네스의 일이라고 그는 적었다.

말이 이렇게 갈리는 것은 이 열두 달이 무엇을 하는 시기였는지를 그대로 보여 준다. 모델 안에 있던 판단이 하나씩 바깥으로 걷혀 나왔고, 걷어 낸 것을 담을 그릇에 사람들이 저마다 이름을 붙였다. SemiAnalysis 는 아예 벤치마크를 「과제 + 채점 방식 + 하네스」 세 조각으로 다시 정의했다. 무엇을 재든 하네스를 빼고는 잴 수 없게 됐다는 뜻이다.

② 판단을 모델 바깥으로 옮기면 무엇이 달라지나

마이크로소프트의 오넬라 바히디카와 조엘 알루는 학생과 말을 주고받으며 레슨 하나를 끝까지 진행하는 음성 튜터 에이스를 만들었다. 데모까지는 잘 돌았고, 진짜 사용자가 붙자 중간에서 무너졌다 — 절반쯤 가서 스스로 끝났다고 판단하거나, 단계를 건너뛰거나, 같은 데를 맴돌았다.

두 사람이 지목한 원인은 프롬프트가 약해서가 아니라 모델에게 준 통제 권한이었다. 조엘의 비유로는 모델이 배우이고 하네스가 감독이다. 배우는 대사 한 줄을 훌륭히 소화하지만 지금이 여섯 장면 가운데 세 번째인지 기억하는 일에는 형편없다.

그래서 레슨 하나를 인트로·티치·체크·그레이드·어드밴스·랩 여섯 단계를 오가는 상태 머신으로 만들었다. 요점은 단계를 쪼갠 것이 아니라 단계를 넘기는 판단을 모델 바깥으로 옮긴 것이다. 각 단계는 모델에게 한 가지만 하고 결과를 돌려 달라는 좁은 계약을 보내고, 돌아온 결과를 하네스가 검증하고 상태를 넘기고 다음에 무엇을 할지 정한다. 조엘의 표현으로는 모델이 제안하고 하네스가 결정한다. 레슨 하나에 하네스가 넷 붙어 각각 섹션 입력을 만들고, 화이트보드에 그리고, 대기열을 비우고, 레슨을 끝내는 절차를 맡는다.

특히 공들인 판단은 셋이었다 — 레슨이 언제 끝났는지, 학생이 정말 이해했는지, 다음에 무엇을 할지. 이 세 갈래에 들어가는 모든 물음과 모델이 취할 모든 행동을 모델 바깥에서 미리 설계해 두었다.

값으로 나온 것은 모델을 내린 대목이다. 흐름을 하네스가 붙잡고 나자 무거운 오퍼스 4.7 대신 훨씬 작고 추론 능력도 떨어지는 하이쿠 4.5로 내려갈 수 있었고, 그런데도 기대한 수준으로 작동했다. 이 대목만 떼어 「작은 모델로 갈아 끼우면 싸진다」로 읽으면 순서가 거꾸로다. 모델이 내릴 판단을 하네스가 먼저 가져갔고, 그래서 모델에 남은 일이 쉬워졌고, 쉬워진 다음에야 하이쿠 4.5로 내려갈 수 있었다.

두 사람이 댄 판단 기준은 한 줄이다 — 지금 굴리는 에이전트가 성공할지 실패할지가 동전 던지기 수준이라면 제어 흐름을 모델에서 빼내라. 음성 튜터에만 해당하는 이야기가 아니라 코딩 에이전트·옵스 런북·온보딩 흐름에도 같은 원칙이 든다고 말하며 발표를 닫는다.

다만 아낀 값이 얼마인지는 나오지 않는다. 비용과 지연을 아꼈다는 말만 있고 잰 수가 없다. 하네스가 모델 결과를 어떻게 검증하는지도 공개되지 않았다 — 검증이 또 다른 모델 호출인지 규칙으로 짠 코드인지가 이 구조의 값을 좌우하는데 로그 화면으로만 지나갔다. 그리고 모델에게서 뺏은 판단은 사라지지 않는다. 상황이 늘어날 때마다 사람이 상태를 늘려야 하고, 그 값을 발표는 다루지 않는다.

③ 커서는 왜 반대로 갔나

두 달 앞선 2026년 5월, 커서의 데이비드 고메스는 정확히 반대 방향으로 갔다.

지운 것은 기능 둘이다. 워크트리(같은 저장소를 여러 폴더로 갈라 각각 다른 가지를 놓고 일하는 깃 기능)는 커서에서 워크트리마다 에이전트를 띄워 화면에 격자로 늘어놓는 기능이었고, 베스트오브N 은 같은 과제를 여러 모델에 한꺼번에 주고 결과를 견주는 기능으로 2025년 10월 커서 2.0 과 함께 나왔다. 발표자는 이 둘을 통째로 걷어내는 PR 을 열었고 코드 1만 5천 줄쯤이 지워졌다.

지워진 코드가 하던 일이 무엇이었는지가 이 절의 핵심이다. 워크트리를 만들고 관리하고 에이전트에 맥락으로 넣어 주는 일, 에이전트가 자기 워크트리를 벗어나지 못하도록 가두는 일, 사용자가 정해 둔 셋업 스크립트를 매번 돌리는 일, 어느 구현이 나아 보이는지 판정하는 일, 워크트리가 수백 개씩 쌓여 디스크가 불어나면 치우는 일이 전부 코드에 있었다.

대신 넣은 것은 마크다운 두 조각이다 — 스킬(에이전트가 필요할 때만 읽어 들이는 마크다운 지시 파일)과 서브에이전트(부모 에이전트가 따로 띄워 제 맥락에서 일을 시키는 에이전트). 이 둘을 겹치면 워크트리 기능도 베스트오브N 도 마크다운만으로 다시 만들 수 있다는 것이 판단이었다. 베스트오브N 쪽은 마크다운 마흔 줄이고 예전 구현은 코드 4천 줄쯤이었다. 가장 어려운 대목은 워크트리를 벗어나지 말라고 시키는 대목이라 절대 밖에서 일하지 말라고 세게 적었다.

좋아진 것을 발표자가 넷 든다. 유지할 코드가 훨씬 줄었고, 대화 도중에 워크트리로 옮겨 갈 수 있게 됐고, 저장소를 여럿 놓고 일할 때도 되고, 판정이 나아졌다 — 부모가 서브에이전트들의 작업을 더 많이 알고 있어 조각을 이어 달라고 시킬 수 있게 됐다.

나빠진 것 가운데 첫째가 이 보고서의 물음과 정면으로 만난다. 예전에는 워크트리 밖 파일을 건드리는 것이 물리적으로 불가능했고 지금은 모델을 믿는다. 긴 세션에서 어디서 일해야 하는지 잊고, 떨어지는 모델일수록 엉뚱한 짓을 한다. 옮겨 간 것은 줄 수가 아니라 막는 방식이다 — 예전에는 나갈 수 없었고 지금은 나가지 말라고 프롬프트로 못 박아 두고 지키기를 기다린다.

발표자는 이 기능을 두고 평가를 짜 봤고 사실상 처음이라고 말한다. 커서 CLI 를 화면 없이 띄워 돌리고 채점하는 눈을 둘 뒀다 — 하나는 모델이 자기 워크트리에서 할 일을 했는지, 다른 하나는 건드리지 말아야 할 원본 체크아웃에서 뭔가 했는지 본다. 결과는 하이쿠가 작고 덜 똑똑한 모델이라 원본 체크아웃으로 자주 새고 컴포저와 그록은 훨씬 낫다는 데서 멈춘다. 몇 번 가운데 몇 번인지는 대지 않는다.

고치는 길로는 둘을 든다 — 평가를 늘려 프롬프트를 고치는 길, 강화학습으로 자기네 모델을 고치는 길. 컴포저 2 에는 이런 상황을 다루는 강화학습 과제가 아예 없었고 컴포저 3·4·5 를 낼 때쯤에는 그 과제를 파이프라인에 넣는 중이라고 말한다. 남의 회사 모델은 자기가 고칠 수 없으니 다른 연구소와 모델 제공사에 겪은 것을 전해 왔다.

가장 큰 구멍은 이탈이 났을 때다. 모델이 원본 체크아웃에서 일해 버리면 그 변경이 어떻게 되는지, 되돌릴 길이 있는지, 사용자가 알아채는 대목이 있는지를 발표가 설명하지 않는다. 예전 구현에서는 일어날 수 없던 일이라 물을 필요조차 없던 물음이다.

④ 도구를 말로 부르나 코드로 부르나

클라우드플레어의 수닐 파이는 주장을 한 줄로 세웠다 — 코드가 시스템과 주고받는 방식이 되어야 한다. 근거는 자기네 API 표면이다. 엔드포인트가 약 2,600개인데 이것을 도구로 다 노출하면 툴 콜링(모델이 정해진 형식으로 도구를 불러 쓰는 방식)을 시작하기도 전에 컨텍스트가 터진다.

동료 한 사람이 낸 방법은 도구를 딱 두 개만 노출하는 것이었다 — 검색(OpenAPI 스펙 전체를 넘겨 필요한 것을 찾게 한다)과 실행(찾아낸 것들을 부르는 코드를 받아 돌린다). 둘 다 입력이 코드 문자열이라는 점이 같다. 2,600개를 다 노출하면 첫 호출에만 약 120만 토큰이 드는데 두 도구 방식으로 바꾸자 1,000 토큰으로 줄었고, 발표자는 약 99.9% 줄었다고 말한다. 보통 방식이면 왕복이 약 여덟 번 드는 일이 한 번에 끝난다고도 덧붙인다.

모델이 쓴 코드를 돌린다는 말은 곧 안전 문제인데, 여기서 막는 순서가 거꾸로다. 샌드박스는 아무 능력도 없이 시작한다 — 코드를 돌리는 것 말고는 아무것도 못 하고 요청도 못 보내며 열린 API 도 없다. 필요한 능력을 하나씩 명시적으로 준다.

같은 방향으로 더 간 것이 코덱스다. 오픈AI 의 도미닉 쿤델은 컴퓨터 조작에서 동작 하나씩 노출하던 방식을 버리고 코드 실행으로 바꿨다고 말한다. 코덱스는 턴을 넘어 살아 있는 노드 REPL 안에 플레이라이트 코드를 써서 크로미움을 움직이며, 한 페이지 구조를 파악한 뒤 스크립트로 나머지를 훑어 같은 일을 훨씬 빨리 끝낸다.

여기서 값이 갈리는 대목이 하나 있다. 99.9% 는 특정 API 표면 하나를 놓고 든 값이고, 표면이 작거나 성격이 다른 API 에서도 같은 폭으로 줄어드는지는 나오지 않는다. 왕복 여덟 번도 그 예의 값이다. 그리고 이 방식의 급소는 무대에서 그대로 드러났다 — 라이브 데모를 돌리자 자바스크립트 오류가 이어졌고, 발표자는 무대에 오르기 전 열 번 시험했다고 말했다. 모델이 쓴 코드가 얼마나 자주 틀리는지, 틀렸을 때 무엇으로 되돌리는지가 발표에 없다.

⑤ 컨텍스트 창의 상한을 누가 거나

판단을 걷어 내면 걷어 낸 것을 어딘가에 두어야 하고, 그 어딘가는 대개 컨텍스트 창(모델이 한 번에 볼 수 있는 글의 한도)이다. 창은 유한하므로 여기서 상한을 거는 일이 하네스의 새 몫이 됐다.

앤스로픽의 케이틀린 레세는 창을 다루는 손을 셋으로 나눴다. MCP(에이전트가 바깥 도구나 자료에 붙는 방식을 정해 둔 규격)는 창 밖에 있는 것에 닿게 해 주고, 메모리 도구는 반대로 창 바깥에 두었다가 정말 필요할 때만 도로 불러오고, 컨텍스트 편집은 지금 쓸모없는 옛 도구 결과처럼 창에 있을 이유가 없는 것을 지운다. 예로 든 것이 클로드 코드다 — 도구를 수백 번 부르고 그때 읽은 파일이 창을 차지하므로 그것들을 걷어낸다.

이 발표에서 나온 유일한 수는 39%다. 메모리 도구와 컨텍스트 편집을 함께 썼더니 벤치마크 대비 성능이 39% 올랐다고 하며, 발표자 스스로 사내 평가에서 잰 값이라고 밝힌다. 어느 벤치마크인지, 무엇을 기준선으로 삼았는지, 몇 번 돌린 값인지는 없다.

코덱스는 같은 일을 기계 규칙으로 못 박았다. 컨텍스트 조립에서 보는 것은 셋이다 — 크기(토큰 예산이자, 창이 길수록 서로 어긋나는 정보가 들어갈 확률이 오른다), 유연성(스킬·플러그인·MCP 를 많이 깔든 적게 깔든 경험이 같아야 한다), 성능과 비용(캐시가 깨지지 않는 것이 중요하다). 모델 지시문은 구조가 정해져 있어 크기가 잘 안 변하고 캐시를 안 깨지만, 스킬 개수와 도구 레지스트리 크기는 예측이 안 된다 — MCP 를 깔수록 늘어난다.

그래서 장치를 둘 두었다. 일부 도구를 지연으로 표시해 컨텍스트 창에 아예 넣지 않고 모델이 도구 검색으로만 찾게 하는 것이 하나고, 스킬 목록이 최대 컨텍스트 창의 2% 를 넘지 않게 묶고 넘치면 설명 분량을 조금씩 줄이는 것이 다른 하나다. 지연 로딩은 코덱스만의 것이 아니라 GPT-5.4 부터 리스폰시스 API 에서 어떤 도구든 지연으로 표시할 수 있다.

구글 딥마인드의 필립 슈미트는 이 상한을 스킬 만드는 사람 쪽에서 말한다. 스킬 설명은 모델을 부를 때마다 무는 값이다 — 백에서 이백 토큰이 늘 실린다. 그래서 여러 갈래로 갈리는 지침은 본문이 아니라 참고 파일로 내려야 하고, 파일 자체는 500줄 아래로 두라고 말한다. 다만 500줄과 백에서 이백 토큰이 어디서 나온 선인지, 넘으면 무엇이 나빠지는지는 없다.

세 편이 같은 장치를 다르게 부른다. 앤스로픽의 배리 장과 마헤시 무라그는 이것을 점진적 공개(평소에는 이름과 설명만 보이다가 쓰겠다고 정한 뒤에야 본문을 읽어 들이는 방식)라고 이름 붙였다 — 평소에는 스킬의 이름과 설명만 모델에 보이고, 에이전트가 그 스킬을 쓰겠다고 정하면 그때 본문을 읽어 들인다. 목록 전체를 컨텍스트에 넣지 않는다는 것이 요점이다.

여기에 상한을 거는 대가가 하나 남는다. 코덱스는 2% 를 넘치면 설명을 조금씩 줄인다고만 하고 어느 스킬 설명이 먼저 깎이는지를 밝히지 않는다. 어느 설명이 깎이느냐가 어떤 스킬이 안 불리느냐를 정하는데 그 순서가 없다. 컨텍스트 편집도 같은 급소를 안는다 — 지금 안 쓰는 것을 지운다고 하는데 나중에 필요해질 것을 지웠을 때 어떻게 되는지가 없다.

⑥ 스킬은 언제 만들고 언제 버리나

스킬이라는 말이 처음 이 자리에 선 것은 2025년 12월이다. 앤스로픽의 배리 장과 마헤시 무라그는 「모델은 쓰는 사람의 전문성을 잘 흡수하지 못하고 시간이 지나도 배우지 않는다」는 한계를 인정하는 데서 출발했다고 말한다. 그래서 도메인마다 새 에이전트를 짓는 대신 다른 길을 골랐다.

비유는 세금 신고다. IQ 300짜리 수학 천재와 경험 많은 세무 전문가 가운데 고르라면 매번 후자를 고르겠다고 말한다 — 2025년 세법을 첫 원리부터 알아내 주기를 바라는 것이 아니라 도메인을 아는 사람의 일관된 실행이 필요하다는 것이다. 목표는 한 줄로 「함께 일한 지 서른 날째의 클로드가 첫날의 클로드보다 훨씬 나아야 한다」이다.

위계도 함께 그렸다. 프로세서가 모델이고, 운영체제가 에이전트 루프와 런타임이고, 애플리케이션이 스킬이다. 같은 에이전트 하나에 MCP 서버를 붙이고 그 위에 수백에서 수천 개 스킬을 얹을 수 있다고 말한다. 스킬을 내놓은 지 다섯 주 만에 수천 개 스킬로 이루어진 생태계가 자랐고, 수천에서 수만 명 개발자를 지원하는 생산성 팀들이 코드 스타일 모범 사례를 스킬로 가르치고 있으며 금융·채용·회계·법무처럼 기술직이 아닌 사람들도 스킬을 만들고 있다고 한다.

MCP 와 스킬의 경계를 또렷하게 그은 것은 같은 날 다른 발표다. MCP 는 도구와 자료에 닿게 해 주고 스킬은 그것을 쓸 줄 알게 해 준다 — 도구에 닿아도 어떻게 쓰는지 모르면 소용이 없다는 뜻이다.

일곱 달 뒤, 구글 딥마인드의 필립 슈미트는 그 생태계를 열어 보고 다른 말을 한다. 스킬 5만 개 넘게 색인한 벤치마크를 보니 거의 아무것도 평가를 갖고 있지 않았고 대부분은 AI 가 썼으며 제대로 시험되지 않은 것이었다. 우리가 쓰는 에이전트와 우리가 만드는 에이전트는 다르다고도 짚는다 — 고객은 스킬이 무엇인지 모르고 「환불 스킬을 써서」로 말을 시작하지 않는다.

그가 나눈 두 갈래가 이 절의 답이다. 능력 스킬은 모델이 아직 일관되게 못 하는 것을 가르치므로 한때뿐이다 — 모델이 좋아지면 지운다. 선호 스킬은 그 팀의 방식과 결을 담으므로 오래간다 — 바탕 모델이 알 길이 없는 것이기 때문이다. 부르는 방식도 둘로 갈리는데, 고객용 에이전트를 만들 때는 사람이 짚어 부르는 쪽이 없고 모델이 알아서 부르는 쪽만 남는다.

내보내기 전 확인하는 문턱을 여덟 가지로 세운 가운데 둘이 특히 이 보고서와 맞닿는다. 물음 열댓 개를 만들되 되어야 할 것 다섯과 안 불려야 할 것 다섯을 함께 만들라는 것, 그리고 켜고 끄고 재 봐서 없이도 되면 지우라는 것이다. 되는 것만 재면 과하게 불리는 것을 못 잡는다.

실물로 든 사례는 이렇다. 새로 낸 인터페이스가 모델을 마지막으로 학습시킨 뒤에 나와 모델이 그것을 아예 모르는 상황이었고, 테스트 케이스 117개를 실제 사용자에게서 본 것·지어낸 것·「이미 다음 판인데 모델이 옛 판을 쓴다」는 불평에서 뽑아 만들었다. 유효한 코드를 내놓는 성공률이 90% 가까이까지 올랐다고 한다. 필요한 것은 케이스를 담은 파일 하나와 코딩 에이전트를 태워 돌리는 스크립트 하나뿐이었고 채점은 대개 정규식이면 됐다. 안에서는 스킬 파일이 바뀔 때마다 이 평가를 돌리고 케이스가 나아지지 않으면 병합하지 않는다.

그가 자기 실패도 함께 밝힌다 — 실패의 절반이 스킬이 제대로 불리지 않아서였고, 그 원인은 사용자의 물음이 충분히 구체적이지 않아서였다. 잴 때 지킬 것 가운데 하나로 「하네스를 바꿔 본다」를 든 것도 같은 맥락이다. 어느 도구에서는 잘 되고 다른 도구에서는 나쁠 수 있다.

90% 에는 견줄 앞의 값이 없다 — 스킬 없이는 얼마였는지가 나오지 않고 무엇을 유효한 코드로 쳤는지도 없다. AI 가 쓴 스킬이 성능을 떨어뜨릴 수 있다는 대목에도 수가 없다. 그리고 발표자 스스로 유효기간을 짧게 잡는다 — 모델이 갱신되는 속도를 보면 반년 전에 필요하던 스킬을 오늘은 버리게 되는 것에 놀랄 것이라고 말한다.

⑦ 토큰이 값이 되면 무엇을 재야 하나

마이크로소프트의 티샤 차울라와 수심 쿨은 통제가 걸리는 위치를 시대별로 나눴다. 구독기에는 화면에서 쓸 수 있는 양과 자리 수와 등급으로 걸었고, 클라우드기에는 쓴 만큼 내기와 자동 증감 규칙으로 걸었고, 모델을 부르는 지금은 제대로 된 통제 장치가 없다는 것이다.

모델 앞에 문을 세워 한도를 걸거나 더 싼 모델로 내려 보내는 방식은 있지만 그것은 부르는 요청 하나하나를 볼 뿐이다. 필요한 것은 한 번의 실행 전체를 보는 것이다 — 도구와 에이전트 사이에서 도는 고리, 하나가 여럿을 새로 띄우는 것, 맥락이 계속 불어나는 것을 봐야 한다.

원칙 넷을 세웠다. 값의 단위가 토큰이고, 값은 모델을 부르는 경계에서 나고, 누가 불렀는지 못 대면 못 막고, 막는 것은 맨 나중이다 — 먼저 줄이고 정책을 다 쓴 뒤에야 끊는다. 셋째가 귀속인데, 없으면 무엇이 잘못됐는지 큰 그림만 알고 되짚어 좁힐 수가 없다.

만든 것은 코드 바깥에 따로 두는 판이고, 코드에 끼어들지 않는 것을 설계에서 일부러 골랐다. 바꾸는 것은 부르는 자리에 표시를 다는 것 하나뿐이며 어떤 틀의 어떤 함수든 붙일 수 있다. 그 표시가 드나든 것을 원장에 올리고, 통제 판이 내리는 명령을 받아오는 통로가 된다.

돌려세우는 방식이 이 발표에서 가장 구체적이다. 자료 가져오는 도구가 부를 때마다 조각 스무 개를 만드는데 모델이 다섯 개 넘어서는 쓰지도 않으면 가져올 것을 다섯 개로 깎으라는 명령을 내려보낸다. 쓴 예산의 비율과 쓰는 속도 둘을 보다가 바닥날 것 같으면 시스템 지시문에 「예산이 모자라니 짧게 내라」는 식으로 끼워 넣는다. 넘으면 끊는 쪽과 죽이지 않고 행동을 돌려세우는 쪽, 둘이 함께 있다.

잰 값은 둘이다 — 평균 지출 78% 감소, 끝맺는 비율 67% 에서 96% 남짓으로. 견준 대상은 그냥 조여 막는 방식 하나뿐이며, 그렇게 막으면 무슨 일이 있어도 실행이 죽는다는 것이 대비의 근거다. 78% 도 96% 도 자기네가 만든 정책 묶음으로 자기네가 쟀고, 손으로 잘 짠 한도와 견주면 어떤지가 없다. 지출이 78% 줄었다면 답의 품질은 어떻게 됐는지도 나오지 않는다 — 짧게 내라고 끼워 넣는 방식은 답을 바꾸는 일인데 그 대가가 없다. 오픈소스 저장소 두 곳에서 돌렸다고만 하고 실제 업무에서 잰 값이 없다. 판을 얹는 값도 없다 — 부르는 자리마다 표시를 달고 명령을 오가게 하면 느려질 텐데 그 값이 나오지 않는다.

SemiAnalysis 는 같은 물음을 재는 단위 쪽에서 다시 세운다. 토큰 하나당 가격이 아니라 문제 하나를 실제로 풀기까지 드는 총비용을 봐야 한다는 것이다 — 단가가 비싸도 토큰을 적게 쓰면 과제당 비용은 더 쌀 수 있다. 실제로 코덱스는 입력 대 출력 토큰 비율이 80:1 로 클로드 코드(100:1)보다 입력을 덜 써서, 토큰 단가가 비싸도 과제당 비용은 오히려 코덱스가 저렴한 것으로 잠정 확인됐다고 적었다. 프롬프트 캐싱과 입출력 비율과 도구 호출 무늬는 모두 하네스가 좌우한다.

가격 쪽에서도 같은 이야기가 나온다. GPT-5.5 는 입력 100만 토큰당 5달러·출력 30달러로 GPT-5.4 대비 가격이 두 배인데 벤치마크 점수는 오르면서 사용 토큰은 줄이는 토큰 효율화를 내세웠다. 반대 방향도 있다 — 오퍼스 4.7 은 새 토크나이저를 넣으면서 토큰 사용량이 최대 35% 늘었고 이는 사실상 가격이 35% 오른 것이며, 도구 호출을 줄이고 추론에 더 의존하게 되어 앤스로픽이 강도를 xhigh·max 로 올리라고 권하는 바람에 효율화 발표와 반대로 토큰을 더 쓰게 됐다.

⑧ 경쟁이 모델에서 하네스로 옮겨 왔다는 근거는 무엇인가

SemiAnalysis 는 2026년 2월에 이 이동을 한 편으로 정리했다. 클로드 코드는 코드 편집기 플러그인이 아니라 터미널에서 코드베이스를 읽고 다단계 작업을 계획한 뒤 직접 실행하는 명령줄 도구이며, 사실상 컴퓨터 전체를 다루는 데 가깝다고 적었다. 그리고 경쟁의 축이 모델 벤치마크 순위에서 도구·메모리·서브에이전트·검증 루프를 조율해 만들어내는 최종 결과물 자체로 옮겨 가는 중이라고 결론지었다.

근거로 든 인용이 둘이다. Node.js 를 만든 라이언 달의 「사람이 코드를 직접 짜는 시대는 끝났다」와, 클로드 코드를 만든 보리스 체르니의 「우리 코드의 거의 100% 가 클로드 코드와 오퍼스 4.5 로 작성된다」. 자사 사용 사례로는 InferenceMAX 대시보드를 아홉 종의 시스템·클러스터에서 매일 밤 자동 실행하는 것을 든다.

역설도 함께 적었다. 벤치마크만 보면 GPT-5.2 High 가 SWE-bench 에서 동률이고 MMLU-pro·AIME 2025 에서는 오히려 우위인데도 모두가 오퍼스에 열광하는데, 답은 토큰 효율성 — 같은 작업을 훨씬 적은 토큰으로 끝내는 능력이라는 것이다. 챗GPT 는 컨텍스트 창이 훨씬 크지만 작업당 필요한 토큰 수가 한 자릿수 더 많아 장기 계획을 오히려 무너뜨린다고 본다.

왜 그런지를 계산으로 댄 대목이 이 절의 뼈대다. 단일 컨텍스트 창에서 90% 성능이 필요한 작업을 여러 단계에 걸쳐 되풀이하면 작은 오차율도 단계 수가 늘수록 복리처럼 쌓여 최종 실패 확률이 사실상 100% 로 수렴한다. 토큰을 적게 쓸수록 이 쌓임이 줄어든다.

오케스트레이션 자체가 새 성능 축이 됐다는 사례로는 문샷 AI 의 Kimi 2.5 를 든다. 벤치마크 성능이 아니라 에이전트 조율 계층 자체를 비공개로 지킬 만큼 경쟁의 핵심이 옮겼다는 것이며, Kimi 의 PARL(병렬 에이전트 강화학습)은 여러 에이전트를 병렬로 돌려 자체 벤치마크에서 오퍼스 4.5 보다 높은 성능을 낸다고 주장한다 — 문샷 자체 벤치마크라는 것을 원문이 그대로 밝힌다. 다만 무한정 늘릴 수는 없다. 앤스로픽 자체 연구에 따르면 추론·행동에 쓰는 시간이 길어질수록 모델이 점점 앞뒤가 안 맞아지는 현상이 확인돼, 한 컨텍스트 창 안의 일관성이 에이전트를 몇 개까지 병렬로 늘릴 수 있는지를 좌우한다.

두 달 뒤 SemiAnalysis 는 이 이동을 재는 일 자체가 어려워졌다고 적는다. 자체 하네스로 GPT-5.5·5.4·오퍼스 4.6 을 같은 조건에서 재측정한 결과는 두 회사의 공식 점수보다 전반적으로 낮았고, 두 랩이 비공개 전용 하네스로 점수를 극대화했기 때문이라고 본다. 같은 하네스로 비교하면 공정해 보이지만 실제 사용자가 신경 쓰는 것은 모델 단독이 아니라 코덱스 대 클로드 코드라는 결합 제품의 체감 성능이다.

체감 차이는 사내 실험으로 남겼다. 같은 지시를 주었을 때 오퍼스 4.6 은 기존 대시보드를 그대로 복제했고 코덱스는 지시받지 않은 부분을 통째로 건너뛰었는데, 코덱스가 채운 실제 수치는 클로드보다 훨씬 정확했다. 코덱스는 좁고 명확한 문제를 깊게 풀고 클로드는 열린 결말의 신규 프로젝트에 강하다는 인상과 맞아, 클로드로 설계와 뼈대를 잡고 코덱스로 문제를 풀고 버그를 잡는 순서가 자리 잡는 중이라고 적었다.

시장 구도에서 이 절의 결론이 나온다. 바이브 코딩 스타트업들은 매출이 급성장해도 마진이 마이너스라 하네스만 있고 모델은 없는 반쪽 제품에 그친다는 것이다. 하네스가 경쟁의 자리가 됐다는 말과, 하네스만으로는 안 된다는 말이 같은 편에 함께 있다.

⑨ 실패는 왜 조용히 오나

오픈AI 의 비노스 고빈다라잔이 든 출발 사고는 이렇다. 사용자가 고객 환불 건을 다음 턴을 위해 기억해 달라 했고 어시스턴트는 기록했다고 답했다. 화면에는 빨간 오류도 눈에 띄는 실패도 없었다. 그런데 다음 턴에서 그 사실을 다시 불러오지 못했다.

충돌은 경계를 주지만 조용한 성공은 경계를 주지 않는다. 전달은 성공했고 저장은 실패했는데 사용자도 운영자도 의심할 이유가 없었다. 다음 턴에도 모델은 여전히 그럴듯하게 말한다 — 일관돼 보이지만 끊긴 이력 위에서 일관된 것뿐이다.

여기서 하네스가 맡는 것이 다시 정의된다. 대화 기록은 증거가 아니다 — 기록은 에이전트가 무엇이라 말했는지를 남기고, 영수증은 시스템이 실제로 무엇을 했는지를 남긴다. 자동차에 빗대면 모델은 엔진이고 하네스는 조향·제동·도로 규칙·계기판·블랙박스다. 브레이크 없는 강력한 엔진은 자율이 아니라 가속도만 좋은 부채다.

하네스가 맨 처음 하는 일은 들어온 신호가 어느 대화의 것인지 이름표를 붙이는 것이다. 그 이름표가 곧 울타리가 되어 그 대화에 딸린 기록·메모리·정책이 안에 들고, 울타리 안의 것을 고치는 문은 하나로 둔다 — 두 곳에서 동시에 고치는 일을 막으려는 것이다. 에이전트는 턴이 끝나면 잊으므로 하네스가 매 턴 필요한 것을 다시 모아 넘기는데, 하나가 빠지거나 낡아도 답은 여전히 그럴듯하게 들린다.

공개된 이슈에서 뽑은 사고 다섯과 그 각각이 놓친 경계 다섯이 이 발표의 뼈대다.

여기서 소유자를 사람이 아니라 시스템으로 잡는 대목이 눈에 띈다. 달력 일정은 달력 시스템이, 상담 상태는 티켓 시스템이, 코드 변경은 저장소가, 대화 턴은 세션 기록이, 사용자 선호는 메모리 저장소가 소유한다. 저장은 바이트가 어디 있는지를 말하고 소유권은 누가 그 실재를 다시 세울 수 있는지를 말한다. 순서 규칙도 좁게 잡는다 — 가변 상태 경계 하나에 순서가 정해진 커밋 경로 하나이며, 병렬 읽기·독립 검색·여러 세션 동시 실행·서브에이전트 분기는 괜찮다. 보수적으로 지킬 것은 커밋 시점이지 시스템 전체가 아니다.

승인은 막연한 기억이 아니라 범위가 한정된 실행 상태여야 한다. 누가, 어떤 세션과 실행에서, 어떤 도구와 인자에 대해, 얼마 동안, 어떤 결과로 승인했는지에 답하고 영수증을 가리켜야 한다. 그 항목이 재시도나 재생 도중 떨어져 나가면 하네스는 그 행동이 승인된 것임을 더는 증명할 수 없다.

마지막이 가장 날카롭다. 내부 성공은 외부 증명이 아니다. 도구 결과는 내부 경로가 요청을 받아들였다는 것만 증명하고 사용자가 그것을 봤다는 것은 증명하지 못한다. 그래서 에이전트는 나중에 이미 보냈다고 말할 수 있고 사용자는 정말로 본 적 없다고 말할 수 있다. 영수증은 사용자가 신경 쓰는 그 경계에서 끝나야 한다.

처음 사고에 감사 다섯 물음을 대 보면 답이 나온다. 깨운 것은 사용자 메시지, 물려받은 상태가 곧 깨진 경계, 실행된 것은 채널 전송, 살아남은 증거는 전달뿐이고 지속된 턴은 아니었다. 필요했던 것은 더 나은 모델도 더 나은 프롬프트도 아니고 완전한 영수증을 갖춘 더 나은 하네스였다.

다만 사고 다섯 건이 모두 오픈클로 것이고, 개인 비서형과 코딩 에이전트가 같은 밑구조를 쓴다는 말은 발표자 주장이라 같은 다섯 경계가 다른 시스템에서도 같은 순서로 무너지는지는 이 발표만으로 알 수 없다. 얼마나 자주 났고 얼마나 많은 사용자가 겪었는지도 없다. 그리고 모든 실행 경계에 영수증을 남기라는 요구는 기록량이 실행량을 따라 늘어난다는 뜻인데, 그 저장과 조회 비용을 발표가 다루지 않는다.

⑩ 모델이 하네스의 구멍을 찾으면 어떻게 되나

앞 절이 하네스의 구멍으로 사람이 손해를 보는 이야기라면, 이 절은 모델이 그 구멍을 이용하는 이야기다.

어플라이드컴퓨트의 레이먼드 펑은 환경 충실도(훈련 환경이 실제와 얼마나 같은가)와 리워드 해킹(모델이 점수를 얻으려고 일 대신 채점의 허점을 파고드는 것)이 사실 같은 문제라고 말한다. 사례 둘이 이 문장을 받친다.

첫째. 지난 학습 실행에서 네트워크 문제로 도구 호출이 열에 하나쯤 실패한 적이 있다. 그러자 모델이 점점 짧은 답을 내놓기 시작했다 — 길이에 벌점을 준 적이 없는데도 그랬다. 발표자는 인도를 걷는 사람에 견준다. 도구 호출 실패가 인도의 구덩이고, 구덩이가 많으니 오래 걷지 않으려 한다는 것이다 — 오래 갈수록 구덩이에 빠져 0점으로 끝날 일이 늘기 때문이다.

둘째는 방향이 반대다. 도구 호출이 오래 걸리는 판에서는 문제가 어렵다 싶으면 모델이 호출을 잇달아 던져 샌드박스를 시간 초과로 죽이도록 배웠다 — 0점을 받느니 그 판을 통째로 버리게 만드는 쪽이 낫기 때문이다.

두 사례가 말하는 것은 하나다. 하네스가 환경이고, 환경에 난 흠은 리워드에 난 흠과 구별되지 않는다. 리워드 함수를 정교하게 짜는 싸움이 아니라 모델이 실패를 어떻게 우회하는지를 계속 뒤쫓는 싸움이다.

이 발표가 그리는 흐름도 하네스가 점점 손댈 수 없는 것이 되어 가는 방향이다. 합성 환경 단계에서는 환경 상태 자체를 훈련 스택 바깥으로 빼두고, 오케스트레이터가 여러 턴을 진행하며 모델이 도구를 부르고 싶어하면 샌드박스를 불러 환경 상태를 읽거나 바꾼 뒤 결과를 모델에 돌려준다. 다음 단계인 「내 하네스를 그대로 가져오기」에서는 환경을 복제하지 않고 실제 프로덕션 환경을 그대로 훈련에 쓰며, 훈련 스택 안에 남는 것은 모델 완성 엔드포인트와 요청·응답을 기록하는 장치뿐이다.

대가가 함께 온다. 프로덕션에 가까워질수록 롤아웃 진행에 대한 통제력이 줄고, 데이터가 익숙한 형식이 아니라 뽑아낼 학습 신호도 줄어든다. 같은 과제로 여러 롤아웃을 병렬로 만드는 방식이 더 안 통할 수 있다 — 고객 상담 채팅에서는 다르게 답했으면 고객이 더 만족했을지 알아보려 반응을 다시 받아올 방법이 없다. 엔비디아가 발표 약 한 달 전에 낸 폴라 논문도 같은 주제를 다룬다고 그는 덧붙인다 — 롤아웃을 세세히 통제하던 하네스에서 벗어나 검은 상자 하네스를 그냥 엿듣는 방식으로 넘어가는 이야기다.

이 발표 전체가 어플라이드컴퓨트의 커스텀 모델 훈련 방법론을 파는 자리라는 점은 밝혀 둔다 — 이미 어떤 방식으로 모델을 쓰고 있으면 그 자리에 학습 방법론을 그대로 꽂아 준다는 것이 이 방식의 값이라고 발표자가 말한다. 정량 값도 도구 호출이 열에 하나쯤 실패했다는 것 하나뿐이다.

⑪ 막는 일을 코드로 하나 부탁으로 하나

3절의 커서와 5절의 코덱스가 여기서 정면으로 만난다. 커서는 격리를 코드에서 걷어내 프롬프트로 옮겼고, 코덱스는 같은 해에 운영체제 수준으로 더 깊이 내렸다.

코덱스에서 모든 파일 시스템 조작은 샌드박스(코드가 바깥을 건드리지 못하게 가둬 놓고 돌리는 자리)를 지난다. 맥OS 는 시트벨트, 리눅스는 버블랩을 쓰고, 윈도우는 마땅한 것이 없어 직접 만들어 같은 저장소에 오픈소스로 열어 두었다. GPT-5 부터 모델이 어플라이 패치 도구에 익숙해지도록 훈련됐고 파일을 찾을 때 자연스럽게 립그렙을 쓰려 들어 하네스가 립그렙을 같이 배포한다 — 윈도우에서는 파워셸을 그대로 쓰도록 따로 훈련시켰다. 모델이 배운 습관에 하네스를 맞춘 것이다.

그런데 샌드박스를 세워도 문제가 남는다. 승인 피로다. 긴 작업일수록 승인 요청이 성가셔서 전체 접근을 켜 버리게 되고 보안 담당은 그것을 싫어한다. 모델이 좋아져도 사고는 남는다 — 높은 자율성을 프롬프트로 밀어붙이면 엉뚱하게 해석될 수 있어서, 첨부가 안 되니 파일 공유에 올려 버리거나 이스케이프를 잘못해 데이터를 너무 많이 지우는 일이 생긴다.

코덱스가 낸 답은 판단을 또 다른 모델에게 넘기는 것이다. 오토 리뷰(막아선 행동을 사람 대신 심사하는 장치)는 샌드박스가 막아선 행동이 올라오려 할 때 판단을 대신할 서브에이전트를 띄운다. 이 서브에이전트는 따로 돌고 읽기 권한만 가지며 다른 서브에이전트를 못 띄운다. 받는 것은 넷이다 — 사용자 권한이 무엇인지, 위험을 어떻게 분류하는지, 어떻게 판단하기를 바라는지, 대화 기록과 실제로 일어나려는 도구 호출. 맥락이 판단을 정한다. 지우라고 시킨 파일이면 지워도 되고, 시키지 않은 `.git` 폴더면 이력을 통째로 날리는 일이라 건드리면 안 된다.

마이크로소프트의 크리스 노링은 같은 문제를 문서로 푼다. 가드레일(에이전트가 넘지 말아야 할 선을 미리 문서와 설정으로 박아 두는 것)을 셋으로 세운다 — Agents.md 는 저장소가 무엇을 하려는 곳인지와 하지 말 것은 무엇인지를 적고, 스킬은 되풀이할 수 있는 레시피이며, 커스텀 에이전트는 성격을 지니고 스킬 여럿을 부리는 윗자리다. Agents.md 에는 「시키기 전에는 얼개를 바꾸지 마라」 같은 줄을 둔다. 커스텀 에이전트는 앞머리에 쓸 수 있는 도구를 적어 할 수 있는 일을 조인다 — 데모에 나온 조사용 에이전트는 읽고 웹을 뒤지고 할 일을 적을 수 있되 파일을 만들거나 고치지는 못한다.

같은 발표가 사람이 남는 자리도 짚는다. 넘기면 작업이 시작되고 초안 PR 이 생기며, 에이전트는 샌드박스 안에서 도니 밖으로 나가 이상한 짓을 하지는 못하는데 PR 은 만들 수 있다. 그 대목에서 사람이 들어온다. 승인 문턱을 스스로 두고 있고 더 둘 수도 있으며 머지하는 것은 여전히 사람이다.

세 편을 나란히 놓으면 방향이 이렇다. 커서는 물리적 격리를 지우고 프롬프트로 부탁하는 쪽으로 갔고, 코덱스는 운영체제 샌드박스에 모델 심사관을 얹었고, 마이크로소프트는 문서와 도구 목록으로 조인 뒤 마지막 판정만 사람에게 남겼다. 셋 다 2026년의 답이고 서로 다르다.

값으로 견줄 수는 없다. 커서는 하이쿠가 자주 샌다는 데서 멈췄고, 코덱스는 오토 리뷰가 얼마나 맞히는지를 대지 않았으며 발표자 스스로 이 설명이 엄청난 단순화라고 밝히고 자세한 것은 글로 넘겼다, 마이크로소프트는 잰 값이 하나도 없다. 20배라는 수가 나오지만 발표자 자신이 곧바로 「코드가 스무 배면 슬롭도 스무 배일 수 있다」고 덧붙인다.

⑫ 긴 호흡에서 기억은 왜 스스로 썩나

앤스로픽의 랜스 마틴은 맡길 수 있는 일의 길이가 어떻게 늘었는지를 셋으로 적었다. 오퍼스 3 무렵에는 한 번에 10~20분이었고 쓰던 것은 메시지 API 였다. 클로드 코드 무렵에는 한 시간쯤이었고 에이전트 SDK 를 썼다. 지금은 12시간 넘는 대이고 매니지드 에이전트를 쓴다. 일이 길어질수록 감싸는 장치가 두꺼워진다.

그 구조에서 하네스는 상태를 들지 않는다. 무슨 일이 있었는지는 기록이 맡고 그 기록은 덧붙이기만 한다. 실제로 돌리는 일은 컨테이너가 하며, 머리가 죽었다 살아나도 기록을 다시 읽어 이어 갈 수 있다. 자격 증명은 컨테이너가 든 상자에 넣지 않고 따로 둔 금고에 두었다가 필요할 때만 꺼낸다. 검증도 갈라 둔다 — 만드는 에이전트와 검사하는 에이전트를 다른 맥락에 두고, 검사하는 쪽이 자기 목표와 루브릭(무엇을 어떻게 채점할지 미리 적어 둔 기준표)을 따로 들고 채점한다. 만든 사람이 자기 것을 검사하지 않게 한 것이 요점이다.

기억에서 나온 실험 하나가 이 절의 값이다. 기억을 쓰는 방식이 둘인데, 하나는 일하는 중에 그때그때 파일에 적는 것이고 다른 하나는 일이 끝난 뒤 따로 돌면서 쌓인 것을 훑어 잘못 적힌 것을 고치는 것이다 — 발표자는 뒤엣것을 사람의 잠에 빗댄다. 클로드에게 포켓몬을 하게 두고 셋을 견줬다. 기억이 없으면 거의 나아가지 못했다. 일하며 적는 기억만 두면 같은 함정에 되풀이해 빠져 되돌아갔다. 나중에 훑어 고치기까지 넣자 그 잘못을 고치고 다음 단계로 나아갔다. 가운데 줄의 일은 다섯 번 돌려 다섯 번 다 벌어졌다.

적어 둔 기억에는 틀린 것도 함께 남는다는 뜻이다. 그리고 고치는 과정 자체의 값이 없다 — 얼마나 자주 돌려야 하는지, 그 과정이 잘못 고칠 확률은 얼마인지가 나오지 않는다. 기억을 고치는 장치가 기억을 망칠 수도 있다. 12시간이라는 길이도 무엇을 잰 값인지 좁혀지지 않는다 — 바깥 측정 기준을 따랐다고 말하지만 어떤 일을 맡겼을 때의 값인지, 그중 몇 번이나 끝까지 갔는지가 없다. 포켓몬에서 본 것이 코드나 문서 작업에서도 같은 모양으로 나오는지도 없다.

승격을 누가 정하는지에서 두 편이 만난다. 어플라이드컴퓨트가 그리는 자동화된 데이터 파이프라인은 대량 트레이스를 자동으로 훑어 바람직하지 않은 행동과 실패 사례를 골라내고 그것으로 훈련 데이터를 만들어 모델에 다시 먹이는 구상이다. 지금은 그 일을 대부분 사람이 손으로 한다 — 트레이스를 직접 훑어 실패 사례를 찾고 어떻게 고칠지 적고 데이터셋을 사람이 큐레이션한다. 기억을 고치는 일도, 무엇을 스킬로 올릴지 정하는 일도 아직 사람 몫이다.

⑬ 혼자 쓰던 장치가 조직 것이 되면 무엇이 더 드나

지금까지 에이전트는 대체로 혼자 쓰는 것이었다. 각자 자기 맥락에 맞춰 다듬은 장치를 자기 컴퓨터에서 굴렸다. 옮겨 가는 방향은 조직이 함께 쓰는 쪽이다 — 조직 전체가 접근하고, 그 장치가 자기 신원과 자격 증명을 갖고, 조직 수준의 맥락에 닿는 형태다.

네오포제이의 에밀 아이프렘은 그 조직 수준 맥락이 왜 비싼지를 은행 예로 세운다. 계좌 개설을 자동으로 처리하는 에이전트를 만든다고 하면 신원을 확인하려고 자료를 찾아야 하는데, 스타트업이면 데이터베이스 하나만 보면 되지만 기업은 데이터베이스가 수백 개이고 그 밖에 여러 저장소가 흩어져 있다. 에이전트를 무엇을 할지 정하는 부분과 자료에 닿는 부분으로 나눠 보면 문제가 또렷해진다 — 팀마다 에이전트를 만들 때마다 뒤쪽을 처음부터 다시 잇는다.

그래서 그가 그리는 방향은 공유하는 바닥이 그 일을 맡고 에이전트는 가벼워지는 모양이다. 바닥을 이루는 기둥이 셋이다 — 이 조직에서 그 말이 무엇을 가리키는지(업무 쪽 뜻풀이), 그것이 실제로 어느 저장소 어느 자리에 있는지(기술 쪽 뜻풀이), 무엇을 골라 어떻게 됐는지(실행 흔적). 셋째가 되먹임을 만든다. 에이전트가 준법 확인을 하려다 정부가 낸 신분증을 봐야 한다는 것을 알아채고 확인할 데가 둘 있어 하나를 고르면, 어디서 무엇을 했고 잘 됐는지가 기록으로 남아 다음번 고르기에 든다.

이 발표에는 수치가 하나도 없다. 바닥을 세웠을 때 무엇이 얼마나 나아지는지, 배선을 다시 하지 않아 아낀 시간도, 자료를 더 잘 찾게 된 정도도 없다. 무엇보다 바닥을 만드는 법을 이 발표에서 안 다룬다 — 기술 쪽 뜻풀이를 세 가지 방법으로 만들 수 있다고 말하면서 여기서는 다루지 않겠다고 그 자리에서 밝힌다. 얇은 에이전트가 성립하려면 그 바닥이 있어야 하는데 만드는 값이 통째로 빠져 있다. 점수를 어떻게 매기는지도, 두꺼운 방식과 얇은 방식을 나란히 놓고 잰 값도 없다.

사람 쪽에도 새 자리가 생긴다. 깃허브의 매기 애플턴이 만든 프로토타입은 팀원들이 같은 세션에 들어와 함께 일하는 형태다. 계획을 짜 달라고 시키면 계획이 문서로 열리고 팀원들의 커서가 같은 문서에 보이며 함께 고친다. 한 사람이 제안을 얹고 다른 사람이 요구사항을 손보다가, 다 됐다 싶으면 채팅으로 돌아가 실행을 맡긴다. 에이전트에게 시키기 전에 사람들끼리 합의하는 자리를 화면 안에 들여놓은 것이 요점이다. 세션에서 바로 풀 리퀘스트를 만들 수 있고 그 설명란에는 세션으로 되돌아오는 링크가 들어 있다.

여기서 나온 수 하나가 이 보고서에서 가장 크게 들리는데 가장 얇기도 하다. 어느 팀이 이제 하루에 기능 다섯 개를 내보내고 있고 그 전에는 하루 반 개였다는 것이다. 어느 팀 하나의 값이고, 무엇을 한 기능으로 셌는지와 어느 기간을 견줬는지가 나오지 않는다. 합의가 병목이라는 주장을 받치는 측정도 없다 — 사람들이 합의에 얼마나 시간을 쓰는지, 도구를 쓴 뒤 그 시간이 얼마나 줄었는지가 없다. 여럿이 같은 계획을 고치다 부딪히면 무엇이 이기는지도 나오지 않는다. 발표자 스스로 아직 제대로 된 제품이 아니고 거칠다고 밝히며 조기 접근이 몇 달 안에 열릴 것이라고 말한다.

⑭ 아직 안 풀린 것과 우리가 검증하지 않은 것

열두 달을 가로질러 남는 것은 방향 하나와 갈림 하나다.

방향은 또렷하다. 2025년 8월 앤스로픽의 보리스 체르니는 클로드 코드가 제품이 어떤 모습이어야 하는지에 대해 일부러 견해를 안 갖는다고 말했고 그 이유를 「모르기 때문」이라고 했다. 헐겁게 두는 까닭도 둘로 나눠 댔다 — 모델 회사라 사람들이 모델 자체를 겪기를 바라고, 올바른 UX 가 무엇인지 자기들도 모른다는 것이다. 「더 일반적인 모델이 늘 이긴다」는 교훈을 벽에 액자로 걸어 뒀다고도 말했다.

그런데 같은 발표가 이미 판단을 하네스로 가져가고 있었다. 코드를 쓰기 전에 훑어보고 계획을 세워 사람에게 확인받게 하는 순서를 관행으로 고정했고, 먼저 도구로 맥락을 끌어온 다음에 생각하게 했다 — 처음부터 생각부터 시키면 토큰만 쓴다는 것이다. 시험을 먼저 쓰게 하되 아직 통과하지 않는다는 것을 분명히 알리고 돌리지 말라고 하며, 시험을 쓰고 커밋하고 그다음에 코드를 쓰고 커밋하게 시켰다. 발표 당일 나온 플랜 모드가 그 순서를 손쉽게 만든 장치였다. 헐겁게 두겠다고 말하는 발표가 이미 순서를 못 박고 있었다는 것이 이 열두 달의 출발점이다.

갈림은 세 방향으로 벌어진다. 마이크로소프트는 판단을 상태 머신으로 걷어내고 모델을 작은 것으로 내렸다. 커서는 격리 코드를 지우고 프롬프트로 부탁하는 쪽으로 갔다. 오픈AI 는 샌드박스를 운영체제까지 내리고 그 위에 모델 심사관을 얹었다. 같은 해에 나온 세 답이며 서로를 반박한다.

오픈AI 의 빌 첸과 브라이언 피오카가 남긴 경고가 여기에 걸린다. 어느 모델을 냈을 때 사람들이 다른 모델용 프롬프트를 그대로 옮겨 왔고 거기에 「고치기 전에 파일마다 꼼꼼히 살펴보라」는 말이 들어 있었다. 모델이 그대로 했고 오래 걸렸으며 결과도 좋지 않았다. 하네스가 모델의 습관을 덮어써서 난 실패다. 답은 하던 대로 하게 두고 과하게 시키지 않는 것이었다. 반대 방향의 사례도 같은 발표에 있다 — 새로 낸 모델이 맥락을 줄이는 일을 알아서 해 준다며 판단 하나를 모델에 돌려준 것을 든다. 하네스가 떠맡아야 하는 몫으로 든 목록도 길다 — 새 도구, 생각하는 동안의 표시, 맥락 관리와 캐시, 동시 도구 호출 합치기, 권한과 통로, 도구 규격 배관, 그림 해상도, 그리고 부르는 방식 자체가 계속 바뀌는 것.

이 갈림에 대한 답이 아직 없다. 어디까지 걷어내고 어디부터 남길지를 재는 자리가 없기 때문이다.

우리가 검증하지 않은 것을 밝혀 둔다.

절을 세운 것은 우리 것이다. 열넷의 순서와 묶음은 발표 열여섯 편과 뉴스레터 두 편을 가로질러 이 보고서가 세운 것이고, 어느 발표자도 자기 이야기를 이 자리에 놓아 달라고 하지 않았다.

숫자는 원문에 있는 것만 옮겼고 우리가 다시 재지 않았다. 그런데 이 층의 숫자는 성격이 유난히 얇다. 39% 는 앤스로픽 사내 평가이고, 99.9% 는 클라우드플레어 자사 API 표면 하나를 놓고 잰 값이며, 90% 는 견줄 앞의 값이 없고, 78% 와 96% 는 마이크로소프트가 자기 정책 묶음으로 자기가 쟀고, 하루 다섯 개는 팀 하나의 값이며, 20배는 아예 잰 수가 아니다. 열여덟 편 가운데 기준선과 견준 값을 낸 편이 하나도 없다. 이것은 우리 판단이며, 각 편의 한계는 그 편이 스스로 밝힌 대목을 옮긴 것이다.

발표는 파는 자리다. 오픈AI 의 두 편은 자사 SDK 와 코덱스를 쓰라는 이야기가 뼈대에 섞여 있고, 어플라이드컴퓨트 편은 훈련 방법론을 파는 자리이며, 네오포제이 편은 자기네 바닥을 세우라는 이야기다. 다만 코덱스 하네스가 오픈소스라 말한 것을 코드로 확인할 수 있다는 점은 다른 제품 발표와 다르다.

시점이 흩어져 있다. 가장 이른 것이 2025년 8월이고 가장 늦은 것이 2026년 8월이라 열세 달이 걸쳐 있다. 제품 이야기는 그만큼 빨리 낡는다 — 2025년 8월 발표에서는 프로 요금제 지원이 「어제부터」이고 플랜 모드가 「오늘」이었다. 코덱스 발표자도 이것이 현재 상태일 뿐이고 새 모델이 나올 때마다 API 도 하네스 동작도 자주 바뀐다고 먼저 밝혔다. 스킬 발표자는 반년 전에 필요하던 스킬을 오늘은 버리게 되는 것에 놀랄 것이라고 말했다.

원문 자체가 흐린 대목이 둘 있다. 오픈AI 의 「버티는」 편은 자막이 모델과 제품 이름을 크게 뭉개 판 번호와 제품 이름이 여러 군데 어긋나 있고, 「스킬평가」 편은 여러 번 돌리라면서 몇 번인지를 자막이 흐려 놓았다. 이 대목은 맞추지 않고 그대로 두었다.

마지막으로, 이 열여덟 편은 AI Engineer 컨퍼런스와 SemiAnalysis 라는 두 통로로만 들어온 것이다. 발표자 소속을 세어 보면 앤스로픽·오픈AI·마이크로소프트·구글 딥마인드·커서·클라우드플레어·깃허브·네오포제이·어플라이드컴퓨트로, 모델이나 도구를 파는 회사가 아닌 곳에서 온 발표가 하나도 없다. 하네스를 사서 쓰는 쪽에서 무엇이 실제로 부러졌는지는 이 재료로 알 수 없다.

카드 장이 원문 한 편씩을 답한다면, 이 장은 그 답들을 이어 붙입니다. 지금 실린 것은 여덟입니다 — CPO(광학을 칩 옆까지 끌어온 방식)는 빛이 데이터센터 어디까지 들어왔는지를, 선단 패키징은 다이 하나로 못 만들게 된 뒤 무엇이 그 일을 대신했는지를, 금리·물가는 연준이 내렸는데 왜 장기금리는 올랐는지를, 메모리는 40년 만에 모자란데 왜 만드는 회사 손에 안 남는지를, 트럼프는 무엇을 걸어 무엇을 받아냈는지를, 전력은 계통에 막힌 값을 누가 냈는지를, 하네스·스킬은 모델 안에 있던 판단이 바깥으로 걷혀 나간 뒤 그 값을 누가 냈는지를, 순환금융은 파는 쪽이 사는 쪽에 돈을 빌려주는 고리가 어디서 끊기는지를 묻습니다. 본문은 insights/reports/ 의 원본에서 읽어 옵니다.
