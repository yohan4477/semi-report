# 원문 분석과 보고서 작성 — 전부 쪼개기다

원문을 뜯는 일도 보고서를 쓰는 일도 하는 일은 하나다. **쪼갠다.** 무엇을 어떤 기준으로
가르느냐가 글의 전부이고, 나머지(문장·도해·번호)는 그 뒤에 붙는 것이다.

쪼개는 법에 정해진 목록은 없다. 깊이에도 제한이 없다. 한 대상을 여러 구조로 쪼갤 수 있고,
그중 무엇을 쓸지 고르는 것이 실력이다.

## 목차

```
1  쪼개는 법        1-1 수식  ·  1-2 프로세스  ·  1-3 그 밖  ·  1-4 목록이 아니다
2  MECE            2-1 겹치나  ·  2-2 빠졌나  ·  2-3 층위가 같나
3  깊이            3-1 레벨 1 은 아무것도 아니다  ·  3-2 층마다 다른 법  ·  3-3 멈추는 자리
4  여러 뷰          4-1 같은 것을 여러 구조로  ·  4-2 베스트 뷰 고르기
5  적용            5-1 원문 분석  ·  5-2 보고서 작성  ·  5-3 검사
```

---

## 1. 쪼개는 법

### 1-1 수식 — 구성요소의 합이나 곱

가장 센 쪼개기다. **부분을 합치거나 곱하면 원래 값이 나온다**는 것이 증명되므로 빠진 것이
바로 드러난다.

```
합    지연 = 프리필 + 디코드 + 대기
      다이 면적 = 연산 배열 + 온칩 메모리 + 인터페이스
곱    매출 = 단가 × 수량
      전력 = 전압 × 전류            600kW = 48V × 12,500A = 800V × 750A
      파드 = 그룹 36 × 보드 8 × 칩 4 = 1,152칩
```

숫자를 쓰라는 말이 아니다. **무엇을 더하고 무엇을 곱해 그 값이 나왔는지**를 남기라는
말이다. 항이 그대로 아래 층의 마디가 된다.

식이 서면 빠진 항이 보인다. 「전력이 얼마나 드나」를 사실 셋으로 늘어놓으면 모듈 전력과
케이블 수가 나란한 값이지만, `트랜시버 전력 = 케이블 수 × 양 끝 2개 × 모듈 30W` 로 적으면
랙 하나가 그것만으로 얼마를 먹는지가 물음이 된다.

### 1-2 프로세스 — 순서로 가른다

밸류체인·공정·의사결정 흐름. **앞 단계의 산출이 뒷 단계의 입력**이 되면 프로세스다.

```
밸류체인   설계 → 파운드리 → 패키징 → 보드 → 랙 → 데이터센터
공정       첫 RTL → 테이프아웃 → 베타 → 양산
글의 흐름   무엇을 노렸나 → 무엇을 했나 → 무엇이 나왔나 → 무엇을 모르나
```

프로세스로 갈랐으면 **순서가 뜻이다.** 성과를 공정 앞에 두면 만들기 전에 재는 셈이 된다.
차례가 맞는지 반드시 되짚는다.

### 1-3 그 밖

```
부분 나눔   칩 안 / 칩 사이 · 메모리 / 연산 / 연결
층위        칩 → 보드 → 랙 → 도메인 (담는 것과 담기는 것)
대비        우리 것 / 견주는 것 · 되는 조건 / 안 되는 조건
조건 갈림   비율이 고정이면 전담 칩, 바뀌면 균형 칩
인과 사슬   구리 도달거리가 준다 → 스위치를 옮긴다 → 랙 하나에 가둔다
주체        누가 만드나 / 누가 사나 / 누가 겨루나
```

### 1-4 목록이 아니다

위의 것들은 **자주 쓰이는 것을 적어 둔 것이지 고를 메뉴가 아니다.** 대상이 새 기준을
주면 새 기준으로 가른다. 목록에서 고르기 시작하면 모든 글이 같은 모양으로 굽는다.

## 2. MECE

### 2-1 겹치나

두 마디가 같은 물음을 답하고 있으면 안 가른 것이다. 「설계 기준」과 「벤치마크」가 둘 다
「무엇을 재나」였던 적이 있다 — 재기로 정한 것과 재 본 결과는 다른 층이다.

### 2-2 빠졌나

수식으로 가르면 이게 자동으로 걸린다. 합이 안 맞거나 곱이 안 맞으면 항이 빠진 것이다.
수식이 안 되는 자리에서는 **반대편을 물어 본다** — 잰 것을 세웠으면 못 잰 것도 있나.

### 2-3 층위가 같나

한 층에 성격이 다른 것이 섞이면 안 가른 것이다.

```
✕  목표 · 메모리 배치 · 스케일업 도메인 · 칩 분업 · 벤치마크 · 개발 주기
    목표(노림) · 구조 셋 · 성과 · 공정이 같은 들여쓰기로 섰다
✓  목표 → 시도 → 성과 → 한계
    시도 아래에 설계(칩 안·칩 사이)와 기간을 둔다
```

## 3. 깊이

### 3-1 레벨 1 까지만 하는 것은 아무것도 아니다

마디 이름만 늘어놓으면 분류지 분석이 아니다. **한 층 더 판 자리에서 비로소 뜻이 나온다.**

```
레벨 1 만    메모리 배치 · 칩 분업 · 스케일업
아래까지     설계 ─ 칩 안 ─ 메모리   어떻게 붙였나
                          연산     어떻게 한 칩에 몰았나
                  칩 사이 ─ 연결    몇 개가 한 덩어리로 도나
```

### 3-2 층마다 다른 법을 쓴다

한 글 안에서 층마다 다른 기준으로 갈라도 된다. 오히려 그게 맞다.

```
레벨 1   프로세스   목표 → 시도 → 성과 → 한계
레벨 2   부분 나눔   시도 = 설계 + 기간
레벨 3   층위        설계 = 칩 안 + 칩 사이
레벨 4   부분 나눔   칩 안 = 메모리 + 연산
```

### 3-3 멈추는 자리

```
계속 판다   잎에 아직 여럿이 들어 있으면 한 층 더 판다
            「코드 컴파일 · 웹 검색 · SEC 조회」는 셋이지 하나가 아니다
멈춘다      더 쪼개도 뜻이 안 늘면 거기가 잎이다. 원문이 이름만 준 목록이 그렇다
되돌린다    한 묶음이 값 하나만 갖게 되면 너무 판 것이다. 위 층에 붙인다
```

## 4. 여러 뷰

### 4-1 같은 것을 여러 구조로 쪼갠다

쪼개는 법마다 **보이는 것이 다르다.** 하나가 옳고 나머지가 틀린 게 아니다.

할라페뇨 한 편을 넷으로 갈라 보면 이렇다.

| 뷰 | 쪼개는 법 | 갈래 | 이 뷰라야 보이는 것 |
|---|---|---|---|
| 만든 순서 | 프로세스 | 목표 → 시도 → 성과 → 한계 | 잣대를 먼저 정하고 칩을 그다음에 지었다는 순서 |
| 자리 | 층위 | 칩 안 / 칩 사이 / 랙 | 같은 문제(대역폭)가 층마다 다른 해법을 부른다 |
| 값의 셈 | 수식 | 처리량 = 대역폭 ÷ 모델 크기 | 이론값과 실제가 왜 벌어지나 |
| 누구 | 주체 | 오픈AI / 브로드컴 / 셀레스티카 | 무엇을 직접 하고 무엇을 맡겼나 |

한 글에 뷰를 여럿 실어도 된다. 다만 **한 목차 안에서 뷰를 섞지는 않는다** — 섞으면 층위가
어긋난다. 주 뷰로 목차를 세우고 다른 뷰는 절 안에서 쓴다.

### 4-2 베스트 뷰 고르기

전략 컨설팅 케이스에서 컷을 고르는 것과 같다. 셋을 본다.

```
임팩트     그 쪼갬이 답을 바꾸나. 부분마다 값이 크게 다르면 쪼갤 값이 있고,
           부분마다 비슷하면 쪼개도 아무것도 안 나온다
쪼갬의 뜻   나눈 부분이 서로 다른 이야기를 하나. 「국내 / 해외」로 갈랐는데 둘이 같은
           소리를 하면 그 축은 버린다
자료       그 축으로 가를 만큼 원문에 값이 있나. 없는 축으로 가르면 빈 칸이 남고,
           그 빈 칸을 메우려다 없는 값을 지어내게 된다
```

셋을 다 만족하는 축이 베스트 뷰다. 자료가 많은 쪽부터 파면 이미 판 데로 또 가고 맹점이
꼴찌로 간다 — **임팩트가 먼저고 자료는 마지막 관문**이다.

## 5. 적용

### 5-1 원문 분석 — 주제 뽑기 → 구조화

두 단계다. **주제를 먼저 다 뽑고, 그다음에 가른다.** 뽑으면서 가르면 처음 눈에 띈 축으로
글이 굳고, 나중에 나온 주제가 그 축에 안 들어가면 통째로 떨어진다.

```
1  주제 뽑기   원문에 든 것을 빠짐없이 늘어놓는다. 이때는 안 가른다
2  구조화      뽑은 주제를 여러 뷰로 갈라 보고(4-1) 베스트 뷰를 고른다(4-2)
```

주제 뽑기는 위임한다. 원문은 만 자를 넘는 전사본이라 직접 읽으면 원문 문장이 머리에 남아
요약을 다시 요약하게 된다. **뽑는 일은 위임하고 가르는 일만 직접 한다.**

받는 꼴은 한 줄에 항목 하나다. 요약하지 말고 옮기라고 못박는다.

```
L<줄번호> | <주체> | <무엇> | <값 그대로> | <성격>
```

- 줄번호는 실제 줄. 나중에 인용할 때 원문을 다시 안 연다
- 주체는 회사·기관 이름. 진행자 이름을 주체에 쓰지 않는다
- 값은 원문 표기 그대로. 환산도 반올림도 하지 않는다
- 성격은 여덟뿐 — 사실 · 계획 · 전망 · 추정 · 가정 · 발언 · 제안 · 개념

소제목 목록 · 저자 논지 · **원문이 안 밝힌 것** 셋을 함께 받는다. 셋째가 한계 절이 된다.

받은 줄은 재료지 글이 아니다. 여기서 2단계로 넘어간다.

구조화는 **뷰를 여럿 세워 놓고 고르는 일**이다. 하나만 세워 놓고 그걸로 가면 그게 최선인지
알 수 없다. 뷰마다 어떤 주제가 담기는지를 표로 두고, 담기지 않는 주제가 무엇인지도 함께
본다 — 어느 뷰에도 안 담기는 주제가 있으면 뷰가 모자란 것이다.

```
뷰       쪼개는 법   레벨 1                담기는 주제   이 뷰라야 보이는 것
만든 순서  프로세스    잣대 → 설계 → 제작 → 측정   전부         잣대를 먼저 정했다
값의 셈    수식        실제 = 이론 − 손실      메모리·연산    대역폭을 깔고도 왜 못 쓰나
자리      층위        칩 안 → 칩 사이 → 랙     메모리~연결    같은 병목이 층마다 다른 해법
누구      주체        직접 / 맡김 / 안 한 곳   사람·파트너    무엇을 맡겼나
확실성    대비        발표 / 추정 / 안 나온 것  한계          무엇을 믿을 수 있나
```

임팩트가 작은 뷰는 목차로 세우지 않고 절 안에서 쓴다. 확실성 뷰는 한계 절이 되고, 주체
뷰는 절 안 한 문단이 된다.

### 5-2 보고서 작성

목차가 곧 쪼갠 결과다. 마디를 미리 정해 두지 않는다.

```python
('toc', ('글이 굴러가는 차례', [ … ]))   # 프로세스로 갈랐을 때. 사슬이 걸린다
('toc', [ … ])                        # 대상의 부분으로 갈랐을 때. 마디는 본문의 말
```

- 절 제목은 **물음 하나**. 「무엇으로 쟀고 무엇이 안 재졌나」는 절이 둘이다
- 절이 셋을 넘는 마디에는 축을 판다. 축 이름을 괄호로 앞세운다 — (메모리)·(연산)
- 나열은 ①②③. 「셋 남는다」로 열었으면 번호도 셋이다
- 값에 이름을 붙인다. 「합치면 초당 약 1페타바이트다」는 무엇이 그만큼인지가 없다
- 지어낸 말을 쓰지 않는다. 「겹이 둘이다」의 겹이 어디에도 안 적혀 있었다
- 마지막 절은 한계

도해도 쪼갠 것을 그린다. 원문에 없는 값을 그리지 않고(막대 길이도 아이콘 개수도 값이다),
판 위 글자는 그 자체로 읽혀야 하며(「600Gb」는 줄임말이다), 한 문장을 세 줄로 자르지
않는다.

### 5-3 검사

`CLAUDE.md` 의 검사기를 전부 돌린다. 쪼개기에 직접 걸리는 것은 `check_struct` 다 —
마디가 본문의 말인가(S3), 차례로 갈랐다면 차례를 이루는가(S9), 절이 셋을 넘는데 축이
있는가(S11), 나열을 열고 번호를 달았는가(S12).

**규칙을 새로 세웠으면 결함을 넣어 무는지 확인한다.** S12 는 처음에 「번호가 하나라도
있으면 통과」였고, 확인을 안 했으면 ① 만 남은 문단이 그대로 나갔다. S3 도 목차 상자를 자기
본문으로 세고 있어서 본문에 없는 마디를 통과시켰다 — 「물총새」를 넣어 보고 알았다.

## 이 문서가 밝히지 않은 것

- 카드 여러 장을 한 물음으로 꿰는 일은 여기 없다. 그건 `insight-report` 다
- 뉴스 묶음·TIL 묶음처럼 원문 하나에 주제가 여럿인 갈래를 어떻게 가르는지는 아직 안
  세웠다. 한 편짜리부터 굳히고 정한다
