# 원자·뷰 기반 인사이트 추출 — 설계

작성일: 2026-07-30

## 문제

지금 인사이트는 문서 65편을 주제 클러스터 9개로 묶고, 클러스터마다 5블록 산문을 쓰는 구조다. 여기서 나온 실패가 셋이다.

1. **요약의 요약.** 65편 → 9덩이 → 105문장. 13:1로 줄이는데 무엇이 살아남을지 규칙이 없어 숫자가 먼저 떨어진다. 추상 문장은 개별 소스로 반박당하지 않아 "안전"하고, 구체 문장은 틀릴 위험이 있어 깎인다.
2. **중간층 상속.** 대장(548행)이나 `facts.py` 색인(1,424행)에서 뽑으면 그 층의 추상화를 그대로 물려받는다. 코퍼스 본문에서 단위 붙은 수치가 있는 줄은 4,213줄이고, 색인은 그중 34%다.
3. **조건 소실.** 2026-07-30 실측 사례 — `[260723]` 문서는 요약(46행)에서 "GB200 대비 메가와트당 5.4배"라 쓰고, 본문 §6(256·258행)에서는 그 5.4배가 GB300 대비이며 GB200은 그 측정 구간(초당 300토큰)에 도달조차 못 한다고 쓴다. 배수를 인용하면서 측정 조건과 비교군을 떼면 사실이 뒤집힌다.

## 목표

문서 원문에서 **조건이 붙은 최소 단위(원자)** 를 뽑고, 원자를 **여러 뷰의 좌표**에 매달아, 같은 칸에 모인 원자들에서 인사이트를 쓴다. 조건 필드가 붙어 있으므로 비교 가능 여부를 기계가 판정한다.

**비목표(YAGNI)**
- 대장(`대장/*.md`)을 근거로 쓰지 않는다. 코퍼스 본문만.
- 자동 클러스터링·커뮤니티 요약(GraphRAG류)을 도입하지 않는다. 코퍼스 수준 요약으로 되돌아가는 길이다.
- 기존 9개 클러스터와 두 아티팩트(통합 인사이트·인사이트 지도)는 건드리지 않는다. 이 설계는 그 옆에 새로 만든다.
- 런타임 LLM 호출 없음. 산출물은 정적 파일.

## 원자

문서 원문의 한 지점에서 뽑은, 조건이 붙은 사실 하나.

**저장**: `insights/atoms/<YYMMDD>-<짧은슬러그>.json` — 문서 하나당 파일 하나, 원자 배열. `source_id`는 파일 안의 필드로 둔다(소스 id에 `:`가 들어가 파일명으로 못 쓴다).

```json
{
  "id": "A-260723-07",
  "source_id": "semi:compute:베라-루빈-NVL72-vs-GB200-NVL72-추론-TCO아키텍처-분석",
  "line": 258,
  "claim": "초당 300토큰을 유지하는 구간에서 GB200·GB300은 서빙 자체가 불가능하고 루빈만 곡선이 이어진다",
  "value": "96,446 tok/s/MW",
  "condition": "DeepSeek R1 · 300 tok/s/user · 엔지니어링 샘플",
  "attributed_to": "CoreWeave 측정",
  "view": { "stack": "랙", "actor": ["엔비디아", "CoreWeave"], "time": "2026-07-23" }
}
```

| 필드 | 규칙 |
|---|---|
| `id` | `A-<YYMMDD>-<일련>`. 문서 발행일 + 문서 내 순번 |
| `source_id` | `insights/manifest.json`의 소스 id와 일치 |
| `line` | 원문 파일의 1-based 줄 번호. 표·mermaid 안의 줄도 대상 |
| `claim` | 한 문장. 원문의 주장을 옮기되 요약하지 않는다 |
| `value` | 단위 붙은 수치. 없으면 `null` (수치 없는 구조적 주장도 원자가 된다) |
| `condition` | 측정 조건·비교군·전제. **비어 있으면 안 된다**. 원문에 조건이 없으면 `"조건 명시 없음"`이라고 적는다 |
| `attributed_to` | 누가 말한 값인가 (저자 분석 / 업체 발표 / 제3자 측정) |
| `view.stack` | 아래 스택 노드 중 하나 |
| `view.actor` | 아래 주체 사전의 이름 배열. 없으면 빈 배열 |
| `view.time` | 문서 발행일. manifest에서 자동 |

원자는 **원문에서만** 뽑는다. `facts.py` 색인이나 클러스터 산문에서 옮기지 않는다.

## 뷰

### 스택 뷰 (고정 8노드)

물리적 의존 순서. 위가 상류.

```
전자·공정   →  칩  →  메모리
                  ↘   열
                  ↘   랙  →  데이터센터  →  전력망  →  연료·지정학
```

| 노드 | 담는 것 |
|---|---|
| 전자·공정 | 노드 세대, 가동률, 수율, CFET 등 트랜지스터 층 |
| 칩 | 다이 구성, 패키징(CoWoS·EMIB), 본딩, 연산 성능 |
| 메모리 | HBM·DRAM·NAND, 대역폭, 캐파 배분 |
| 열 | 열저항, 냉각판, TIM, 마이크로플루이딕, 칠러 |
| 랙 | 랙 전력 밀도, 배전(800VDC), 스케일업 링크, 랙 단위 TCO |
| 데이터센터 | 부지, 건설 일정, 시설 전력·용수, 인허가 |
| 전력망 | 예비율, 접속 대기, 변압기·송전, 발전원 |
| 연료·지정학 | LNG·원유, 해협·항로, 수출 통제 |

노드가 애매하면 **더 하류**를 고른다(열 vs 랙이면 열).

### 주체 뷰

`insights/views/actors.json`에 정규화 이름 사전을 둔다. 별칭을 정식 이름으로 접는다.

```json
{ "TSMC": ["TSMC", "티에스엠씨", "대만적체전로"],
  "엔비디아": ["엔비디아", "Nvidia", "NVIDIA"] }
```

사전에 없는 이름이 원자에 나오면 검사기가 경고하고 사전 추가를 요구한다. 임의 추가는 막지 않되 조용히 늘어나지 않게 한다.

### 프로세스 뷰 (고정 7단계)

스택 뷰는 물리 의존이라 정적이다 — 열이 랙의 상류라는 사실만 말하고 "그래서 무엇이 밀리나"는 말하지 못한다. 프로세스 뷰는 같은 층 이름을 쓰더라도 다른 축을 본다: **어느 결정이 어느 결정보다 먼저 고정되나.**

`insights/views/process.json`에 단계 사전(순서 배열)과 원자별 배정을 둔다.

```
웨이퍼 배정 → 칩·랙 설계 확정 → 부지·전력 계약 → 냉각 방식 확정 → 건물 착공 → 랙 발주·인수 → 가동
```

**배정을 원자 파일에 넣지 않는 이유**: 원자는 원문 환원 대상(줄 번호·수치로 감사된다)이고, 단계 배정은 해석이다. 섞으면 감사 경계가 흐려진다. 배정이 바뀌어도 원자는 불변이어야 한다.

**기간은 다루지 않는다.** 원자에 리드타임 수치가 없다. 순서만 말하고, "몇 달 밀린다"는 말하지 않는다.

**원자끼리 직접 잇지 않는다.** 원자 84개면 짝이 3,486개이고 65편을 다 원자화하면 12만 짝이 된다. 어느 짝을 볼 가치가 있는지 판단할 규칙이 없으므로, 짝 검사는 뷰가 좁혀 준 범위 안에서만 한다(C9가 이미 그 형태다). 엣지는 원자 사이가 아니라 **단계 사이**에 있고 개수는 원자 수와 무관하다.

**프로세스 뷰 인사이트**: `view: process`, `stages: [...]`(사전 순서를 역행 금지), 인용 원자는 최소 2단계에 걸쳐야 한다. 한 단계에 머물면 스택 뷰와 다를 게 없다. 스택 뷰의 5개 절에 하나가 더 붙는다.

```markdown
## 되돌릴 수 없는 지점
- 어느 단계를 지나면 앞 단계 결정을 못 고치는가. 고치려면 무엇을 버려야 하는가
```

### 시간 뷰

문서 발행일을 그대로 쓴다. 태깅 비용이 없다. 같은 주제의 원자를 발행일순으로 늘어놓는 용도다.

## 인사이트

**쓸 수 있는 조건**: 원자 **3개 이상**, **문서 2편 이상**. 노드는 하나여도 되고 **여러 개를 묶어도 되지만, 스택 의존 그래프에서 서로 이어져 있어야 한다**(아무 층이나 갖다 붙이는 것을 막는다).

```
전자·공정 — 칩 — 메모리 — 랙
              └ 열 — 랙 — 데이터센터 — 전력망 — 연료·지정학
```

**저장**: `insights/synth/<view>-<노드들>-<번호>.md`

```markdown
---
view: stack
node: 열
atoms: [A-260702-11, A-260702-14, A-250214-03, A-250214-09]
as_of: 2026-07-02
---

## 주장
(한 문장. 굵게. 수치가 아니라 판단이 주어)

## 근거
- 원자를 인용하며 무엇이 어떻게 맞물리는지. 각 항목 끝에 원자 id

## 조건 충돌
- 비교가 성립하지 않는 지점. 없으면 "없음"

## 그래서 무엇이 달라지나
- 이 판단을 받아들이면 무엇을 다르게 보게 되는가

## 아직 모르는 것
- 원문이 공개하지 않은 것 + 언제·무엇이 나오면 풀리는가
```

**절의 무게 (2026-07-30 추가)**: 이 글의 값은 `## 그래서 무엇이 달라지나`에 있다. 사용자 지적 — "그래서 뭐가 달라지나 자체가 인사이트 아니야?" 맞다. `## 주장`은 세계가 어떻게 되어 있는지(구조)를 한 문장으로 말하고, `## 그래서`는 그 구조를 받아들이면 무엇을 다르게 보는지(관측·행동)를 말한다. 층이 달라 둘 다 필요하지만 **읽는 순서는 주장 → 그래서**이고, 근거·조건 충돌은 그 판단을 받치는 장치이므로 뒤로 간다. 산출물 페이지(`gen_atomview.py`)가 이 순서로 렌더하고 「그래서」를 강조 블록으로 뺀다.

주장이 「그래서」 항목 하나를 그대로 옮겨 쓴 경우는 중복이다 — 주장에 남기고 그 항목은 다른 각도로 다시 쓰거나 지운다(실제 사례: 웨이퍼 인사이트의 "확보 발표를 증설 신호로 읽으면 안 된다"가 두 절에 같은 문장으로 있었다).

**문체**
- 현상을 먼저 쓰고 용어는 괄호로 뒤에 붙인다. `DLC는 4LPM에서 포화한다`(나쁨) → `물을 분당 4리터 넘게 흘려도 더 안 식는다 — 칩 위에 금속판을 얹는 방식(DLC)의 한계다`(좋음)
- 수치가 문장 주어가 되면 대장을 옮긴 글이 된다. 주장이 주어다
- 회사는 정체를 한 마디로: `TSMC(엔비디아 칩을 찍는 대만 파운드리)`

**2026-07-30 추가 — 용어를 없애는 게 아니라 풀어 쓴다.** 첫 인사이트에서 사용자가 "한국말 같지도 않다"고 지적했고, 그래서 용어를 전부 쉬운 말로 바꿨더니 두 번째 지적이 왔다 — **"용어를 다 풀 필요 없어. 어려우면 설명하면 되잖아. 용어가 다 없어도 문제야. 용어가 있어도 이해가 가야 한다는 거지."** 둘 다 맞다. 용어는 정확하고, 읽는 사람이 그 말을 배워야 다음 문서도 읽는다. 없앨 게 아니라 첫 등장에서 정체를 밝히는 것이다.

| 진짜 금지 | 이유 |
|---|---|
| `벤더`·`진영`·`커스텀 실리콘`처럼 대명사로 회사 가리키기 | 어느 회사인지 모르면 문장이 성립하지 않는다 → `엔비디아`, `아마존이 직접 만든 칩 Trainium3` |
| `헤지`·`익스포저`처럼 다른 분야 비유를 설명 없이 들이밀기 | 이 문서의 용어가 아니다 → `둘 다 받게 지어두기` |
| `섞으면`·`혼용`처럼 무엇을 섞는지 안 밝히기 | 목적어가 없으면 칩을 섞는 걸로 읽힌다 → `한 건물에 공랭 랙과 액체 냉각 랙을 같이 넣으면` |
| 한 문장에 `—`로 절을 세 개 이상 잇기 | 읽는 사람이 숨 쉴 곳이 없다 |

| 용어는 살린다 | 첫 등장 처리 |
|---|---|
| 공랭 · 액체 냉각 | `공랭(공기로 식히는 방식)`, `액체 냉각(칩에 물을 직접 흘려 식히는 방식)` |
| 칠러 · CDU · RDHx | `칠러(냉각수를 강제로 식히는 냉동기)`, `냉각수를 랙마다 나눠 주는 장치(CDU)` |
| TDP · SKU · 랙 전력밀도 | `발열 한도(TDP)`, `같은 세대에서 랙당 전력을 낮춘 대안 SKU`, `랙 전력밀도(랙 하나가 먹는 전력)` |
| 콜로케이션 · 네오클라우드 | `데이터센터를 지어 임대하는 회사들(콜로케이션·네오클라우드)` |
| 전환률 · 잔존 가치 · 착공 | 그대로 쓴다. 다만 `"액체 냉각 전환률"(전체 중 액체로 넘어간 비율)`처럼 처음 한 번은 푼다 |

판단 기준 하나: **이 분야를 모르는 사람이 첫 문장만 읽고 무슨 얘기인지 알 수 있는가.** 모르면 다시 쓴다 — 용어를 지우는 게 아니라 괄호를 붙여서. 원자 id 인용은 그대로 둔다(검사기가 대조한다).

## 검사기

`insights/check_atoms.py` — 원자와 인사이트를 함께 검사한다.

| # | 규칙 | 판정 |
|---|---|---|
| C1 | `source_id`가 manifest에 존재 | FAIL |
| C2 | `line`이 해당 문서의 줄 수 이내이고, 그 줄에 `value`의 **숫자 토큰**이 존재(콤마·공백 제거 후 비교, 단위 표기 차이는 무시) | FAIL (value가 null이면 줄 존재만 확인) |
| C3 | `condition`이 비어 있지 않음 | FAIL |
| C4 | `view.stack`이 8노드 중 하나 | FAIL |
| C5 | `view.actor`의 이름이 actors.json에 존재 | WARN |
| C6 | 인사이트의 `atoms`가 모두 실재하고, 전부 그 `node`에 속함 | FAIL |
| C7 | 인사이트당 원자 ≥3, 출처 문서 ≥2 | FAIL |
| C8 | 인사이트 본문에 `## 그래서 무엇이 달라지나`·`## 아직 모르는 것`이 있고 각 1항목 이상 | FAIL |
| C9 | **비교 가능성** — 인용 원자 중 `condition`이 서로 다른 둘이 **같은 단위**(kW·%·MW·LPM·°C 등)의 수치를 쓰면 `## 조건 충돌`이 비어 있으면 안 됨 | FAIL |
| C10 | **시간 정합** — `뒤집`·`바뀌`·`이전에는` 표현이 있으면 인용 원자의 `view.time`이 둘 이상이어야 하고, 본문에 이른 날짜가 늦은 날짜보다 먼저 언급되어야 함 | WARN |
| C11 | **STALE** — 인사이트의 노드에 속한 원자 중 `atoms:`·`dismissed:` 어디에도 없고 `view.time`이 `as_of`보다 늦은 것이 있음 | WARN (목록 출력) |
| C12 | `dismissed:`의 원자가 실재하고 그 인사이트 범위 소속이며, 본문 `## 검토 후 무관` 절에 해당 id가 언급돼 있음 | FAIL |
| C13 | `process.json`의 배정이 실재 원자를 가리키고, 단계 이름이 사전에 있고 중복이 없음 | FAIL |
| C14 | 프로세스 인사이트의 `stages`가 사전에 있고 순서를 역행하지 않으며, 인용 원자가 모두 배정돼 있고 **2단계 이상**에 걸침 | FAIL |
| C15 | 프로세스 인사이트에 `## 되돌릴 수 없는 지점`이 있고 1항목 이상 | FAIL |
| C16 | 원자 파일의 `source_hash`가 manifest의 그 소스 hash와 일치 | FAIL |
| C17 | 원자의 `line_text`가 `line`행 원문과 (공백 무시) 일치 | FAIL |
| C18 | 한 인사이트가 인용하는 원자의 코퍼스(`source_id` 접두어)가 하나 | FAIL |
| C19 | 원자 `id`가 전체 원자 중 유일 — 같은 날 발행된 다른 문서가 순번을 이어 같은 id를 만들면 안 됨 | FAIL |

**C2가 잡지 못하는 것 (2026-07-30 실측)**: 원자 하나의 `claim`을 원문과 반대되는 내용으로 바꿔도 `line`·`value`가 맞으면 검사기가 통과한다. C2는 **숫자의 소재지**를 보고 주장의 진위는 보지 않는다. 기계로 진위를 판정할 방법이 없으므로 두 가지로 나눠 대응한다.

- **C16 (원문 변경 탐지)**: 줄이 밀렸는데 그 줄에 우연히 같은 숫자가 있으면 C2는 통과한다. 본문 hash를 직접 대조해 원문 변경 자체를 잡는다. 파일당 한 번.
- **C17 (원문 병치)**: 그 줄의 원문을 `line_text`로 원자 옆에 그대로 둔다. `claim`이 원문과 어긋나면 파일 하나만 열어 눈으로 확인된다 — 원문 파일을 찾아가 줄을 세지 않아도 된다. 진위 판정을 자동화하는 게 아니라 **검토 비용을 0에 가깝게 만드는 장치**다.

C9가 이 설계의 핵심 장치다. 5.4배 사고는 조건이 다른 두 원자를 조건 표기 없이 이어 붙여서 생긴다.

**스택 뷰의 `열` 노드 하나**를 끝까지 돌린다.

근거 문서 2편:

- `[250214] 데이터센터 해부학 Part 2` — DLC, 칠러, 냉각탑, 공랭 한계

절차: 두 문서에서 열 관련 원자 추출 → `insights/atoms/*.json` → 검사기 통과 → `insights/synth/stack-열.md` 작성 → 검사기 통과 → 사용자 확인.

파일럿에서 확인할 것:
- 원자 하나를 뽑는 데 드는 시간과, 문서당 원자 개수(대략 10~30개 예상)
- C9가 실제로 걸리는 사례가 나오는가
- 인사이트가 기존 클러스터 산문보다 실제로 읽을 만한가

여기서 아니면 확장하지 않는다.

### 파일럿 결과 (2026-07-30)

- 원자 **34개** / 문서 2편 (열 16 · 데이터센터 9 · 랙 8 · 칩 1). 문서당 16~18개로, 예상 범위(10~30) 안
- `조건 명시 없음`으로 채운 원자 **0개** — 두 문서 모두 측정 조건을 본문에 적고 있었다
- 검사기가 실제로 잡은 것: 서로 다른 줄의 수치를 한 원자에 섞은 사례 2건(C2). 원자를 쪼개서 해결
- 음성 테스트로 게이트 3종 확인 — 수치 조작(C2), 끊긴 노드 묶기(C6), 조건 충돌 누락(C9) 모두 FAIL 발생
- **설계 변경 2건이 파일럿에서 나왔다**
  1. 단일 노드로는 인사이트가 안 나온다. 열 노드 원자 16개가 전부 한 문서여서 C7(문서 2편)을 못 넘겼다. 값어치 있는 판단은 인접 노드의 사슬(열 → 랙 → 데이터센터)에 걸쳐 있었다 → `nodes:` 복수 허용 + 연결성 검사
  2. C9 트리거를 `N배·대비·vs` 표현에서 **단위 겹침**으로 바꿨다. 실제로 쓴 인사이트에는 비교 표현 단어가 없는데도 조건이 다른 kW 수치가 나란히 놓여 있었다

## 증분 갱신 — 새 문서가 들어올 때

이 설계를 택하는 가장 큰 이유다. 기존 클러스터 방식은 문서 1편이 추가되면 해당 클러스터 산문을 통째로 다시 써야 했다. 원자 방식은 파일 하나가 늘고, 영향받은 칸만 표시된다.

**절차**

1. 문서 변환 완료 → `gen_manifest.py`로 manifest 갱신(기존 파이프라인)
2. 새 문서에서 원자 추출 → `insights/atoms/<source_id>.json` 신규 파일. **기존 원자 파일은 수정하지 않는다** (원본 문서가 바뀌지 않았으므로)
3. 새 원자의 `view.stack` 값 집합 = 갱신 대상 칸
4. 검사기가 해당 칸의 인사이트를 STALE로 표시
5. 사람이 아래 셋 중 하나로 처리

| 새 원자가 기존 주장을 | 처리 |
|---|---|
| 뒷받침 | `atoms:` 목록에 id 추가, 근거 절에 한 줄 추가. 주장 불변 |
| 조건이 다름 | `## 조건 충돌` 갱신. C9가 강제 |
| 뒤집음 | `## 주장` 재작성. 이전 주장은 지우지 말고 `## 조건 충돌`에 "이전 판단과 그것이 무너진 이유"로 남긴다 |
| 무관 | `dismissed:`에 id 추가 + `## 검토 후 무관` 절에 왜 이 주장과 맞물리지 않는지. C12가 강제 |

네 번째 행은 실제 사례에서 나왔다. C11은 노드와 날짜만 보므로, 같은 노드라도 다루는 물리량이 다른 원자가 영구 WARN으로 남는다(`[260723]` 문서의 추론 TCO 원자 6개가 냉각 인사이트에 STALE로 걸렸다). 그냥 무시하면 WARN이 소음이 되고, 조용히 넘기면 검토했다는 기록이 사라진다. `dismissed:`는 "봤고, 이 주장과는 안 맞물린다"는 판정을 파일에 남기는 자리다. 사유 없이 id만 넣어 WARN을 끄는 것은 C12가 FAIL로 막는다.

**STALE 판정 (C11)**: 어떤 인사이트의 노드에 속한 원자 중, 그 인사이트의 `atoms:`에 없고 `view.time`이 인사이트 `as_of`보다 늦은 원자가 1개 이상이면 STALE. WARN으로 출력하고 목록을 함께 찍는다.

**원문이 수정된 경우**: 문서 본문 hash가 바뀌면 줄 번호가 밀린다. C2(줄·수치 대조)가 그 문서 원자에서 FAIL을 낸다. 해당 문서의 원자만 재추출하면 되고 다른 문서는 무관하다.

**새 도메인이 들어오는 경우**: 스택 8노드에 담기지 않는 주제라면 노드를 임의로 늘리지 않는다. 노드 추가는 기존 원자 전체의 좌표 재검토를 부르므로 스펙 개정으로 처리한다.

**문서가 자기 계층·자기 프로세스를 갖고 오는 경우 (2026-07-30 추가)**: 실제로 일어났다. `[260729] 레고 데이터센터` 문서는 본문에 자기 분류체계(부지·셸·시스템 3층)와 자기 프로세스(모듈화 사이클 5단계 — 설계·문서화·조립·운송·현장 커미셔닝)를 갖고 있었고, 원자 27개 중 25개가 `데이터센터` 노드 한 칸, 20개가 `건물 착공` 단계 한 칸으로 접혔다. 좌표가 일을 안 하는 상태다.

그렇다고 문서마다 축이나 하위 단계를 만들면 사전이 문서 수만큼 늘어난다. **좌표는 문서를 가로질러 비교하는 자리이지 한 문서의 목차를 옮기는 자리가 아니다.** 그래서 문턱을 둔다.

- **스킬은 사전을 절대 늘리지 않는다.** 기존 8노드·7단계에 배정하고, 안 맞으면 미배정으로 남긴다
- **뭉침은 `crosscheck.py`의 `find_lumps`가 알린다.** 원자 10개 이상인 칸마다 원자 수·출처 문서 수·**최다 문서 비중**을 찍는다
- **한 문서가 그 칸의 60%를 넘으면 쪼개지 않는다.** 그 구조는 아직 그 문서의 목차다. 문서 수만 세면 거의 모든 칸이 2편을 넘어 아무것도 걸러지지 않는다 — 실측: 문서 수 기준으로는 9칸 전부 "후보"였고, 독점 비중 기준으로는 5칸이 걸러졌다
- **비중이 흩어진 칸만 하위 단계 후보다.** 여러 문서가 같은 순서를 말하는지는 기계가 못 보므로 후보까지만 낸다. 승격은 사람 판단 + 스펙 개정
- **시간 순서가 없는 분류는 단계로 만들지 않는다.** 레고의 3층 구조는 순서가 아니라 분류이므로 인사이트 본문 서술로 처리한다

레고의 `건물 착공`은 지금 83%가 한 문서다 — 뭉쳐 있는 게 틀린 게 아니라 "아직 한 문서만 이 구조를 말한다"는 정확한 표시다. 두 번째 모듈러 건설 문서가 오면 그때 쪼갠다.

**비용**: 문서 1편 = 원자 10~30개(에이전트 1회). 인사이트 갱신은 영향 칸 1~3개.

## 실패 모드

- **원자가 문서 요약으로 변질된다.** 원자는 "이 줄이 말하는 것"이지 "이 절이 말하는 것"이 아니다. 완화: C2가 줄 번호와 수치 문자열을 대조한다.
- **조건 필드가 형식적으로 채워진다.** `"조건 명시 없음"`을 남발하면 C9가 무력해진다. 완화: 파일럿에서 `조건 명시 없음` 비율을 세고, 30%를 넘으면 추출 방식을 재검토한다.
- **한 노드에 원자가 몰려 인사이트가 다시 뭉뚱그려진다.** 완화: 노드당 인사이트를 1개로 강제하지 않는다. 같은 노드에서 서로 다른 주장 여러 개를 쓸 수 있다(`stack-열-1.md`, `stack-열-2.md`).
- **주체 사전이 무한정 늘어난다.** C5를 WARN으로 두되 파일럿 후 사전을 한 번 정리한다.
