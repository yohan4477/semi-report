# 원자·뷰 기반 인사이트 추출 — 설계

작성일: 2026-07-30

## 문제

지금 인사이트는 문서 65편을 주제 클러스터 9개로 묶고, 클러스터마다 5블록 산문을 쓰는 구조다. 여기서 나온 실패가 셋이다.

1. **요약의 요약.** 65편 → 9덩이 → 105문장. 13:1로 줄이는데 무엇이 살아남을지 규칙이 없어 숫자가 먼저 떨어진다. 추상 문장은 개별 소스로 반박당하지 않아 "안전"하고, 구체 문장은 틀릴 위험이 있어 깎인다.
2. **중간층 상속.** 대장(548행)이나 `facts.py` 색인(1,424행)에서 뽑으면 그 층의 추상화를 그대로 물려받는다. 코퍼스 본문에서 단위 붙은 수치가 있는 줄은 4,213줄이고, 색인은 그중 34%다.
3. **조건 소실.** 2026-07-30 실측 사례 — `[260723]` 문서는 요약(46행)에서 "GB200 대비 메가와트당 5.4배"라 쓰고, 본문 §6(256·258행)에서는 그 5.4배가 GB300 대비이며 GB200은 그 측정 구간(초당 300토큰)에 도달조차 못 한다고 쓴다. 배수를 인용하면서 측정 조건과 비교군을 떼면 사실이 뒤집힌다.

## 목표

문서 원문에서 **조건이 붙은 최소 단위(원자)** 를 뽑고, 원자를 **여러 뷰의 좌표**에 매달아, 같은 칸에 모인 원자들에서 인사이트를 쓴다. 조건 필드가 붙어 있으므로 비교 가능 여부를 기계가 판정한다.

**비목표(YAGNI)**
- 대장(`대장/*.md`)을 근거로 쓰지 않는다. 코퍼스 본문만.
- 자동 클러스터링·커뮤니티 요약(GraphRAG류)을 도입하지 않는다. 코퍼스 수준 요약으로 되돌아가는 길이다.
- 기존 9개 클러스터와 두 아티팩트(통합 인사이트·인사이트 지도)는 건드리지 않는다. 이 설계는 그 옆에 새로 만든다.
- 런타임 LLM 호출 없음. 산출물은 정적 파일.

## 원자

문서 원문의 한 지점에서 뽑은, 조건이 붙은 사실 하나.

**저장**: `insights/atoms/<source_id>.json` — 문서 하나당 파일 하나, 원자 배열.

```json
{
  "id": "A-260723-07",
  "source_id": "semi:compute:베라-루빈-NVL72-vs-GB200-NVL72-추론-TCO아키텍처-분석",
  "line": 258,
  "claim": "초당 300토큰을 유지하는 구간에서 GB200·GB300은 서빙 자체가 불가능하고 루빈만 곡선이 이어진다",
  "value": "96,446 tok/s/MW",
  "condition": "DeepSeek R1 · 300 tok/s/user · 엔지니어링 샘플",
  "attributed_to": "CoreWeave 측정",
  "view": { "stack": "랙", "actor": ["엔비디아", "CoreWeave"], "time": "2026-07-23" }
}
```

| 필드 | 규칙 |
|---|---|
| `id` | `A-<YYMMDD>-<일련>`. 문서 발행일 + 문서 내 순번 |
| `source_id` | `insights/manifest.json`의 소스 id와 일치 |
| `line` | 원문 파일의 1-based 줄 번호. 표·mermaid 안의 줄도 대상 |
| `claim` | 한 문장. 원문의 주장을 옮기되 요약하지 않는다 |
| `value` | 단위 붙은 수치. 없으면 `null` (수치 없는 구조적 주장도 원자가 된다) |
| `condition` | 측정 조건·비교군·전제. **비어 있으면 안 된다**. 원문에 조건이 없으면 `"조건 명시 없음"`이라고 적는다 |
| `attributed_to` | 누가 말한 값인가 (저자 분석 / 업체 발표 / 제3자 측정) |
| `view.stack` | 아래 스택 노드 중 하나 |
| `view.actor` | 아래 주체 사전의 이름 배열. 없으면 빈 배열 |
| `view.time` | 문서 발행일. manifest에서 자동 |

원자는 **원문에서만** 뽑는다. `facts.py` 색인이나 클러스터 산문에서 옮기지 않는다.

## 뷰

### 스택 뷰 (고정 8노드)

물리적 의존 순서. 위가 상류.

```
전자·공정   →  칩  →  메모리
                  ↘   열
                  ↘   랙  →  데이터센터  →  전력망  →  연료·지정학
```

| 노드 | 담는 것 |
|---|---|
| 전자·공정 | 노드 세대, 가동률, 수율, CFET 등 트랜지스터 층 |
| 칩 | 다이 구성, 패키징(CoWoS·EMIB), 본딩, 연산 성능 |
| 메모리 | HBM·DRAM·NAND, 대역폭, 캐파 배분 |
| 열 | 열저항, 냉각판, TIM, 마이크로플루이딕, 칠러 |
| 랙 | 랙 전력 밀도, 배전(800VDC), 스케일업 링크, 랙 단위 TCO |
| 데이터센터 | 부지, 건설 일정, 시설 전력·용수, 인허가 |
| 전력망 | 예비율, 접속 대기, 변압기·송전, 발전원 |
| 연료·지정학 | LNG·원유, 해협·항로, 수출 통제 |

노드가 애매하면 **더 하류**를 고른다(열 vs 랙이면 열).

### 주체 뷰

`insights/views/actors.json`에 정규화 이름 사전을 둔다. 별칭을 정식 이름으로 접는다.

```json
{ "TSMC": ["TSMC", "티에스엠씨", "대만적체전로"],
  "엔비디아": ["엔비디아", "Nvidia", "NVIDIA"] }
```

사전에 없는 이름이 원자에 나오면 검사기가 경고하고 사전 추가를 요구한다. 임의 추가는 막지 않되 조용히 늘어나지 않게 한다.

### 시간 뷰

문서 발행일을 그대로 쓴다. 태깅 비용이 없다. 같은 주제의 원자를 발행일순으로 늘어놓는 용도다.

## 인사이트

**쓸 수 있는 조건**: 한 뷰의 한 노드에 원자 **3개 이상**, 그 원자가 **문서 2편 이상**에서 나왔을 때.

**저장**: `insights/synth/<view>-<node>.md`

```markdown
---
view: stack
node: 열
atoms: [A-260702-11, A-260702-14, A-250214-03, A-250214-09]
as_of: 2026-07-02
---

## 주장
(한 문장. 굵게. 수치가 아니라 판단이 주어)

## 근거
- 원자를 인용하며 무엇이 어떻게 맞물리는지. 각 항목 끝에 원자 id

## 조건 충돌
- 비교가 성립하지 않는 지점. 없으면 "없음"

## 그래서 무엇이 달라지나
- 이 판단을 받아들이면 무엇을 다르게 보게 되는가

## 아직 모르는 것
- 원문이 공개하지 않은 것 + 언제·무엇이 나오면 풀리는가
```

**문체**
- 현상을 먼저 쓰고 용어는 괄호로 뒤에 붙인다. `DLC는 4LPM에서 포화한다`(나쁨) → `물을 분당 4리터 넘게 흘려도 더 안 식는다 — 칩 위에 금속판을 얹는 방식(DLC)의 한계다`(좋음)
- 수치가 문장 주어가 되면 대장을 옮긴 글이 된다. 주장이 주어다
- 회사는 정체를 한 마디로: `TSMC(엔비디아 칩을 찍는 대만 파운드리)`

## 검사기

`insights/check_atoms.py` — 원자와 인사이트를 함께 검사한다.

| # | 규칙 | 판정 |
|---|---|---|
| C1 | `source_id`가 manifest에 존재 | FAIL |
| C2 | `line`이 해당 문서의 줄 수 이내이고, 그 줄에 `value`의 **숫자 토큰**이 존재(콤마·공백 제거 후 비교, 단위 표기 차이는 무시) | FAIL (value가 null이면 줄 존재만 확인) |
| C3 | `condition`이 비어 있지 않음 | FAIL |
| C4 | `view.stack`이 8노드 중 하나 | FAIL |
| C5 | `view.actor`의 이름이 actors.json에 존재 | WARN |
| C6 | 인사이트의 `atoms`가 모두 실재하고, 전부 그 `node`에 속함 | FAIL |
| C7 | 인사이트당 원자 ≥3, 출처 문서 ≥2 | FAIL |
| C8 | 인사이트 본문에 `## 그래서 무엇이 달라지나`·`## 아직 모르는 것`이 있고 각 1항목 이상 | FAIL |
| C9 | **비교 가능성** — 인사이트가 배수·대비 표현(`N배`, `대비`, `vs`)을 쓸 때, 인용한 원자 중 둘 이상의 `condition`이 서로 다르면 `## 조건 충돌`에 그 사실이 적혀 있어야 함 | FAIL |
| C10 | **시간 정합** — `뒤집`·`바뀌`·`이전에는` 표현이 있으면 인용 원자의 `view.time`이 둘 이상이어야 하고, 본문에 이른 날짜가 늦은 날짜보다 먼저 언급되어야 함 | WARN |
| C11 | **STALE** — 인사이트의 노드에 속한 원자 중 `atoms:`에 없고 `view.time`이 `as_of`보다 늦은 것이 있음 | WARN (목록 출력) |

C9가 이 설계의 핵심 장치다. 5.4배 사고는 조건이 다른 두 원자를 조건 표기 없이 이어 붙여서 생긴다.

## 파일럿

**스택 뷰의 `열` 노드 하나**를 끝까지 돌린다.

근거 문서 2편:
- `[260702] ECTC 2026 총정리` — 마이크로플루이딕 냉각, TIM, HCB 열저항
- `[250214] 데이터센터 해부학 Part 2` — DLC, 칠러, 냉각탑, 공랭 한계

절차: 두 문서에서 열 관련 원자 추출 → `insights/atoms/*.json` → 검사기 통과 → `insights/synth/stack-열.md` 작성 → 검사기 통과 → 사용자 확인.

파일럿에서 확인할 것:
- 원자 하나를 뽑는 데 드는 시간과, 문서당 원자 개수(대략 10~30개 예상)
- C9가 실제로 걸리는 사례가 나오는가
- 인사이트가 기존 클러스터 산문보다 실제로 읽을 만한가

여기서 아니면 확장하지 않는다.

## 증분 갱신 — 새 문서가 들어올 때

이 설계를 택하는 가장 큰 이유다. 기존 클러스터 방식은 문서 1편이 추가되면 해당 클러스터 산문을 통째로 다시 써야 했다. 원자 방식은 파일 하나가 늘고, 영향받은 칸만 표시된다.

**절차**

1. 문서 변환 완료 → `gen_manifest.py`로 manifest 갱신(기존 파이프라인)
2. 새 문서에서 원자 추출 → `insights/atoms/<source_id>.json` 신규 파일. **기존 원자 파일은 수정하지 않는다** (원본 문서가 바뀌지 않았으므로)
3. 새 원자의 `view.stack` 값 집합 = 갱신 대상 칸
4. 검사기가 해당 칸의 인사이트를 STALE로 표시
5. 사람이 아래 셋 중 하나로 처리

| 새 원자가 기존 주장을 | 처리 |
|---|---|
| 뒷받침 | `atoms:` 목록에 id 추가, 근거 절에 한 줄 추가. 주장 불변 |
| 조건이 다름 | `## 조건 충돌` 갱신. C9가 강제 |
| 뒤집음 | `## 주장` 재작성. 이전 주장은 지우지 말고 `## 조건 충돌`에 "이전 판단과 그것이 무너진 이유"로 남긴다 |

**STALE 판정 (C11)**: 어떤 인사이트의 노드에 속한 원자 중, 그 인사이트의 `atoms:`에 없고 `view.time`이 인사이트 `as_of`보다 늦은 원자가 1개 이상이면 STALE. WARN으로 출력하고 목록을 함께 찍는다.

**원문이 수정된 경우**: 문서 본문 hash가 바뀌면 줄 번호가 밀린다. C2(줄·수치 대조)가 그 문서 원자에서 FAIL을 낸다. 해당 문서의 원자만 재추출하면 되고 다른 문서는 무관하다.

**새 도메인이 들어오는 경우**: 스택 8노드에 담기지 않는 주제라면 노드를 임의로 늘리지 않는다. 노드 추가는 기존 원자 전체의 좌표 재검토를 부르므로 스펙 개정으로 처리한다.

**비용**: 문서 1편 = 원자 10~30개(에이전트 1회). 인사이트 갱신은 영향 칸 1~3개.

## 확장 순서 (파일럿 통과 후)

1. 스택 뷰 나머지 7노드 — 문서 65편에서 원자 추출
2. 주체 뷰 — 좌표는 이미 원자에 붙어 있으므로 인사이트만 추가 작성
3. 시간 뷰 — 같은 방식
4. 산출물 페이지 — 뷰 전환이 되는 정적 HTML 1개. 기존 두 아티팩트는 유지

## 실패 모드

- **원자가 문서 요약으로 변질된다.** 원자는 "이 줄이 말하는 것"이지 "이 절이 말하는 것"이 아니다. 완화: C2가 줄 번호와 수치 문자열을 대조한다.
- **조건 필드가 형식적으로 채워진다.** `"조건 명시 없음"`을 남발하면 C9가 무력해진다. 완화: 파일럿에서 `조건 명시 없음` 비율을 세고, 30%를 넘으면 추출 방식을 재검토한다.
- **한 노드에 원자가 몰려 인사이트가 다시 뭉뚱그려진다.** 완화: 노드당 인사이트를 1개로 강제하지 않는다. 같은 노드에서 서로 다른 주장 여러 개를 쓸 수 있다(`stack-열-1.md`, `stack-열-2.md`).
- **주체 사전이 무한정 늘어난다.** C5를 WARN으로 두되 파일럿 후 사전을 한 번 정리한다.
