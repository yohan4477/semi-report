# 새 문서 원자화 스킬 — 설계

작성일: 2026-07-30
선행 스펙: `2026-07-30-원자-뷰-인사이트-design.md` (원자 스키마·8노드·프로세스 7단계·검사기 C1~C17)

## 문제

원자·뷰 체계는 서 있는데, **새 문서를 그 체계에 넣는 절차가 매번 손으로 재구성된다.** 2026-07-30 하루의 실측이 근거다.

1. TPUv7 문서를 원자화하려고 에이전트 프롬프트를 인라인으로 새로 썼다. 스키마·C2 규칙·완료 조건을 그 자리에서 다시 적었다 — 다음번에 같은 프롬프트가 나올 보장이 없다.
2. 원자 84개의 프로세스 단계 배정을 한 번에 손으로 했다. 새 문서가 들어올 때 어디에 무엇을 추가하는지가 파일에 안 적혀 있다.
3. `yt-dlp`가 환경 문제로 막혔던 것처럼, 파이프라인 중간의 함정이 사람 기억에만 남는다.

추출 프롬프트가 이 파이프라인의 품질 결정 변수다. 그것이 매 호출마다 달라지면 원자의 일관성이 무너지고, 검사기가 잡는 것(줄·수치·조건)만 남고 잡지 못하는 것(주장의 충실성)이 드리프트한다.

## 목표

새 문서 1편이 들어왔을 때 **원자 추출 → 좌표 배정 → 검사 → 기존 산출물과의 대조 보고**까지를 한 번의 스킬 호출로 재현 가능하게 만든다.

**비목표(YAGNI)**
- 인사이트 본문 자동 수정. STALE·충돌은 **보고만** 하고 멈춘다. 주장을 기계가 재생산하면 평범해진다.
- 새 인사이트 후보 제안.
- 프로세스 축 추가. 축이 늘어나면 무엇이 상류인지 헷갈린다 — 스펙 개정 사항.
- 기존 원자 파일 소급 수정. 원문이 안 바뀌었으면 원자도 안 바뀐다.

## 구성

| 파일 | 역할 |
|---|---|
| `.claude/skills/insight-atomize/SKILL.md` | 절차 지휘 — 순서·검사·커밋·보고. 추출은 하지 않는다 |
| `.claude/agents/insight-atomizer.md` | 추출 전담 에이전트 정의. 스키마·규칙·자체 검사 루프를 파일로 못박는다 |
| `insights/crosscheck.py` | 신설. 새 원자 대 기존 원자에서 충돌 후보 쌍을, 새 원자가 건드린 칸에서 STALE 인사이트를 뽑는다 |
| `insights/check_atoms.py` | C18 추가 (코퍼스 혼합 금지) |

스킬과 에이전트를 나누는 이유는 토큰 격리다. 문서 1편 원문(2~4만 자)과 추출 시행착오가 메인 대화에 들어오면 그 세션의 남은 작업이 오염된다. 에이전트는 파일만 남기고 요약 한 줄로 돌아온다.

## 절차 (6단계)

1. **manifest 갱신** — `python insights/gen_manifest.py`. 대상 소스의 `id`·`path`·`hash`를 확보한다. manifest에 없으면 여기서 멈추고 변환 파이프라인 쪽 문제로 보고한다.
2. **원자 추출** — `insight-atomizer` 에이전트 **1회** 호출. 산출은 `insights/atoms/<YYMMDD>-<슬러그>.json` 신규 파일 하나. 기존 원자 파일은 건드리지 않는다. 목표 원자 수 10~30개.
3. **프로세스 단계 배정** — 메인이 새 원자의 `claim`·`view.stack`을 보고 `insights/views/process.json`의 `assign`에 항목을 추가한다. 현재 축(컴퓨트 배치 순서)에 걸리지 않는 원자는 **배정하지 않고 남긴다**. 없는 연결을 억지로 만들지 않는 것이 프로세스 뷰의 값을 지키는 길이다. 배정은 원자 파일이 아니라 이 파일에만 둔다(원자는 원문 환원 대상, 배정은 해석).
4. **검사** — `python insights/check_atoms.py`가 FAIL 0이 될 때까지. 새 문서에서 가장 흔히 걸리는 것은 C2(줄에 없는 수치), C17(line_text 불일치), C5(actors.json 미등록, WARN). C16은 원문 hash 대조라 추출 시점과 현재가 다르면 즉시 FAIL이다.
5. **대조** — `python insights/crosscheck.py <원자파일>` 실행. 두 가지를 출력한다.
   - **STALE 인사이트**: 새 원자의 스택 노드/프로세스 단계를 쓰는 인사이트 중 `as_of`가 새 원자보다 이른 것. 처리 4갈래(뒷받침 / 조건 다름 / 뒤집음 / 무관)는 사람이 고른다.
   - **충돌 후보 쌍**: 새 원자와 기존 원자가 **같은 단위**의 수치를 쓰면서 `condition`이 다른 쌍. C9는 인사이트가 그 둘을 함께 인용할 때만 FAIL을 내므로, 인사이트를 쓰기 **전에** 목록을 준다.
6. **커밋·보고** — 원자 파일 + `process.json`을 한 커밋으로. 커밋 메시지에 원자 수·노드 분포·미배정 수를 적는다. 그다음 5의 리포트를 사람에게 보고하고 **멈춘다.**

## crosscheck.py — 출력 규약

인수는 원자 파일 경로(또는 소스 id). 없으면 git에서 아직 커밋되지 않은 원자 파일을 쓰고, 그것도 없으면 mtime이 가장 최근인 파일을 쓴다.

**C11과의 관계**: C11은 모든 인사이트를 훑어 `as_of` 이후 미인용 원자가 있으면 WARN을 낸다 — 상시 위생 검사다. `crosscheck.py`는 **방금 들어온 원자가 건드린 칸으로 범위를 좁혀** 무엇을 어떻게 처리해야 하는지(4갈래)까지 붙여 준다. 판정 로직은 같은 것을 보지만 용도가 다르고, 둘 다 남긴다.

출력 예시:

```
STALE 2건
  stack-열-랙-데이터센터-01.md  as_of 2026-07-23 < 신규 2026-07-25
    미인용 신규 원자: A-260725-03, A-260725-07 (노드 열)
  process-설계확정-랙인수-01.md  as_of 2026-07-23 < 신규 2026-07-25
    미인용 신규 원자: A-260725-03 (단계 냉각 방식 확정)

충돌 후보 4쌍  (같은 단위 · 다른 조건 — 함께 인용하면 C9가 FAIL)
  kW   A-260725-03 "랙당 132kW" [Max-P 구성]  ↔  A-250214-07 "공랭 41kW" [2025-02 H100 설계]
  ...
```

단위 판정은 `check_atoms.py`의 `UNIT` 정규식을 재사용한다. 판정 로직이 두 곳에 갈라지면 C9와 리포트가 어긋난다 — `crosscheck.py`는 `check_atoms`를 import한다.

## C18 — 코퍼스 혼합 금지

원자화 대상에 제3자(언더스탠딩) 문서를 포함한다. 대신 **한 인사이트가 인용하는 원자는 모두 같은 코퍼스**여야 한다(`semi:` 끼리, `und:` 끼리). 위반은 FAIL.

근거: 제3자 해설은 SemiAnalysis 계통 산출물에 섞지 않고 전용 대시보드로 분리한다는 기존 원칙이 있다. 원자 층에서 섞으면 인사이트의 근거 무게가 뒤섞이고, 어느 주장이 1차 리포트에서 나왔는지 추적이 끊긴다. 제3자 근거로 쓰는 인사이트는 별도 파일로 쓰고 별도 산출물에 붙인다.

`source_id` 접두어가 이미 코퍼스를 인코딩하므로 새 필드는 만들지 않는다.

## insight-atomizer 에이전트 — 정의 요건

프롬프트를 파일로 못박는 게 이 스펙의 핵심이므로, 정의에 반드시 들어갈 것을 명시한다.

- **읽을 것**: 선행 스펙의 "원자"·"뷰"·"검사기" 절, 기존 원자 파일 2개(형식 예시)
- **스키마**: `id` `source_id` `path` `source_hash` `line` `line_text` `claim` `value` `condition` `attributed_to` `view.{stack,actor,time}`
- **원칙**: 원자는 "이 줄이 말하는 것"이지 "이 절이 말하는 것"이 아니다. 요약하지 않는다
- **`condition` 필수**. 원문에 없으면 `"조건 명시 없음"`으로 적되, 그 비율이 30%를 넘으면 추출 방식을 재검토하도록 보고
- **비교 수치**: 요약부와 본문에서 비교군이 다른 사례가 실제로 있었다(`[260723]` 문서의 5.4배). **본문 서술을 우선**하고, 요약부만 근거로 삼지 않는다. 비교군·측정 조건을 `condition`에 반드시 적는다
- **노드 선택**: 애매하면 더 하류
- **자체 검사 루프**: `check_atoms.py`를 직접 실행해 새 파일에서 FAIL 0이 될 때까지 고친다. 다른 파일의 기존 WARN은 건드리지 않는다
- **금지**: 커밋, 다른 파일 수정, `views/process.json` 수정(배정은 메인이 한다)
- **보고**: 원자 수, 노드 분포, `조건 명시 없음` 비율, 판독 불가로 생략한 대목, 검사기 요약 줄

## 검증

스킬이 실제로 재현 가능한지는 다음으로 확인한다.

1. **미처리 문서 1편으로 전 절차 완주** — 전력망 노드가 비어 있으므로 `[260526] 800VDC 혁명 Part 1`이 첫 대상으로 적합하다. 완주 후 검사기 FAIL 0, 전력망 노드 원자 > 0
2. **crosscheck 음성 테스트** — 같은 단위·다른 조건 쌍이 실제로 잡히는지, 조건이 같은 쌍은 안 잡히는지
3. **C18 음성 테스트** — `semi:` 원자와 `und:` 원자를 함께 인용한 임시 인사이트가 FAIL을 내는지
4. **두 번째 문서로 반복** — 같은 프롬프트로 두 문서를 처리했을 때 원자 형식·조건 서술 밀도가 비슷한지. 이게 드리프트 여부를 보는 실제 지표다

### 완주 실측 (2026-07-30)

첫 완주 대상은 계획의 800VDC가 아니라 **`[260729] 레고 데이터센터의 무법지대 — 모듈러 건설 벤더 지형도와 경제성 분석`** 이었다(사용자 지정). 그래서 이 회차로는 **전력망 노드가 채워지지 않았다** — 문서가 건물·벤더 층이라 원자가 데이터센터 노드로 갔다. 전력망 0은 그대로 남아 있고 800VDC·온사이트 가스가 다음 대상이다.

- 원자 **27개** 추가 → 전체 **111개 / 문서 8편**, 검사기 FAIL 0
- 노드 분포 변화: 데이터센터 9 → **34**(+25). 이 문서 한 편이 데이터센터 노드를 세 배 이상으로 키웠다
- 단계 배정 25개 / **미배정 2개**. 미배정은 `A-260729-26`(Vertiv 백로그·인수로 생산능력 확대)·`A-260729-27`(Comfort Systems 모듈러 백로그 73% 증가) — 공급자 측 사실이고 컴퓨트 배치 결정 사슬의 단계가 아니다. 억지 배정하지 않았다
- `crosscheck.py`가 실제 신규 문서에서 동작: **STALE 5건**(기존 인사이트 5건 중 4건이 걸림), **충돌 후보 57쌍**. 환경변수 없이 실행해 종료코드 0
- **리포트 가독성이 첫 실전에서 문제로 드러났다.** STALE 항목이 인사이트마다 원자 id 27개를 한 줄로 쏟아내고, 충돌 후보 57쌍이 평평하게 나열된다. 노드·단위별 접기와 id 요약(`A-260729-01~11 외 16개`)이 필요하다 — 스킬 자체의 결함은 아니지만 다음 개선 항목이다
- **드리프트 확인은 아직 못 했다.** 두 번째 문서를 같은 경로로 처리해야 형식·조건 서술 밀도를 비교할 수 있다

## 실패 모드

- **에이전트가 원자를 절 요약으로 만든다.** 완화: C2·C17이 줄 단위 대조를 강제. 그래도 claim 진위는 못 잡으므로 보고 단계에서 `line_text`와 claim을 나란히 검토
- **충돌 후보가 너무 많아 무시된다.** 단위 겹침만으로 뽑으면 kW·%가 흔해 수십 쌍이 나올 수 있다. 완화: 같은 스택 노드 또는 같은 프로세스 단계인 쌍만 출력. 그래도 많으면 노드·단위별로 접어서 출력
- **미배정 원자가 계속 늘어난다.** 프로세스 축이 컴퓨트 배치 하나뿐이라 다른 도메인 문서는 전부 미배정이 된다. 완화: 검사기 요약의 미배정 수를 지표로 보고, 특정 도메인이 쌓이면 그때 축 추가를 스펙 개정으로 논의
- **스킬이 인사이트를 고치고 싶어진다.** 완화: 절차 6단계에서 "멈춘다"를 명시하고, 스킬 정의에 인사이트 파일 수정 금지를 박는다
