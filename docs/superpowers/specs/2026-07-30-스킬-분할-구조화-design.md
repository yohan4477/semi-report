# 스킬 분할 + 문서 구조화 — 설계

작성일: 2026-07-30
선행 스펙: `2026-07-30-원자-뷰-인사이트-design.md`(체계·검사기 C1~C19), `2026-07-30-원자화-스킬-design.md`(절차)

## 문제

세 가지가 같은 날 실측으로 드러났다.

**1. 스킬 하나가 두 주기를 섞고 있다.** `insight-atomize`가 manifest 갱신·추출·배정·검사·대조·커밋을 다 지휘한다. 그런데 앞의 넷은 **문서 1편이 들어올 때** 하는 일이고, 대조(STALE·충돌 후보·뭉침)와 좌표 승격 판단은 **문서가 쌓인 뒤** 하는 일이다. 여기에 구조 추출까지 얹으면 6단계가 8단계가 된다.

**2. 원자화 대상을 안 가렸다.** 원자 111개 중 86%가 수치를 갖고 있지만 문서별로 갈린다.

| 문서 | 원자 | 무수치 |
|---|---|---|
| `[250820]` H100 vs GB200 | 5 | 0% |
| `[251204]` Trainium3 | 11 | 0% |
| `[260702]` ECTC 2026 | 16 | 0% |
| `[260723]` 루빈 vs GB200 | 8 | 0% |
| `[260226]` 코디자인 | 13 | 8% |
| `[260729]` 레고 | 27 | 15% |
| `[250214]` 해부학 Part 2 | 18 | 17% |
| `[260313]` AI 실리콘 대란 | 13 | **54%** |

`[260313]`은 구조 추출에서도 **0개**가 나왔다. 이 문서는 "관문이 전력에서 실리콘으로 옮겨갔다"는 하나의 논증이고, 13조각으로 부수면 논증이 사라진다. 그 원자들은 "이 줄이 말하는 것"이 아니라 절의 요지를 옮긴 것에 가깝다 — 선행 스펙이 실패 모드로 적어 둔 변질이 실제로 일어났다.

**3. 라벨 기반 중복제거가 작동하지 않는다.** 문서 8편에서 구조 38개(계층 23·프로세스 15)를 뽑았는데 **중복 후보 0쌍**이다. Jaccard 문턱을 0.15까지 낮춰도 0이다. 개념적으로 인접한 구조(레고의 모듈화 사이클 5단계 vs ECTC의 EMIB-T 로드맵, 둘 다 제작 로드맵)조차 공유 라벨이 없다. 리포트마다 자기 어휘로 틀을 만들기 때문이다.

참고 지표: 원자 111개 중 **74%만** 인사이트나 무관 처리에 등장한다. 29개는 아직 아무 데도 안 쓰였다. 인사이트를 5건만 썼으므로 과잉 추출이라 단정하지 않되, 이 비율을 계속 본다.

## 목표

- 스킬을 **돌리는 주기로** 자른다 — 문서 1편용과 여러 문서용.
- 문서 유형에 따라 **원자화할지 말지**를 먼저 판정한다.
- 구조 중복제거를 **의미 기준**으로 옮긴다.

**비목표(YAGNI)**
- 플러그인 패키징. 다른 저장소 이식이 목적이 아니다 — 목적은 스킬 크기다.
- 구조 추출 전담 에이전트. 원자 추출 에이전트가 같은 문서를 이미 읽으므로 한 번에 낸다.
- 좌표(스택 8노드·프로세스 7단계) 자체의 변경. 승격은 이 스펙이 만드는 리포트를 보고 **사람이 스펙 개정으로** 한다.
- 인사이트 본문 자동 수정. 여전히 보고만 한다.

## ① 분할 — 주기로 자른다

| 스킬 | 언제 | 하는 일 |
|---|---|---|
| `insight-atomize` (기존, 축소) | 문서 1편이 변환을 끝냈을 때 | manifest 갱신 → **원자+구조 추출(에이전트 1회)** → 프로세스 단계 배정 → `check_atoms.py` FAIL 0 → 커밋. 여기서 멈춘다 |
| `insight-review` (신설) | 아래 세 조건 중 하나 | `crosscheck.py`(STALE·충돌 후보·문서 내부 충돌·뭉침) + `structures.py`(기록 검증·1차 겹침) → **구조 의미 중복제거** → 좌표 승격 후보·인사이트 갱신 대상 보고. 파일을 고치지 않는다 |

`insight-review`를 도는 시점(셋 중 하나면 돈다):
- 직전 리뷰 이후 원자화된 문서가 **3편 이상**
- `check_atoms.py`의 **STALE(C11) WARN이 1건 이상**
- **인사이트를 새로 쓰거나 고치기 직전** — 이때는 문서 수와 무관하게 돈다(충돌 후보를 모르고 쓰면 C9가 나중에 FAIL을 낸다)

경계 규칙: **`insight-atomize`는 여러 문서를 가로지르는 판단을 하지 않는다.** 대조 리포트를 읽는 것도 `insight-review`의 일이다. 반대로 `insight-review`는 원자를 만들지 않는다.

## ② 원자화 대상 판별

추출 에이전트가 문서를 훑고 **먼저 판정한다.**

- **정량 문서** — 수치와 측정 조건이 본문에 반복해서 나온다 → 원자화한다(현행 그대로).
- **논증 문서** — 하나의 주장을 여러 절로 밀고 나가며, 수치는 예시로만 나온다 → **원자를 만들지 않는다.** 대신 `structures.json`에 그 문서의 구조와 **핵심 주장 한 줄**을 기록한다.

**기계 지표**: 뽑은 원자 중 `value`가 없는 비율이 **40%를 넘으면** 추출을 중단하고 그 사실을 보고한다. 억지로 채우지 않는다. (`[260313]`이 54%였다.)

**논증 문서 기록 형식** — `structures.json`의 문서 항목에 필드 하나를 추가한다.

```json
{
  "source_id": "semi:compute:AI-실리콘-대란-TSMC-N3부터-메모리까지",
  "path": "...",
  "kind_of_doc": "argument",
  "thesis": { "line": 412, "claim": "병목이 전력에서 가속기 실리콘으로 넘어갔다", "line_text": "<그 줄 원문>" },
  "structures": []
}
```

- `kind_of_doc`은 `quantitative` 또는 `argument`. 생략하면 `quantitative`로 본다(기존 8편 호환)
- `thesis`는 `argument`일 때만. `line`·`line_text`를 붙여 원문 환원을 유지한다 — 원자와 같은 감사 기준이다
- 이미 원자화된 `[260313]`은 **소급 삭제하지 않는다.** 원자는 원문이 안 바뀌면 안 바뀐다는 원칙이 우선이고, 대신 `kind_of_doc: argument`와 `thesis`를 추가해 다음 회차부터 그 문서를 인용할 때 무엇이 본줄기인지 알 수 있게 한다. 이 경우 `"legacy_atoms": true`를 함께 넣는다 — 이 스펙 이전에 원자화된 논증 문서라는 표시이고, 아래 검증 규칙의 예외가 된다

## ③ 구조 중복제거 — 의미 기준

`structures.py`의 Jaccard 겹침은 **1차 필터로만** 남긴다(라벨이 실제로 같은 경우를 잡는다). 실측에서 0쌍이었으므로 이것만으로는 부족하다.

`insight-review`가 `insights/views/structures.json` **전수를 읽고** 같은 것을 말하는 구조를 묶는다. 이 파일은 라벨만 담아 짧으므로(구조 38개) 전수 읽기가 싸다.

**출력**: `insights/views/structure_groups.json` — 의미가 같다고 판정한 묶음.

```json
{
  "groups": [
    {
      "name": "제작·조립 로드맵",
      "kind": "process",
      "members": [
        {"source_id": "...레고...", "name": "모듈화 사이클 5단계"},
        {"source_id": "...ECTC...", "name": "EMIB-T 범프 피치 로드맵"}
      ],
      "shared_order": ["설계", "제작", "검증", "현장 반영"],
      "note": "라벨은 다르지만 공장에서 현장까지의 순서라는 점이 같다",
      "promote": false,
      "promote_note": "두 문서가 같은 순서를 말하지만 대상 층이 달라(건물 vs 패키지) 공통 단계로 올리기엔 이르다"
    }
  ]
}
```

**승격 규칙**
- 묶음의 `members`가 **2편 이상**이어야 승격 후보다(단독 구조는 그 문서의 목차다 — 선행 스펙의 60% 독점 규칙과 같은 취지)
- 승격은 `promote: true`로 표시만 하고, 실제 좌표 변경(하위 단계 추가 등)은 **사람이 스펙 개정으로** 한다
- 시간 순서가 없는 `hierarchy` 묶음은 단계로 승격하지 않는다. 분류는 서술로 쓴다

## insight-review 절차

1. `PYTHONIOENCODING=utf-8 py insights/check_atoms.py` — FAIL 0 확인(FAIL이 있으면 여기서 멈추고 원자화 쪽 문제로 보고)
2. `py insights/crosscheck.py` — STALE·충돌 후보·문서 내부 충돌·뭉침
3. `py insights/structures.py` — 기록 검증·1차 겹침
4. `structures.json` 전수를 읽고 의미 묶음을 만들어 `structure_groups.json`에 쓴다(기존 묶음은 유지하고 새 구조만 배치 — 멱등)
5. 보고: STALE 인사이트와 처리 4갈래 / 충돌 후보 중 눈에 걸리는 것 / 뭉침 중 승격 후보 / 구조 묶음 중 `members` 2편 이상인 것 / 원자 인용률
6. 커밋(`structure_groups.json`만). **인사이트 본문·원자·process.json은 고치지 않는다**

## 검증

1. `structure_groups.json` 첫 생성 — 구조 38개가 묶음 몇 개로 접히는지. 0개면 의미 묶기도 실패한 것이므로 접근을 재검토한다
2. `[260313]`에 `kind_of_doc: argument`와 `thesis`를 넣고 `structures.py`가 통과하는지
3. 논증 문서 판별을 새 문서 1편으로 실측 — 무수치 40% 문턱이 실제로 걸리거나, 안 걸리고 정량 문서로 통과하는지
4. `insight-atomize`에서 대조 단계를 뺀 뒤 스킬이 여전히 완주되는지(문서 1편 완주)

## 실패 모드

- **의미 묶기가 매번 다르게 나온다.** 같은 구조를 회차마다 다른 묶음에 넣으면 승격 판단이 흔들린다. 완화: `structure_groups.json`을 파일로 남겨 기존 묶음을 유지하고 새 구조만 배치한다(멱등). 묶음 이름을 바꾸는 것은 스펙 개정으로 본다
- **논증 문서 판별이 자기 실현적으로 쏠린다.** 에이전트가 추출이 어려운 문서를 전부 `argument`로 밀어 원자를 안 만들 수 있다. 완화: 판정 근거(무수치 비율·수치가 예시로만 쓰이는 대목)를 보고에 적게 하고, `argument` 판정이 문서 3편 중 1편을 넘으면 사람이 판정 기준을 다시 본다
- **스킬이 둘로 나뉘어 `insight-review`를 아무도 안 돈다.** 완화: `insight-atomize` 6단계 보고에 "다음: 문서가 쌓이면 `insight-review`" 한 줄을 넣고, `crosscheck`의 STALE 건수를 그 보고에 포함해 미처리가 쌓이는 것이 보이게 한다
- **`thesis`가 원자의 우회로가 된다.** 정량 문서인데 `thesis` 한 줄로 때우면 근거가 사라진다. 완화: `kind_of_doc: argument`인 문서에 원자가 있으면 `structures.py`가 **FAIL**을 낸다. 단 `legacy_atoms: true`가 붙은 문서(이 스펙 이전에 원자화된 `[260313]`)는 예외로 통과시킨다 — 소급 삭제하지 않기로 했으므로 그 하나만 열어 둔다. 새로 `argument`로 판정한 문서가 원자를 만들면 걸린다
