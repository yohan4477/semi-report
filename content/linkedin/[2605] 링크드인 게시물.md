Indium Phosphide (InP) is a III-V compound semiconductor, made from indium (group III) and phosphorus (group V). It is the substrate material that every datacenter laser chip is fabricated on. Every optical transceiver connecting GPUs in AI clusters uses InP laser dies inside.

InP is used because it is the only III-V material whose crystal lattice allows you to grow alloys that emit light at 1310nm and 1550nm, the two wavelengths where optical fiber has minimum signal loss and minimum dispersion. The material choice is dictated by physics, not preference.

The InP substrate market was built for telecom volumes over decades. Wafers are still 3-4 inch while silicon moved to 12-inch long ago. Crystal growth is slow, low-yield, and capital intensive. Floating point math is not associative! And many of the highest performance kernels split the workload among SMs and accumulate partial results in a nondeterministic order. Many AI labs just accept this, or pay a huge performance penalty for determinism. DeepSeek decided to do neither.

Common workload-balancing scheduling strategies such as splitK or split-KV give nondeterministic output bits for the same inputs. This makes debugging training failures nearly impossible -- you can't reproduce a loss spike.

For inference, some kernels can give different results depending on the sequence's position in the batch. This is because split-KV attention distributes one sequence's computation across multiple SMs to balance load, and which SMs handle which parts changes depending on what else is in the batch.

DeepSeek V4's answer: end-to-end bitwise deterministic and batch invariant kernels. They replaced all uses of cuBLAS with their own custom implementations in DeepGEMM. Instead of using atomics to accumulate partial results in split-reduction workloads, they write partials to separate buffers and use a second kernel with fixed accumulation order to ensure determinism and batch-invariance, claiming negligible performance penalty over atomic-accum variants.

So why doesn't replacing cuBLAS cost them performance? Because DeepSeek's custom kernel stack (DeepGEMM + TileLang) is actually faster. Pre-compiled cuBLAS leaves real wins on the table: build-your-own with many more tile sizes available for better SM occupancy, JIT compilation with shapes baked as compile-time constants, fast host dispatch via custom host codegen, and SMT-solver-assisted compiler optimization to generate better SASS.

The problem is that MoE with Expert Parallelism requires all-to-all communications before and after the layer to dispatch tokens to their respective experts then combine results back afterwards. Naively, these communications are separate kernel launches that don't get overlapped with computation, so the tensor cores and ALUs sit idle while waiting on network comms. Existing approaches do achieve some overlap, but sync all experts at operation boundaries.

DeepSeek takes it one step further by breaking up the workload and adding fine-grained pipelining of communication and computation within a single layer. MegaMoE breaks the experts into waves, and instead of only overlapping TMA memory loads+tensor core math+epilogue SIMT work, the kernel pipelines and overlaps NVLink communication, memory loads, and computation for each wave of experts. Synchronization between stages uses lightweight barriers rather than kernel launches. Dispatch writes a token and increments an arrival counter. All of this happens in one kernel, with fine grained pipelining over experts.
