1. 발표자는 애자일(Arize)에 최근 합류한 RL 네이버스(RL Nabors)이고, 모질라(Mozilla) 파이어폭스 개발자도구·W3C 웹표준·마이크로소프트 엣지(Edge) 브라우저·리액트(React) 팀을 거쳐 지난 3년간 AI 스타트업과 LLM·브라우저 회사들을 컨설팅해왔다고 밝힘.

2. 오늘 주제는 프런티어 모델(가장 크고 비싼 최상위 모델)을 쓸 때마다 사용자·환경·회사가 치르는 비용이고, 이를 로컬(기기 안에서 도는) 모델로 없애는 방법을 다룬다고 함.

3. 첫 번째 비용은 보안으로, 클라우드에 있는 대형 LLM에 데이터를 보내면 원격 서버 노출·가로채기·제3자 보관 위험이 늘 따라오고, 실제로 원격 챗봇 사용 때문에 민감한 업무 데이터가 저장·유출된 사례가 있었다고 함.

4. 두 번째 비용은 지연시간으로, VR(가상현실) 챗 환경에서 응답 지연을 다룬 연구를 인용해 사용자가 신뢰를 잃지 않는 한계가 4초라고 밝히고, 뒤에서 확인하겠지만 대형 모델 호출 다수가 이 4초를 넘긴다고 함.

5. 세 번째 비용은 사업 비용으로, 제3자 추론 비용은 API 요금표만으로 통제가 안 되는데, 에이전트가 여러 단계를 거치며 추론을 반복하면 토큰 단가가 내려가도 실제로 쓰는 토큰 양이 늘어 총비용이 오히려 커질 수 있다고 함.

6. 네 번째 비용은 연결성과 생산성으로, 원격 모델은 인터넷이 끊기면 아예 못 쓰고, 와이파이가 없거나 보안 때문에 네트워크가 막힌 환경에서는 서비스 전체가 멈춘다고 함.

7. 토큰 단가는 최근 떨어지고 있지만, 에이전트형 추론(여러 단계를 거치며 도구를 부르는 작업)이 토큰을 그보다 빠르게 소비하면서 전체 추론 지출은 오히려 늘고 있다고 함.

8. 이 비용 대부분을 없애는 첫걸음은 "이 일에 정말 LLM이 필요한가"를 스스로 묻는 것이라고 함.

9. 대안으로 태스크-특화 모델(한 가지 일만 하도록 만든 작고 가벼운 모델)을 제시하며, 카메라가 뭔가를 찍고 있으면 모바일넷(MobileNet)·욜로(YOLO)·미디어파이프(MediaPipe) 같은 비전 모델을, 마이크가 소리를 담고 있으면 위스퍼(Whisper)·웨이브투벡2(Wav2Vec2) 같은 오디오 모델을 쓰라고 함.

10. 채팅 번역이나 분석처럼 언어 능력이 필요한 자리에는 젬마(Gemma)나 큐원(Qwen) 같은 소형 언어모델(SLM, 파라미터 수가 적어 가볍게 도는 언어모델)을 쓰면 된다고 함.

11. SLM은 수백만에서 수십억 개 파라미터를 갖는 반면 LLM은 수십억에서 수조 개까지 가는데, 자신이 보여준 도표에서 큰 점 하나가 이미 작은 축에 드는 LLM인데도 SLM 중 큰 것을 나타내는 작은 점보다 훨씬 크다고 설명함.

12. 대부분의 사용자는 모델을 채팅 요약이나 무례한 발언 감지 같은 좁은 일에 쓰는데, 이런 일에는 역사·철학·레딧(Reddit) 잡담까지 통째로 외운 지식이 필요 없고, 놀랄 만큼 적은 파라미터로도 충분하다고 함.

13. 좋은 소식은 소형 언어모델이 대형 언어모델과 같거나 더 적은 에너지로 같은 수준의 정답률을 낸다는 연구 결과가 이미 나와 있다는 것이라고 함.

14. 소형 언어모델은 대개 8비트·4비트 양자화(모델 정밀도를 낮춰 크기를 줄이는 기법)로 배포돼 디스크·메모리 사용량이 4분의 1까지 줄고, 파라미터 10억 개짜리는 FP16(16비트 부동소수점) 기준 디스크 약 2GB면 들어간다고 함.

15. 자신이 보여준 기기별 용량 표는 상한 추정치일 뿐이라며, 어떤 모델이 어떤 기기에 들어가고 안 들어가는지 감을 잡는 용도라고 밝힘.

16. 자신의 픽셀(Pixel) 10 프로가 이미 온디바이스 SLM을 탑재해 나온다며, 온디바이스 모델을 직접 써보고 싶어서 출시되자마자 구매했다고 함.

17. 엔비디아(Nvidia)가 SLM을 "에이전트형 AI의 미래"라 불렀고, 2025년 연구 논문도 SLM이 에이전트 작업 부하를 감당할 만큼 강력하면서 에너지는 더 적게 쓴다는 결과를 냈다고 함.

18. 막대그래프로 보여주길, LLM이 어떤 일을 처리하는 데 드는 에너지를 100이라 하면 SLM은 그 25% 정도만 쓰고, 태스크-특화 모델은 SLM이 쓰는 양의 다시 절반 정도만 쓴다고 함.

19. 로컬 모델의 이점을 더 안전함·오프라인 작동·요금 없음·더 효율적·기기 안에서 도니 왕복 없이 지연시간이 짧다는 다섯 가지로 정리함.

20. 자신이 로컬 AI를 써온 경험을 소개하며, 한쪽엔 클로드(Claude)를, 다른 쪽엔 오픈 에이전트 하네스(harness, 모델을 감싸 실행하는 틀)인 구스(Goose)로 젬마(Gemma)를 돌리는 화면을 나란히 보여줌.

21. 자신이 즐겨 던지는 질문은 어룡(공룡 시대 바다 파충류)이 골격이 돌고래를 닮았으니 반향위치(소리로 위치를 찾는 능력)를 가졌을 가능성이 얼마나 되냐는 것으로, 생물학적 추론이 필요한 문제라고 함.

22. 젬마 3가 화석 기록에 돌고래 특유의 멜론(음파를 모으는 지방 기관)이나 반향위치용 특수 뼈 구조가 남아 있지 않다는 근거로 좋은 답을 내놓아 놀랐다고 함.

23. 반면 클로드는 이 질문에 세 번에 한 번꼴로 "알 수 없다"며 답을 피했는데, 클로드가 원래 의견을 내는 데 조심스러운 편이라고 평가함.

24. 그렇다면 어떤 모델을 고를지가 진짜 어려운 문제라며, 구글(Google)과 함께 만든 자신만의 틀을 web.dev에 공개했다고 소개함.

25. 핵심 원칙은 "크게 시제품 만들고 작게 배포하라"로, 프로토타입 단계에서는 파운데이션 모델을 마음껏 써도 되지만 프로덕션에서는 시스템 일부를 SLM과 특화 모델로 바꾸라는 뜻이라고 함.

26. 첫 단계는 하려는 일이 애초에 가능한지 확인하는 것으로, 가장 크고 강력한 모델(제미나이 같은 파운데이션 모델이든, 손글씨 인식처럼 아주 어려운 태스크-특화 모델이든)로 일단 되는지부터 본다고 함.

27. 이 과정을 자신이 취미로 만드는 소셜 네트워크 클라이언트 앱 미마(Mima)의 기능 하나로 시연하는데, 밤새 올라온 댓글 50개를 아침에 한눈에 훑게 해주는 긴 대화 스레드 요약 기능이라고 함.

28. 먼저 클로드로 프로토타입을 만들어 이 기능이 통한다는 걸 확인했고, 스레드 속 누가 무슨 말을 하는지 요약이 꽤 잘 나왔다고 함.

29. 다음 단계로 입력·출력 쌍을 모은 골든 데이터셋(사람이 검수해 정답으로 삼는 고품질 데이터 모음)을 만들었는데, 스레드 14개를 골라 각각 짧은 요약과 참조 링크가 붙은 요약 두 가지 결과로 뽑아 총 28개 예시를 확보했다고 함.

30. 무엇을 성공으로 볼지도 미리 정해야 한다며, JSON 형식으로 나온 출력이 파싱되는지, 요약 안에 걸린 참조가 실제 대화 속 위치를 정확히 가리키는지, 내용이 사실과 어긋나지 않는지(예를 들어 고양이 얘기를 강아지 얘기라고 하지 않는지), 글자 수 제한을 지키는지, 응답까지 걸리는 시간(P50 중앙값·P95 최악값)을 지표로 삼았다고 함.

31. 사실 일치 여부처럼 사람이 일일이 보기 힘든 항목은 LLM 심판(LLM을 평가자로 쓰는 방식)에게 맡기는 게 사람보다 싸다고 함.

32. 측정 도구로는 애자일(Arize)이 만든 오픈소스 프로젝트 피닉스(Phoenix)를 골랐다고 밝힘.

33. 먼저 캐퍼빌리티 평가(capability eval, 이 에이전트가 무엇을 잘하는지 보는 평가)로 대형 모델과 소형 모델 여러 개의 성능을 나란히 비교했다고 함.

34. 기준선으로 쓴 클로드 소네트(Claude Sonnet)는 평균 지연 2.9초, 스레드 14개를 처리하는 데 0.22달러가 들어, 계산해보니 미마를 매일 쓰면 하루 약 1달러꼴이 나온다고 함.

35. 자신은 그 정도 비용을 매일 감당할 여력이 없다며, 그래서 이 작업을 기기 위에서 돌리기로 했다고 함.

36. 로컬 소형 모델은 총비용 항목이 전부 0인데, 추론 부담이 소비자 기기로 넘어가 배터리를 충전하는 전기값만 든다고 함.

37. 겨룰 후보로 큐원(Qwen) 2.5 인스트럭트 15억 파라미터(디스크 1GB), 큐원 3 17억 파라미터, 라마(Llama) 3.2 30억 파라미터(디스크 2GB), 젬마(Gemma) 4 E2B 50억 파라미터(디스크 3.1GB) 넷을 골랐다고 함.

38. 모델을 고를 때 만난 엔지니어 여러 명이 "젬마 4가 최고"라고 입을 모았는데, 그 말만 믿고 골랐다면 사용자에게 전혀 다른(더 나쁜) 경험을 줬을 거라며, 이래서 직접 재봐야 한다고 함.

39. 원하는 건 쓸 만한 답을 내는 가장 작은 모델이라며, 이를 SAGE 모델(small and good enough model, 작고 충분히 좋은 모델)이라 부르자고 제안함.

40. 처음엔 큐원 2.5가 P50 지연 약 1초로 가장 빨라 끌렸지만, 정확도가 다른 모델들보다 눈에 띄게 낮았다고 함.

41. 젬마 4 E2B는 소형 모델 중 가장 정확했지만 지연이 약 8초로 느렸고, 다른 프롬프트가 필요했을 수도 있지만 이 결과가 꽤 일관됐다고 함.

42. 정확도까지 따졌을 때 실제 승자는 라마 3.2로, 정확도 약 90%를 내면서 클로드 소네트나 다른 빠른 모델들과 비슷한 속도를 냈다고 함.

43. 실험 결과를 직접 열어보니 여러 경우에서 라마의 응답이 클로드의 응답과 거의 구별이 안 될 만큼 가까웠다고 함.

44. 라마 3.2를 만든 메타(Meta)가 사람이 쓴 글을 소셜 네트워크에서 잘 요약하는 모델을 만드는 데 강한 이해관계가 있으니, 소셜 앱에 라마가 잘 맞는 것도 납득이 간다고 함.

45. 모델 크기를 알맞게 고르는 절차를 네 단계로 정리하는데, 첫째 가장 큰 모델로 일이 애초에 가능한지 증명하고, 둘째 입력·출력 쌍을 모아 기준(바(bar))을 세우고, 셋째 작은 모델부터 큰 모델 순서로 그 기준과 비교하고, 넷째 그 기준을 만족하는 가장 작은 모델, 즉 SAGE 모델을 고른다고 함.

46. 그런데 정확도 90%는 여전히 부족할 수 있는 격차라며, 이 격차를 프롬프트 엔지니어링(입력 문장을 다듬어 모델 성능을 끌어올리는 기법)으로 좁힐 수 있다고 함.

47. 이 방법이 특히 중요한 경우는 어떤 모델을 쓸지 개발자가 통제할 수 없을 때로, 이미 팀이 젬마 3에 맞춰 배포를 끝냈거나, 모바일 앱이라 기능 하나 늘 때마다 1~2GB짜리 새 모델을 사용자 데이터 요금까지 써가며 다시 내려받게 할 수 없는 상황을 예로 듦.

48. 대안으로 특정 작업 하나만 잘하도록 다시 학습시킨 증류(distillation) 모델을 만드는 방법도 있지만, 기능을 추가할 때마다 모델을 다시 학습시키고 새로 배포해야 하는 부담이 있다고 함.

49. 격차를 좁히려고 지표를 다시 살펴보니 구조 유효성, 사실 일관성, P50·P95 지연에서 차이가 두드러졌고, 응답이 4초를 넘기면 연결이 끊긴 느낌을 준다는 앞선 연구를 근거로 P50 기준을 1.5초, P95 기준을 3.5초로 잡았다고 함.

50. 프롬프트를 바꿀 때는 한 번에 변수 하나씩만 바꿔 무엇이 효과가 있는지 가려내야 한다며, 원래 프롬프트를 기준선으로 두고 변형 네 가지를 만들었다고 함.

51. 첫 변형은 대화를 JSON 대신 번호 매긴 메시지로 바꿔 넣은 것으로, 작은 모델이 배열 인덱스보다 자연어로 된 번호를 더 잘 따라간다는 가설이었다고 함.

52. 둘째 변형은 예시 몇 개와 그 결과를 프롬프트에 덧붙인 퓨샷(few-shot)으로, 작은 모델은 규칙보다 예시를 보고 형식을 더 빨리 배운다는 가설이었다고 함.

53. 셋째 변형은 하지 말아야 할 것을 못 박은 엄격한 규칙 버전으로, 작은 모델이 문자 그대로의 명령에 더 잘 따른다는 가설이었다고 함.

54. 넷째 변형은 답을 쓰기 전에 핵심 순간부터 짚게 한 사고 사슬(chain of thought)로, 소리 내어 생각하게 하면 근거가 더 탄탄해질 거라는 가설이었다고 함.

55. 라마 3.2로 다시 돌린 결과, 기준선 프롬프트는 요약 길이를 잘 못 맞췄고 구조 정확도 91.2%, 사실 정확도 87.1%, 지연 1초를 냈다고 함.

56. 번호 매긴 입력 변형은 별 차이를 못 냈고, 엄격한 규칙 변형은 오히려 결과를 더 나쁘게 만들었는데, 모델이 하지 말라는 명령에 부정적으로 반응했다고 함.

57. 사고 사슬 변형은 길이는 조금 나아졌지만 지연이 600밀리초 늘었고, 가장 좋았던 것은 퓨샷 변형으로 길이도 더 잘 맞고 정확도도 더 높고 클로드와 참조 내용도 더 잘 맞으면서 지연은 200밀리초만 늘었다고 함.

58. 퓨샷 프롬프트를 적용한 라마 3.2는 P50 지연이 1.5초 아래로, 구조 유효성 91.7%, 사실 일관성 92.9%, P95 지연은 750밀리초를 크게 밑돌아 클로드보다도 낮은 수준까지 왔다고 함.

59. 남은 구조 유효성·사실 일관성 격차 10%를 열어보니, 심판 역할을 한 클로드 오퍼스(Claude Opus)가 지나치게 엄격했다는 게 드러났는데, 클로드 소네트와 라마를 비교하면서 자기 계열 모델(소네트)을 편들어 "앵스티(angsty)"와 "크로스(cross)"처럼 뜻이 같은 표현 차이까지 오답으로 깎았다고 함.

60. 참조 개수·길이 같은 항목은 모델 자체보다 하네스(harness) 안 후처리로 잡을 수 있다며, 스레드 길이보다 참조가 많으면 걸러내고 요약이 너무 길면 그냥 잘라내는 식으로 처리했다고 함.

61. 후처리까지 더하니 JSON 유효성 100%, 구조 유효성 100%, 사실 일관성은 심판이 너무 엄격했던 부분만 빼면 사실상 일치, P50 지연은 약 1초, P95 지연은 3.5초 아래로 떨어져 클로드를 만나거나 앞섰고, 하루 약 1달러이던 추론 비용을 아꼈다고 함.

62. 이렇게 최적화한 뒤에도 프롬프트를 손보거나 모델을 올릴 일이 생기므로, CI/CD 테스트처럼 회귀 평가(regression eval, 바뀐 뒤에도 이전 성능을 유지하는지 계속 재는 평가)를 계속 돌려야 한다고 함.

63. 실제로 어느 창업자 친구는 CTO가 프롬프트를 살짝 바꿨다가 에이전트 경험을 통째로 망가뜨린 적이 있었다며, 회귀 평가가 이런 사고를 막아준다고 함.

64. 청중에게 "지금 클로드로 보내는 호출 중 몇 개를 라마 호출로 바꿀 수 있는가"를 오늘 집에 가서 직접 점검해보라고 던짐.

65. 크롬(Chrome)의 프롬프트 API(prompt API)가 크롬에 기본 탑재된 제미나이 나노(Gemini Nano)에 접근하는 것처럼, 이미 기기 안에 있는 SLM·특화 모델을 먼저 찾아보라고 권함.

66. 로컬 모델을 쓰면 정보가 기기를 벗어나지 않아 개인식별정보(PII) 걱정이 줄고, 에너지 소비 면에서도 환경에 이득이라고 정리함.

67. 마지막으로 "크게 시제품 만들고 작게 배포하라"는 원칙과 증명·기준 설정·테스트·SAGE 모델 선택 네 단계를 다시 짚고, 지금 쓰는 기능 하나를 골라 로컬 소형 모델로 바꿔보라는 과제를 남기며 발표를 마침.

한줄 코멘트. 모델을 키우는 대신 프롬프트와 후처리만 손봐서 격차를 메웠다는 점이 핵심이고, 그 격차의 상당 부분이 모델 성능이 아니라 심판(클로드)의 편향에서 나왔다는 사실이 더 눈여겨볼 대목임.
