---

1. 발표자는 허깅페이스(Hugging Face)에서 머신러닝 플랫폼·데이터베이스 엔지니어로 일하는 아렉 보루츠키(Arek Borucki)이고, 허브 인프라를 어떻게 키워왔는지 발표함.

2. 허깅페이스는 지금 1400만 명 넘는 사용자를 두고 있고, 이 숫자가 최근 몇 달 사이 특히 빠르게 늘고 있다고 밝힘.

3. 허브에는 공개 모델 300만 개, 데이터셋 100만 개, 조직 5만 개가 올라와 있다고 함.

4. 포춘 500대 기업 중 30% 넘게 AI 워크플로우의 일부로 허깅페이스를 쓴다고 함.

5. 몇 년 전에는 모델이 2만 개였는데 지금은 300만 개로, 몇 년 사이 약 150배 늘었다고 함.

6. 라마(llama)나 딥시크(deepseek) 같은 큰 모델이 하나 나올 때마다 그 위에 파생 모델 수천 개가 새로 생기고, 인프라는 그걸 그대로 받아내야 한다고 함.

7. 데이터셋도 2022년 1만 개에서 2024년 10만 개, 1년이 채 안 된 시점엔 50만 개, 지금은 100만 개로 늘었다고 함.

8. 이 데이터를 전부 저장·색인해 검색 가능한 상태로 두는 게 가장 어려운 부분이고, 그래서 검색 구조를 다시 짜야 했다고 함.

9. 모델이 2만 개일 때는 색인 없이도 어떤 질의든 빨랐지만, 300만 개가 되자 같은 방식이 무너졌다고 함.

10. 허브 검색이 느려지면 사용자는 그냥 떠나 다른 곳으로 가버리고, 다들 즉각적인 결과를 기대한다고 함.

11. 1400만 사용자 중 1%만 느린 검색을 겪어도 14만 명이라는 적지 않은 숫자가 된다고 함.

12. 그래서 평균 응답 시간(P50)보다 최악 구간 응답 시간(P99, 요청 100개 중 가장 느린 쪽 응답 시간)을 훨씬 더 중요하게 보고 거기에 신경 쓴다고 함.

13. 이를 위해 삽입 시점에 검색 토큰을 미리 계산해두는 것과, 읽기 전용 컬렉션을 몽고DB(MongoDB)에 따로 두는 비정규화(denormalize)에 투자한다고 함.

14. 여기에 아파치 루씬(Apache Lucene) 기반 전문 검색, 쿠버네티스(Kubernetes) 오토스케일링, 앞으로 도입할 데이터베이스 샤딩(sharding, 데이터를 여러 조각으로 나눠 저장하는 방식)까지 더한다고 함.

15. 사용자가 허브에 요청을 보내면 프런트엔드에서 허브 API로 가고, 허브는 쿠버네티스 위에서 수평 포드 오토스케일러(HPA)로 돌아간다고 함.

16. 트래픽이 튀면 새 포드가 자동으로 늘고 트래픽이 빠지면 다시 줄어들어, 사람이 손대지 않아도 허브가 건강하게 유지된다고 함.

17. 다음으로 요청은 몽고DB 아틀라스(MongoDB Atlas)로 가는데, 이게 메타데이터의 소스 오브 트루스(source of truth, 데이터가 맞는지 최종 기준이 되는 저장소)라고 함.

18. 몽고DB가 모델 파일 자체를 저장하는 게 아니라 모델에 관한 모든 정보를 저장한다는 점이 사람들을 종종 놀라게 한다고 함.

19. 사용자, 저장소, 모델, 데이터셋 버킷, 스페이스 정보, 설정값, 결제 데이터, 접근 제어까지 전부 몽고DB에 담는다고 함.

20. 실제 모델 아티팩트, 토크나이저 파일, 카드 자산, 설정 파일은 AWS S3 같은 클라우드 객체 스토리지에 따로 저장한다고 함.

21. 메타데이터와 바이너리 저장, 연산을 이렇게 관심사별로 떼어놓으면 각각을 독립적으로 확장하고 워크로드에 맞게 따로 최적화할 수 있다고 함.

22. 검색 예시로 검색창에 "llama"를 입력하면 요청이 허브를 거쳐 몽고DB의 최적화된 읽기 전용 컬렉션으로 간다고 함.

23. 이 컬렉션은 전체 데이터를 담은 메인 저장소가 아니라, 읽기·목록 조회만을 위해 따로 둔 비정규화 복사본이라고 함.

24. 모델 이름은 질의 시점이 아니라 삽입 시점에 미리 토큰화해둔다고 함.

25. 예를 들어 "meta-llama/llama-3.1-8b"를 올리면 이 긴 이름을 meta, llama, 3.1, 8b 같은 작은 토큰으로 쪼개 몽고DB 문서 안 배열에 저장해둔다고 함.

26. 이후 아파치 루씬을 쓰는 아틀라스 서치(Atlas Search)가 자동완성으로 이 토큰 배열을 뒤져 일치하는 모델을 즉시 찾아낸다고 함.

27. 실제 문서 예시를 findOne으로 조회해 검색 토큰 배열만 뽑아 보여주는데, "meta-llama/llama-3.1" 문서 안에 meta llama 3.1, meta llama 같은 토큰이 미리 담겨 있었다고 함.

28. 예전에는 몽고DB의 클래식한 find 메서드에 정규식(regex) 연산자를 써서 검색 토큰 배열 안에서 llama와 일치하는 모델을 찾았다고 함.

29. 정렬은 5분마다 계산되는 트렌딩 점수로 했는데, 이 점수는 최근 7일 다운로드 수와 좋아요 수를 기준으로 삼는다고 함.

30. 이 방식은 데이터가 적을 땐 잘 돌아갔지만 정규식은 데이터가 커지면 확장이 안 돼서, 데이터셋이 빠르게 늘자 지연 문제가 생기기 시작했다고 함.

31. 그래서 아파치 루씬을 내부에서 쓰는 아틀라스 서치로 옮겼다고 함.

32. 몽고DB 서버 자체에는 전문 검색 기능이 없어서 아파치 루씬을 감싼 별도 프로세스(몽고트, mongot)가 따로 돌고, 사용자에게는 이게 감춰져 통합된 몽고DB 쿼리 API처럼 보인다고 함.

33. 애그리게이션 파이프라인에서 $search 연산자를 쓰면 몽고DB가 이걸 아파치 루씬 색인을 검색하라는 뜻으로 알아듣는다고 함.

34. 여기서는 "model_search"라는 색인 이름과 autocomplete 필드를 지정해 검색 토큰 경로에서 llama와 일치하는 것을 찾고, 여전히 트렌딩 점수로 정렬한다고 함.

35. 이 방식이 훨씬 효율적이고 지금까지는 잘 확장되고 있어서 검색창에 더는 지연 문제가 없다고 함.

36. 예시 질의 결과 상위 두 개는 각각 트렌딩 점수 33과 14를 받은 두 개의 meta-llama 모델이었다고 함.

37. 검색 말고도 수백 개의 서로 다른 서비스가 몽고DB를 써서 수백만 건의 질의를 처리하고, 이를 위해 노드 7개짜리 몽고DB 클러스터로 여러 머신에 질의를 분산한다고 함.

38. 삽입·삭제·수정은 전부 프라이머리(primary) 노드 하나로만 가고, 읽기는 여러 세컨더리(secondary) 노드로 분산한다고 함.

39. 애플리케이션 쪽에서는 보이지 않는 애널리틱스 히든 노드도 하나 둔다고 함.

40. 이 노드는 프라이머리로부터 데이터는 계속 복제받지만 몽고DB 드라이버가 질의를 절대 보내지 않고, 리포팅이나 아주 무거운 질의는 여기로 직접 연결해 처리한다고 함.

41. 모든 세컨더리는 프라이머리의 oplog(작업 로그)를 계속 따라가며 클러스터 전체를 동기 상태로 유지한다고 함.

42. 세컨더리로 보내는 질의는 네 종류로, 첫째 최신 데이터가 꼭 필요하지 않은 질의는 세컨더리로 가고 강한 일관성이 필요한 질의만 프라이머리에 남긴다고 함.

43. 둘째, 대량 데이터를 스캔·정렬·그룹화·변환하는 무거운 애그리게이션 파이프라인도 프라이머리가 아니라 세컨더리에서 처리한다고 함.

44. 셋째, 캐시 무효화나 AWS 레드시프트(Redshift) 같은 다른 저장소로의 동기화처럼 데이터 변화에 실시간으로 반응하는 체인지 스트림(change stream)도 세컨더리 몫이라고 함.

45. 넷째, 애드혹 질의·리포팅 질의·실험용 질의는 프로덕션 트래픽과 분리된 히든 레플리카로 보낸다고 함.

46. 프라이머리는 프라이머리만 할 수 있는 일에 집중하고 나머지는 다른 머신으로 밀어내는 게 원칙이라고 함.

47. 다만 1400만 사용자, 300만 모델에 계속 늘고 있는 지금 속도로는 곧 몽고DB 레플리카 셋 하나로는 부족해져서, 다음 단계로 샤딩을 준비하고 있다고 함.

48. 레플리카 셋은 노드마다 전체 데이터를 다 갖고 있지만, 샤드 클러스터는 각 샤드가 데이터의 일부만 갖고 자기 프라이머리·세컨더리 복제 구조를 따로 갖는다는 점이 다르다고 함.

49. 샤드를 더 추가하면 몽고DB 밸런서가 알아서 데이터를 재분배해주는데, 어떤 샤드 키를 고를지는 이번 발표에서 다루지 않는다고 함.

50. 쿠버네티스 레벨에서는 CPU·메모리 임계값을 넘으면 HPA가 새 포드를 자동으로 늘리고 트래픽이 빠지면 다시 줄인다고 함.

51. 허브 배포는 트래픽에 따라 포드 10개에서 500개까지 오가며, 이게 사람 손 없이도 허브를 건강하게 유지하는 비용 효율적인 방식이라고 함.

52. HPA가 포드를 더 늘리려 해도 쿠버네티스에 여유 노드가 없을 때를 대비해, 캐스트 AI(Cast AI)로 노드 자체를 오토스케일링하는 두 번째 레이어를 둔다고 함.

53. 포드가 대기 상태로 남으면 캐스트 AI가 새 노드를 붙여 스케줄러가 그 포드를 배치할 수 있게 해준다고 함.

54. 앞으로는 HPA를 케다(KEDA, 쿠버네티스 이벤트 기반 오토스케일링)로 옮길 계획이라고 함.

55. HPA는 CPU·메모리만 보고 스케일하지만 케다는 초당 요청 수나 이벤트 루프 사용률 같은 실제 애플리케이션 지표로 스케일한다고 함.

56. CPU는 낮아도 요청 큐가 쌓인 포드를 케다는 잡아내지만 HPA는 못 잡아낸다고 함.

57. 이 아키텍처에서 가장 좋은 부분은 사용자가 이걸 전혀 신경 쓸 필요가 없다는 것이라고 함.

58. 모델을 올리거나 검색하거나 내려받을 때 그냥 되는 것, 밑에서 아무리 복잡해도 사용자 경험은 단순하게 지키는 게 스케일링의 본질이라고 밝히며 발표를 마침.

한줄 코멘트. 색인 최적화보다 프라이머리·세컨더리·히든 노드로 질의 종류별 목적지를 나눈 몽고DB 운영 원칙이 더 오래 남을 교훈임.
