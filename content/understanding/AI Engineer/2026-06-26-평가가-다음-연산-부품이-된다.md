1. Sunil Pai와 Matt Carey는 클라우드플레어(Cloudflare)에서 에이전트(사람이 시킨 일을 스스로 여러 단계로 쪼개 도구를 불러가며 처리하는 프로그램) 팀을 맡고 있음.

2. 두 사람은 1년 조금 넘는 기간 진지하게 에이전트를 만들기 시작했고 결과가 꽤 좋았다고 밝힘.

3. 출발점은 더러블 오브젝트(durable object)임 — 요청마다 새로 떴다 사라지는 보통 서버리스 함수와 달리, 특정 아이디 하나에 묶여 상태를 계속 들고 있는 단위임.

4. 예시로 든 건 방문자 수 세는 카운터임 — 보통 서버리스 함수로 짜면 요청이 끝날 때마다 인스턴스가 사라져 카운터가 항상 0으로 돌아옴.

5. 이 문제를 풀려면 원래는 별도 데이터베이스를 붙여야 하는데, 더러블 오브젝트는 같은 아이디의 모든 요청과 웹소켓 연결이 항상 같은 인스턴스로 떨어지게 해줌.

6. 그래서 이걸 "상태를 유지하는 서버리스(stateful serverless)"라고 부르는데, 서버라는 말 자체가 원래 상태를 유지한다는 뜻이라 이름이 헷갈린다고 스스로도 인정함.

7. 더러블 오브젝트는 클라우드플레어의 지구 전역 네트워크 위에서 도는데, 런던 기준 지연시간이 15ms 정도라고 밝힘.

8. 비교로 든 수치는 60fps(초당 60프레임) 화면 갱신 주기가 16ms 남짓이라는 것 — 즉 지연시간이 한 프레임 주기보다 짧다는 뜻임.

9. 이 정도 지연이면 여러 사람이 같은 화면을 실시간으로 같이 그려도 다들 완벽히 동기화된 상태로 보인다고 함 — 협업 드로잉 툴 TLDraw가 이 기술 위에서 돌아간다고 밝힘.

10. 더러블 오브젝트가 좋은 이유로 든 건 아이디로 바로 찾아갈 수 있고(addressable), 요청이 없어도 백그라운드에서 오래 돌 수 있고, 필요 없을 땐 잠들었다(hibernate) 다시 깨어나며, 상태가 그대로 남는다는 점임.

11. 이런 성질이 에이전트를 돌리기에 딱 맞는 연산 단위였다는 게 이들의 원래 베팅이었다고 함.

12. 이 위에 "agents"라는 이름의 npm 패키지를 얹어 프레임워크로 냈고, 리액트(React) 훅과 순수 자바스크립트 클라이언트를 둘 다 제공한다고 밝힘.

13. 이 프레임워크의 스케줄링 기능을 가장 좋아한다고 하며, "매주 금요일 9시에 깃(Git) 히스토리·위키·노션을 훑어 정리해 매니저에게 보내되, 내가 쓴 것처럼 보이게 철자를 좀 틀리게 하라" 같은 예를 듦.

14. 이 인프라가 수백만, 수조 단위까지("클라우드플레어스러운 터무니없는 숫자"라는 표현) 자동으로 늘어난다고 주장함.

15. 지난 1년 동안 만든 것 중 하나는 버셀(Vercel)의 AI SDK를 위한 백엔드임 — 이 백엔드가 세계 최고 수준이라고 자평함.

16. AI SDK 자체는 도구 호출까지만 잘 되고, 이걸 실제 서비스에 쓰려면 탭 사이 동기화나 재개(resumability) 같은 걸 따로 만들어야 했다고 설명함.

17. 다음으로 짚은 건 코드 모드(code mode)로 가는 계기가 된 MCP(모델 컨텍스트 프로토콜, 에이전트가 외부 도구나 서버에 정해진 방식으로 붙게 해주는 규격)임 — 작년 4월 즈음 MCP가 확 유행했다고 함.

18. MCP는 원래 클라이언트와 서버 사이에 상태를 유지하는 연결이 필요한 구조라, 이걸 클라우드에 배포하는 게 가장 골치 아픈 부분이었다고 함.

19. 더러블 오브젝트는 이런 상태 유지 연결을 아주 쉽게 다뤄서 MCP 서버를 만들기에 잘 맞았고, 그래서 일찍 뛰어들었다고 밝힘.

20. 이렇게 만든 초기 MCP 서버 사례로 페이팔(PayPal), 센트리(Sentry), 리니어(Linear), 인터콤(Intercom)을 언급함.

21. 다음 인프라 조각은 워커(worker)임 — 서버리스 함수를 돌리는 단위로, 람다(Lambda)를 10~20년 뒤에 다시 설계했다면 이런 모습일 거라고 비유함.

22. 여기서 한 발 더 나가 최근 만든 게 다이나믹 워커(dynamic worker)라는 새 단위임 — 미리 배포하지 않고, 고객이나 사용자, 혹은 LLM이 만들어 보낸 코드 문자열을 그 자리에서 독립된 워커 하나에 올려 실행함.

23. 지난주 MCP 개발자 서밋에서 옆자리 스타트업 사람은 엔터프라이즈가 생성된 코드를 절대 안 돌릴 거라 확신했는데, 곧이어 록히드 마틴(Lockheed Martin) 쪽 사람은 오히려 코드 생성을 좋아한다고 말해 온도차가 재미있었다고 전함.

24. 다이나믹 워커는 완전한 가상머신이 아니고 전체 파일 시스템도 없지만, 아이솔레이트(isolate, 가상머신보다 훨씬 가벼운 격리 실행 단위) 형태로 즉시 띄울 수 있고 이걸 수십억 개까지 온디맨드로 띄울 수 있다고 함.

25. 활용처로는 예전에 JSON 같은 별도 설정 파일(DSL)을 폼에서 만들어 코드로 변환하던 자리에, 이제는 그냥 코드를 바로 쓰면 된다고 제안함.

26. 클라우드플레어 블로그에 이 샌드박스 설계를 자세히 풀어놨다고 소개하며, 맨 아래 마케팅 문구만 빼면 나머지는 기술적으로 볼 만하다고 함.

27. 보통 샌드박스는 가상머신이나 컨테이너에서 시작해 보안을 덧붙이는 순서인데, 이들은 정반대로 갔다고 설명함.

28. 다이나믹 워커 안에서는 기본적으로 자바스크립트만 돌아가고 fetch나 다른 API에는 아예 접근이 안 되며, 바깥에서 "깃허브(github.com)로 나가는 요청만 허용" 같은 식으로 딱 필요한 권한만 열어준다고 함.

29. 권장 방식은 아예 모든 외부 요청을 막아두고, 샌드박스에 명시적으로 허용할 능력만 하나씩 얹는 것이며 환경변수도 이 코드에는 전혀 노출하지 않는다고 밝힘.

30. 이 능력을 두고 "MCP를 한 번도 아니고 두 번 고쳤다"고 농담 삼아 주장하며, 이게 이번 컨퍼런스 두 사람 발표의 핵심이라고 예고함.

31. Matt은 오후 5시 40분에 코드 모드를 주제로 발표한다고 밝힘.

32. Sunil은 다음 날 코드 모드를 MCP 서버에 적용해 클라우드플레어의 API 엔드포인트 2,600개 전체를 단 1,000토큰 안에 접근하게 만드는 방법을 발표한다고 예고함.

33. 자바스크립트에는 지난 30년 가까이 "eval을 쓰지 말라"는 금기가 있었고, 클라우드플레어 워커에는 아예 eval 자체가 없다고 설명함.

34. 다이나믹 워커를 두고 이 발표 제목처럼 "eval 플러스플러스"라 부르는 이유가 여기 있음 — 30년간 안 건드린 기술 트리 가지를 이제 빠르고 안전하고 싸게 쓸 수 있게 됐다는 주장임.

35. 다만 "빠르고 좋고 싸다"를 동시에 가질 수 있느냐는 자문에는 "빠르고 싼 건 맞는데 좋은지는 아직 모른다, 써보고 알려달라"고 스스로 유보함.

36. 이 primitive(기본 연산 단위)가 있으면 모든 사용자가 코드를 짤 수 있는 세상을 전제로 인터페이스를 다시 설계할 수 있다고 주장함.

37. 다음 사례는 생성형 UI임 — 요즘 유행이 LLM이 JSON을 생성하면 그걸 화면 컴포넌트로 렌더링하는 방식이라고 지적함.

38. 이들은 왜 굳이 JSON을 거치냐고 물으며, 그냥 HTML이나 리액트 코드를 바로 생성해 렌더링하면 되지 않냐고 반문함.

39. 이렇게 못 하는 이유로 일부 플랫폼에는 신뢰할 수 없는 코드를 안전하게 렌더링할 primitive가 아예 없다는 점을 듦.

40. 예시로 클로드 아티팩트(Cloud Artifacts)를 들며, 이것도 결국 HTML을 사용자 브라우저 안에서 렌더링하는 방식이라 이런 구조에서는 보안 걱정이 덜하다고 설명함.

41. 문제가 커지는 건 이걸 서버 쪽에서 렌더링할 때인데, 그럴 때 JSON을 거치던 관행이 이제 리액트를 직접 렌더링하는 쪽으로 옮겨갈 수 있다고 봄.

42. 다음 사례는 재개 가능한 스트리밍(resumable streaming)임 — LLM에 긴 이야기를 요청한 뒤 스트리밍 중간에 새로고침을 하면 보통은 처음부터 다시 받아야 함.

43. 서버리스 구조에서는 이걸 해결하려면 별도 데이터베이스, 복제, 세션 고정(sticky session)까지 다 손으로 짜야 한다고 지적함.

44. 더러블 오브젝트와 이 에이전트 SDK 위에서는 그냥 같은 아이디로 다시 연결하면, 진행 중이던 스트림이 이어서 바이트를 계속 보내준다고 함.

45. 덤으로 여러 탭이나 여러 기기(휴대폰과 노트북 등)에서 동시에 열어도 자동으로 동기화된다고 밝힘.

46. 이 동기화 능력을 두고 "AI는 원래 여러 명이 같이 하는 게임이어야 한다"고 주장하며, 챗GPT(ChatGPT) 대화방을 링크 하나로 같이 쓸 수 없는 걸 예로 듦.

47. 이게 안 되는 이유를 오픈AI(OpenAI)가 아직 안 만들어서일 뿐이라고 깎아내리며, 오픈AI 인력이 3주마다 그만두는 것 같다는 농담을 덧붙임.

48. 이런 동기화·재개·스트리밍 같은 골치 아픈 분산 시스템 문제를 사용자 쪽 코드가 아니라 클라우드플레어 쪽에서 대신 떠안는다고 정리함.

49. 여기서 한 발 더 나가면 코드 모드의 실행 백엔드처럼 클라우드 코드(Cloud Code)식 코딩 에이전트를 워커만으로 돌리는 하니스(harness, 에이전트를 실제로 실행·관리하는 틀)를 만들 수 있다고 함.

50. 이런 서버는 터미널·채팅·휴대폰·웹 앱 등 어떤 클라이언트에서 붙어도 상태와 동기화가 그대로 유지된다고 설명함.

51. 이걸 두고 "지금 짓고 있는 게 맞다"며 곧 내놓을 계획이라고 밝힘 — 다만 컨퍼런스 참석 시간이 그 작업 시간을 뺏고 있다는 농담을 덧붙임.

52. 다른 코딩 에이전트 하니스들도 각자 인프라의 강점을 살려 만드는 중이라며, 자신들의 강점은 코드를 그 자리에서 즉시 생성·실행하는 능력과 재개 가능성이라고 정리함.

53. 그러면서도 큰 컨테이너에 작업을 넘기고 싶으면 그럴 수 있게 클라우드플레어 샌드박스 SDK도 따로 두고 있다고 밝힘.

54. 다른 회사의 샌드박스 제품(Daytona 등)이나 브라우저 자동화 도구를 그대로 붙여 써도 된다고 하며, 워커와 에이전트 SDK가 이 모든 걸 잇는 중심축이 되는 게 목표라고 정리함.

55. 확장 기능(extension) 구상도 밝혔는데, "그날 아침에 직접 확장 기능을 구현해봤다"며 결국 확장도 샌드박스 안에서 안전하게 돌아가는 생성 코드로 만들면 된다는 방향을 제시함.

56. 코딩 에이전트 Pi를 만든 개발자와 친분이 있다고 밝히며, Pi를 워커 위에서 직접 돌리는 것도 이야기 중이라고 함.

57. 저장 쪽은 더러블 오브젝트 안에 SQLite가 바로 들어 있고, 큰 파일은 R2(클라우드플레어의 오브젝트 스토리지, S3와 비슷한 대용량 파일 저장소)에 저장한다고 소개함.

58. 지금은 이 저장소들을 손으로 연결해야 하지만, 곧 자동으로 엮이게 만들 예정이라고 밝힘.

59. 자바스크립트와 파이썬(Python)이 일급(first class)으로 지원되고, 그 외 언어는 WASM(웹어셈블리, 여러 언어로 짠 코드를 저수준 바이트코드로 컴파일해 브라우저나 워커에서 돌리는 방식)으로 돈다고 설명함.

60. 최근에는 지그(Zig) 언어도 프로덕션에 들어왔다고 밝히며, 지그로 컴파일한 WASM 번들 용량이 Go나 러스트(Rust)보다 훨씬 작다는 장점을 듦.

61. 워커 안에서 번들러(bundler)를 직접 돌리는 도구도 있는데, NPM에서 의존성을 받아 타입스크립트·JSX 같은 걸 벗겨내고 실행 가능한 코드로 만들어준다고 소개함.

62. 이 번들러가 NPM 자체의 다운타임 대신 클라우드플레어 자체 캐시를 쓰기 때문에 더 안정적이라고 설명함.

63. "atcloudflare/shell"이라는 프로젝트는 더러블 오브젝트의 SQLite와 R2를 층층이 얹어 워커 안에 완전한 파일 시스템을 제공하며, 이미 오늘 쓸 수 있는 상태라고 밝힘.

64. 지난주 새로 낸 CMS(콘텐츠 관리 시스템) 이야기도 나옴 — 워커와 더러블 오브젝트 위에서 완전히 돌아가고, 플러그인 시스템 자체가 다이나믹 워커로 짜여 있다고 설명함.

65. 워드프레스(WordPress)가 플러그인발 보안 사고를 많이 겪었던 것과 달리, 이 CMS는 플러그인이 도는 자리 자체를 잠가둬서 그런 문제를 원천적으로 막는다고 주장함.

66. 이 CMS는 클라우드플레어 전용이 아니라 다른 플랫폼에도 배포할 수 있고, 다이나믹 워커 기능도 다른 플랫폼 지원을 준비 중이라고 밝힘.

67. 클라우드플레어는 1년에 두 번 "에이전트 위크(Agents Week)" 같은 발표 주간을 운영하는데, 다음 주가 바로 그 주간이라 발표가 몰릴 예정이라고 예고함.

68. 마지막으로 가격 이야기 — 무료 요금제가 마케팅 비용이 아니라, 10년 전 인프라 결정(자체 대형 데이터센터 대신 ISP 근처에 장비를 두고, 최상위 ISP에서 대역폭을 대량으로 사들이는 방식) 덕에 원가 자체가 싸다고 설명함.

69. 유료 요금제는 월 5달러부터 시작하고, 이 위에 수백만 달러 규모 SaaS를 돌리는 고객도 있다고 밝힘.

70. 관련 문서는 agents.cloudflare.com과 developers.cloudflare.com/agents에, 이슈 제보는 github.com/cloudflareagents에서 받는다고 안내하며 마무리함.
