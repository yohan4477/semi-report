1. 엔비디아(NVIDIA) 생성형 AI 플랫폼 팀 소속 실렌드런 아루나기리가 발표를 시작함.

2. 시간이 지나도 계속 쓸모 있는 효과적인 AI 에이전트(사람이 시킨 일을 스스로 여러 단계로 쪼개 도구를 불러가며 처리하는 프로그램)를 만드는 법을 다룬다고 함.

3. 핵심은 시장에 나온 가장 큰 LLM(거대언어모델)으로 힘을 키우는 게 아니라 단순한 데이터 플라이휠이라고 함.

4. 엔비디아 사내 에이전트에 데이터 플라이휠을 적용한 실제 사례와 그 과정에서 배운 교훈을 공유하겠다고 함.

5. 에이전트는 데이터를 살펴보고, 추론해서 계획을 세우고, 툴과 함수와 외부 시스템을 써서 과제를 해내는 시스템이라고 정의함.

6. 여기에 사용자 피드백을 포착해 배우고 그 선호와 데이터로 스스로를 계속 다듬는 능력까지 있어야 순환이 완성된다는 게 발표자 생각이라고 함.

7. 에이전트를 만들고 키우는 일은 고통스러운데, 데이터가 빠르게 바뀌고 기업 고객이라면 새 비즈니스 인텔리전스가 계속 시스템에 흘러들어오기 때문이라고 함.

8. 사용자 선호와 고객 요구도 함께 바뀌는데, 이걸 감당하려고 더 크고 무거운 모델을 쓰면 추론 비용이 올라가서 사용량이 늘수록 비용도 늘어나는 구조가 된다고 함.

9. 바로 이 지점에서 데이터 플라이휠이 도움이 된다고 함.

10. 데이터 플라이휠은 기업 데이터를 중심에 두고 데이터 처리·정제, 모델 커스터마이징, 평가, 안전한 상호작용을 위한 가드레일링, RAG(모델이 답하기 전에 외부 문서를 찾아와 근거로 쓰는 방식) 파이프라인 구축을 계속 도는 순환 고리라고 정의함.

11. 에이전트가 프로덕션에서 돌아가면 이 순환이 추론 데이터·비즈니스 인텔리전스·사용자 피드백으로 정답 데이터를 계속 정제하고, 기존 모델과 새 모델을 실험·평가해서 더 작으면서도 대형 모델과 맞먹는 정확도를 내는 모델을 찾아낸다고 함.

12. 그렇게 찾은 작은 모델은 지연(latency)이 낮고 추론이 빠르고 총소유비용(TCO)이 낮다고 함.

13. 몇 주 전 엔비디아가 발표한 니모 마이크로서비스(NeMo microservices)를 소개하는데, 에이전트형·생성형 AI 시스템과 그 둘레의 데이터 플라이휠을 만드는 엔드투엔드 플랫폼이라고 함.

14. 니모 큐레이터(NeMo Curator)는 멀티모달 데이터를 포함해 고품질 학습 데이터셋을 정제하는 역할이라고 함.

15. 니모 커스터마이저(NeMo Customizer)는 로라(LoRA)·P-튜닝·전체 지도미세조정(full SFT) 같은 최신 기법으로 모델을 파인튜닝·커스터마이징한다고 함.

16. 니모 이밸류에이터(NeMo Evaluator)는 학계·기관 벤치마크는 물론 LLM을 심사자로 쓰는 방식까지 써서 모델을 평가한다고 함.

17. 니모 가드레일(NeMo Guardrails)은 프라이버시·보안·안전을 위한 가드레일 상호작용을 맡고, 니모 리트리버(NeMo Retriever)는 최신 RAG 파이프라인을 만든다고 함.

18. 이 마이크로서비스들은 단순한 API 엔드포인트로 노출돼 있어서 API 호출 한두 번으로 모델을 커스터마이징·평가·가드레일링할 수 있고, 온프레미스·클라우드·데이터센터·엣지 어디서나 돌릴 수 있으며 엔비디아 지원으로 기업급 안정성을 얻는다고 함.

19. 니모 마이크로서비스를 레고 조각처럼 조합해 만든 샘플 데이터 플라이휠 아키텍처를 보여주는데, 최종 사용자가 고객서비스 에이전트 같은 프런트엔드와 상호작용하면 뒤에서 가드레일이 걸린다고 함.

20. 백엔드 모델은 최적화된 추론을 위해 엔비디아 님(NIM)으로 서빙된다고 함.

21. 정확도를 해치지 않으면서 어떤 모델이 맞는지 찾으려고, 데이터를 계속 정제해 니모 데이터 스토어에 담고 커스터마이저·이밸류에이터로 재훈련·재평가를 반복한다고 함.

22. 목표 정확도에 도달하면 IT 관리자나 AI 엔지니어가 그 모델을 승격해 에이전트를 구동시킨다고 함.

23. 이제 실제 사례로 엔비디아 사내 직원 지원 에이전트인 NV 인포 에이전트(NV Info Agent)를 든다고 함.

24. 이 에이전트는 HR 복지, 재무 실적, IT 헬프, 제품 문서 등 여러 영역에 걸쳐 직원이 필요로 하는 사내 지식에 접근하게 돕는 챗봇이라고 함.

25. 직원이 질의를 넣으면 안전하고 보안된 상호작용을 위해 가드레일을 거치고, 그 아래 LLM이 구동하는 라우터 에이전트가 여러 전문가 에이전트를 오케스트레이션한다고 함.

26. 각 전문가 에이전트는 자기 영역에서 일을 잘 해내도록 RAG 파이프라인을 붙여서 관련 정보를 가져온다고 함.

27. 각 모델을 무엇으로 쓸지 정하려고 사용자 피드백과 라우터가 작동할 때 남는 프로덕션 추론 로그를 바탕으로 데이터 플라이휠 루프를 세웠다고 함.

28. 주제 전문가와 사람이 개입하는 피드백(human-in-the-loop)으로 정답 데이터를 계속 정제하고, 니모 커스터마이저·이밸류에이터로 여러 모델을 계속 평가해 가장 효과적인 모델을 님으로 승격해 라우터 에이전트를 구동시킨다고 함.

29. 멀티모델 에이전트 시스템에서 잘못될 수 있는 모든 지점을 표시해뒀다며, 그중 하나로 라우터 에이전트를 자세히 들여다본다고 함.

30. 라우터 에이전트는 혼합 에이전트(mixture of agent) 구조로 짜여 있고, 사용자 질의의 의도와 맥락을 이해해 알맞은 전문가 에이전트로 질의를 넘긴다고 함.

31. 문제는 주어진 질의를 어느 전문가 에이전트로 보내야 정확한지이고, 목표는 정확하게 라우팅하면서도 더 빠르고 비용 효율적인 LLM을 쓰는 것이라고 함.

32. 라우터 에이전트를 구동할 모델을 비교했는데, 라마(Llama) 3.1 70B·3.3 70B 변형을 파인튜닝 없이 그대로 배포한 기준선(baseline)에서 96%의 정확도가 나왔다고 함.

33. 반면 8B 변형은 정확도가 14% 아래로 떨어져 쓸 만하지 않았다고 함.

34. 여기서 많은 기업 평가가 착각에 빠지는데, 큰 모델은 96%·작은 모델은 14%라는 격차만 보고 파인튜닝을 해도 못 메울 거라 지레짐작해 70B 변형으로 가버린다고 지적함.

35. 하지만 바로 이 지점에서 데이터 플라이휠이 진가를 발휘한다고 함.

36. 먼저 70B 라마 변형을 돌리면서 엔비디아 직원들에게 피드백 양식을 돌려 질의를 몇 개씩 제출하고 응답이 쓸 만했는지 표시해 달라고 요청했다고 함.

37. 그렇게 1224개 데이터 포인트를 모았는데, 729개는 만족스러운 응답이었고 495개는 직원이 불만족한 응답이었다고 함.

38. 니모 이밸류에이터와 LLM 심사자로 이 495개 불만족 응답을 들여다봤더니 140개가 잘못된 라우팅 탓이었다고 함.

39. 주제 전문가가 다시 수작업으로 분석해보니 그중 진짜로 라우팅이 틀린 경우는 32개였다고 함.

40. 이렇게 정답 데이터셋 685개를 마련해 60%는 작은 모델을 파인튜닝하는 데, 40%는 정확도를 테스트·평가하는 데 나눠 썼다고 함.

41. 겨우 685개 데이터 포인트로 이룬 결과가 놀라웠는데, 이게 가능했던 건 데이터 플라이휠 구조 덕분이라고 함.

42. 70B 변형은 96% 정확도를 냈지만 첫 토큰이 나오기까지 26초의 지연이 걸렸다고 함.

43. 8B 변형은 정확도가 14%였지만 지연은 70%가량 낮았다고 함.

44. 8B·3B 등 여러 변형을 파인튜닝해보니 8B가 조금만 손봐도 70B의 정확도를 따라잡았다고 함.

45. 미션 크리티컬 정도에 따라서는 1B 변형까지 볼 수 있는데, 정확도가 94%로 70B보다 겨우 2%포인트 낮을 뿐이라고 함.

46. 그러니 원하는 정확도와 관리하고 싶은 비용·자원 사이에서 트레이드오프를 고를 수 있다고 함.

47. 1B 모델을 배포하면 추론 비용이 98% 절감되고, 모델 크기와 지연이 각각 70배 줄어든다고 함.

48. 새 모델이 시장에 나올 때마다 이렇게 자동으로 평가·파인튜닝을 반복하는 루프를 상상해보라며, 프로덕션 로그와 지식에서 계속 배워 작은 모델을 훈련시키는 게 데이터 플라이휠의 힘이라고 함.

49. 다음 단계로 니모 마이크로서비스와 엔비디아 님을 써서 자신만의 에이전트형 사용 사례와 데이터 플라이휠을 만들어보라고 권함.

50. 효과적인 데이터 플라이휠을 만드는 프레임워크를 제시하는데, 첫 단계는 사용자 피드백을 모니터링하는 것이라고 함.

51. 직관적인 사용자 경험, 프라이버시 준수, 암묵적 신호와 명시적 신호까지 동원해 모델이 드리프트(운영 중 성능이 서서히 틀어지는 현상)를 겪고 있는지 파악하라고 함.

52. 두 번째 단계는 왜 에이전트가 그렇게 행동하는지 오류나 드리프트를 분석하고 원인을 짚는 것이라고 함.

53. 오류를 분류하고 실패 원인을 귀속시켜 정답 데이터셋을 만드는 게 이 단계의 결과물이라고 함.

54. 세 번째 단계인 계획(plan)에서는 여러 모델을 찾아보고 합성 데이터를 만들고 실험하고 파인튜닝하면서 자원과 비용을 최적화한다고 함.

55. 네 번째 단계인 실행(execute)은 플라이휠 사이클을 돌리는 데 그치지 않고, 정확도·지연·성능·프로덕션 로그를 꾸준히 추적하는 체계를 세워 엔드투엔드 젠AI옵스(GenAI Ops) 파이프라인을 관리하는 것까지 포함한다고 함.

56. 이 프레임워크가 에이전트형 사용 사례뿐 아니라 그 둘레의 데이터 플라이휠까지 만드는 데 도움이 되길 바란다며 발표를 마침.

한줄 코멘트. 96%짜리 70B를 26초 지연째 그대로 쓰던 데서, 685개짜리 피드백 데이터로 1B를 94%까지 끌어올려 비용을 98% 줄인 순서가 이 발표의 전부이자 핵심임.
