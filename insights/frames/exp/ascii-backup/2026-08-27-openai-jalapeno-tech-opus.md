# OpenAI Jalapeño — 추론 가속기의 구조와 그 설계를 고른 이유

Hot Chips 발표 직후 녹음된 회차다. 발표를 한 쪽은 Richard Ho(전 구글 TPU), Ravi(칩 아키텍트), Chris(소프트웨어 공동설계)였고, 진행자 둘은 발표 슬라이드를 한 장씩 짚어 가며 설계 결정의 근거를 뜯는다. 아래는 그 회차에서 실제로 언급된 구조·사양과, 그 선택을 하게 만든 논리다.

---

## 1. 무엇을 최적화 대상으로 삼았나 — 지표 정의부터가 설계 결정이다

칩 설계는 목적함수를 무엇으로 두느냐에서 갈린다. Jalapeño 팀이 세운 축은 둘이다.

- **사용자 경험**: 첫 토큰까지의 시간(time to first token)이 아니라 **마지막 토큰까지의 시간**, 즉 종단간 지연이다. 언제 시작하느냐가 아니라 언제 끝나느냐를 잰다.
- **요청당 에너지**: 그 응답을 만드는 데 줄(joule)이 얼마나 들었나.

이 둘은 서로 맞선다. 에너지를 더 쓰면 언제든 더 빠르게 갈 수 있다. 그래서 발표 팀은 단일 수치를 내놓지 않고 **파레토 프론티어 곡선**으로 보여 주겠다고 선언했다. 한쪽 손잡이를 돌릴 때 다른 쪽이 어떻게 움직이는지를 통째로 공개하겠다는 뜻이다.

```
  요청당 에너지(적을수록 좋음)
        ^
        |   느리지만 효율적
        |        *
        |          *
        |             *        <- 파레토 프론티어: 이 선 위에서는
        |                *         한쪽을 얻으려면 다른 쪽을 내줘야 한다
        |                    *
        |                        *   빠르지만 전력을 먹음
        +-------------------------------> 사용자당 토큰/초(많을수록 좋음)

  단일 수치 보고     ->  곡선 위의 점 하나만 골라 보여 주는 것
  파레토 곡선 보고   ->  손잡이를 돌린 전 구간을 보여 주는 것
```

Vik이 정리한 표현으로는 **토큰당 줄(tokens per joule)** 이 궁극의 소유 비용이다. 초당 토큰을 와트로 나눈 값인데, 와트와 초를 합치면 줄이 되므로 나눗셈 기호를 줄여 그렇게 부른다. 에너지를 넣어 토큰을 뽑는 기계로 본다는 관점이다. 다만 개념 자체가 새롭지는 않다는 단서도 붙는다 — 상호작용성 곡선의 Y축에 초당 토큰/메가와트를, X축에 사용자당 초당 토큰을 두는 그림은 이미 흔하다.

여기서 회차가 짚는 구조적 차이는 이렇다. 상용 실리콘 업체(merchant silicon)는 칩을 **AI 랩이나 하이퍼스케일러에게 판다**. 그래서 총소유비용(TCO)을 먼저 말한다. Jalapeño를 만든 쪽은 **자기 모델을 쓰는 최종 사용자**를 고객으로 둔 모델 랩이다. 사는 사람이 아니라 쓰는 사람을 보고 설계했고, 지표 정의가 그 자리에서 갈렸다.

```
  상용 실리콘 업체            모델 랩이 직접 설계
  ------------------          ------------------
  칩 설계자                    칩 설계자
     |                            |
     v                            v
  칩 구매자(하이퍼스케일러)      모델 팀(공동설계)
     |                            |
     v                            v
  최종 사용자                  최종 사용자
                              (설계자와 두 칸 거리 -> 한 칸 거리)

  최적화 대상: TCO            최적화 대상: 종단간 지연 + 요청당 에너지
```

## 2. 왜 전용이 아니라 범용에 가깝게 만들었나

먼저 범위를 좁혀 두자. Jalapeño는 **학습이 아니라 추론**용이고, **합성곱 신경망이 아니라 대규모 언어모델** 추론에 초점이 있다. 그 안에서는 넓다.

발표에서 보여 준 것은 자기 모델 전용이 아니라는 증거다. 좁고 작은 GPT OSS부터 모양이 꽤 다른 Kimi K2.5까지 돌렸다. SemiAnalysis 쪽에서는 이 칩으로 Doom을 돌릴 수 있었다는 점까지 짚었다(추론 말고도 뭔가는 된다는 정도의 의미다).

설계 논리로 보면 두 갈래 주장이 회차 안에서 부딪힌다.

| 쪽 | 주장 | 근거 |
| --- | --- | --- |
| 범용 유지 | 앞으로 올 알고리즘·하네스 혁신을 감당할 유연성이 있어야 한다 | 모델 모양이 바뀌면 고정 설계는 도착과 동시에 죽는다 |
| 범용 유지 | 자기네 **미래 모델**을 이 칩 위에서 개발하려면 일반성이 필요하다 | Kimi를 굳이 돌릴 일은 없어도, 일반성은 자기 모델 개발에 쓰인다 |
| 전용화 | 극단적 공동설계로 가면 Cerebras급 성능까지 갈 여지가 있다 | 자기 모델·자기 워크로드·자기 사용 통계를 아는 쪽만 가능한 튜닝이다 |

전용화 쪽 논거의 핵심은 정보 비대칭이다. GPU 공급자는 토큰을 팔지 않으니 자기 모델이 실제로 어떤 워크로드로 어떻게 쓰이는지를 모른다. 모델 랩은 안다. 그 정보를 하드웨어에 박아 넣으면 남이 못 가는 데까지 간다는 논리다.

회차의 결론은 한쪽 손을 들어 주지 않고, 뒤의 "무엇을 잘라내나" 절과 로드맵으로 넘어간다.

## 3. 무엇을 넣고 무엇을 자르나 — 한계비용 대 기회비용

Ravi가 설계 시점의 비용을 둘로 갈랐다.

- **한계비용**: 기능 하나를 더 넣는 데 드는 트랜지스터 수, 플로어플랜 면적.
- **기회비용**: 그 기능이 없어서 못 받아 주는 사용자 수요.

그리고 기회비용이 대체로 한계비용보다 훨씬 크다고 했다. 여기서 **후회 요인(regret factor)** 이라는 말이 나온다. 넣고 싶은 기능 목록은 길고, 안 넣었을 때 후회할 것부터 고른다는 기준이다.

청중이 "가장 어려웠던 결정이 무엇이었나"를 묻자 답은 **무엇을 칩에서 잘라낼지 정하는 일**이었다.

```
  기능 후보 목록(길다)
        |
        v
  [후회 요인으로 순위]  안 넣으면 가장 아플 것이 위로
        |
        v
  [플로어플랜에 밀어넣기]  -> 안 들어간다
        |
        v
  [자른다]  <-- 가장 어려웠던 결정
        |
        +----> 잘린 것 --> 로드맵(2세대 / 3세대)
        |
        v
  테이프아웃
```

로드맵이 이 압력의 배출구다. 발표 시점에 1세대는 손에 들려 있고, **2세대는 테이프아웃에 근접**, 3세대는 검토 중이다. 1세대에서 못 넣은 기능을 2세대에 어떻게 밀어 넣을지의 일정·우선순위 문제로 바뀐다.

## 4. 9개월 설계 주기 — RTL부터 테이프아웃까지

첫 RTL에서 테이프아웃까지 약 **9개월**이다. 통상 최소 2~3년, 수작업이 많이 드는 일이라는 게 회차의 비교 기준이다.

```
  통상적인 신규 칩
  |=========================================| 24~36개월
   RTL                                  테이프아웃

  Jalapeño
  |==========| 9개월
   RTL   테이프아웃

  단축 요인(회차에서 지목된 것)
   1) AI 도구  - 초기 RTL은 GPT-3급 모델로 작성했고,
                 개발이 진행되며 더 나은 모델로 갈아탔다
   2) 사람     - TPU를 하던 팀을 데려왔다
   3) 백지     - 레거시 소프트웨어를 어떻게 얹을지 고민할 필요가 없었다
```

세 번째가 기술적으로 과소평가되기 쉬운 항목이다. 기존 소프트웨어 자산을 이어받아야 하는 설계는 그 제약이 명령어 구조와 메모리 모델까지 따라 들어온다. 백지에서 시작하면 그 구속이 없다.

한 가지 단서. 회차는 AI 도구만으로 설명되지 않는다고 못 박는다 — GPT-3급 모델은 어느 회사나 이미 갖고 있다. 팀과 도구의 조합이라는 게 두 진행자의 공통 결론이다.

## 5. 벤치마크 — 어떤 조건에서 잰 수치인가

측정은 SemiAnalysis의 Inference X로 했고, OpenAI 팀은 이것을 **공정한 공개 전력 정규화 비교**로 인정했다. 발표 팀이 이 벤치마크를 고른 이유가 셋 나온다.

1. 자기에게 잘 맞는 모델 하나를 고르는 대신, 여러 오픈소스 모델(작은 것·중간 것·큰 것)로 잰다.
2. 결국 중요한 것은 시스템 전체가 만든 사용자 경험이다 — 하드웨어든 소프트웨어든 네트워킹이든 무엇을 튜닝해도 좋으니 종단간으로 재라.
3. **전력 정규화**다. 전력을 더 부어 토큰을 늘리는 식의 우회를 막는다.

측정 조건의 한계도 그대로 짚힌다.

| 항목 | 내용 | 성격 |
| --- | --- | --- |
| 입력/출력 길이 | 입력 8K, 출력 1K | 발표·기사에서 쓰인 조건 |
| 긴 컨텍스트 | 100만 토큰급 입력에서의 거동은 안 나왔다 | 미측정 |
| 에이전트 워크로드 | AgentX 플랫폼 기준 벤치마크는 아직 안 돌렸다 | 미측정 |
| 메모리 세대 | Jalapeño는 HBM4, 비교 대상 Blackwell·MI355는 HBM3E | 세대 비대칭 |

마지막 항목 때문에 회차는 **공정한 비교 상대는 Vera Rubin과 Helios**라고 정리한다. 그런 의미에서 Blackwell급이라기보다 Rubin급 칩으로 보는 게 맞다는 것이다.

결과 쪽에서 언급된 두 지점.

```
  (가) DeepSeek R1 671B — 중간 크기 모델
       같은 상호작용성에서 처리량이 훨씬 높고,
       상호작용성 축으로도 GPU보다 더 멀리 뻗는다 -> 새 파레토 프론티어

  (나) GPT OSS 120B — 작은 모델
       사용자당 초당 1,000토큰을 넘긴다

       사용자당 초당 토큰
       0 ------- 500 ------- 1,000 ------- 2,000 ------- 4,000
                              |              |             |
                              |              |             +- Cerebras가 SRAM으로
                              |              |                약속하는 영역
                              |              +- HBM 대역폭만으로 계산상
                              |                 도달 가능하다고 본 값
                              +- 지금까지 SRAM 칩(Groq LPU, Cerebras)의 영역.
                                 GPU는 여기까지 못 갔다. Jalapeño가 여기에 들어왔다
```

(나)가 구조적으로 중요한 이유는 GPU 진영의 대응 방식과 맞물리기 때문이다. GPU 쪽은 Dynamo로 워크로드를 프리필과 디코드로 쪼개고, 디코드는 SRAM 칩(Groq, Cerebras)에 넘기는 조합으로 그 영역을 커버해 왔다. Jalapeño는 **한 칩이 낮은 디코드 속도에서의 고처리량과 초당 수천 토큰을 둘 다** 한다는 주장이다. AI ASIC 스타트업들이 하던 주장과 같은 형태다.

다만 회차는 균형추도 단다 — Rubin 시스템에 Groq LPU를 붙이면 그 파레토 곡선은 나온다. 없던 성능이 아니라 **다른 형태로 존재하던 성능**이다. 대신 그 조합에 랙이 몇 개 드는지를 물어야 한다.

전력 쪽 수치는 이렇다. Jalapeño는 **TDP 700W**. Blackwell GB200은 1,000W를 넘고 1,200W쯤으로 언급된다. 와트로 정규화했을 때의 토큰 처리량이 이 칩의 핵심 강점이라는 게 회차의 정리다.

## 6. 핵심 구조 — 왜 HBM을 다 못 쓰고 있었나

여기가 이 회차에서 기술적으로 가장 밀도가 높은 대목이다.

### 6-1. 문제 제기: 대역폭은 있는데 토큰이 안 나온다

Vik이 세운 계산은 이렇다.

```
  랙 하나에 들어가는 Jalapeño 128개
        |
        v
  128개의 HBM4 대역폭을 전부 합치면 -> 초당 약 1페타바이트
        |
  1조 파라미터 모델을 FP4(4비트)로 담으면 -> 약 0.5테라바이트
        |
        v
  1PB/s ÷ 0.5TB = 초당 약 2,000토큰이 나와야 한다

  그런데 실제로는 2,000토큰이 안 나온다.
  Cerebras와 LPU가 SRAM을 쓰는 이유가 정확히 이 지점이다 —
  더 빠르게 가려고, 즉 2,000 위로 올라가려고 쓴다.
  (Cerebras는 SRAM으로 4,000토큰을 약속하지만 시스템 복잡도가 막대하다)
```

메모리 업계의 대응은 지금까지 한 방향이었다. 핀당 속도를 올린다. 핀당 10Gb/s에서 16Gb/s로 밀고 있고, Hot Chips의 메모리 세션에서는 HBM5가 23~24Gb/s에 이른다는 그림이 나왔다. 그런데 **그 대역폭이 토큰 수로 나타나느냐**가 이 회차가 던지는 물음이다. OpenAI 쪽 답은 "아니오, 우리는 HBM의 능력조차 다 못 쓰고 있다"였다.

```
  지금까지의 길                      Jalapeño가 고른 길
  ------------                      ------------------
  핀당 속도를 매년 올린다             갖고 있는 대역폭을 실제로 다 쓴다
  10 -> 16 -> 23~24 Gb/s            그러려면 데이터가 제때 도착해야 한다
```

### 6-2. 원인: 오퍼랜드가 늦게 도착한다

Chris가 쓴 표현이 **"오퍼랜드가 늦게 도착한다(operands arrive late)"** 이다. 행렬곱을 하려는 순간에 데이터가 레지스터에 없다. 왜인가.

```
  통합 메모리 서브시스템(unified memory subsystem)

   가속기 A --+                              +-- 이웃의 요청
   가속기 B --+---> [ 공유 HBM 풀 ] <--------+-- 스케일업 망 너머의 요청
   가속기 C --+          ^                   +-- 여기저기 흩어진 사본들
                         |
                     경합(contention)

   결과: HBM에서 데이터를 빼내는 속도 자체는 빠르다.
         그런데 "필요한 자리에, 필요한 때에" 도달시키는 것이 병목이다.
         연산이든 메모리든 이동 중인 데이터를 기다리며 멈추면
         이용률(utilization)이 떨어진다.
```

Chris의 한 줄. **자랑하는 플롭스는 의미가 없다. 실제로 전달된 플롭스가 전부다.** 냅킨 계산으로 몇 플롭스가 나온다고 적어 놔도 데이터가 제때 없으면 무의미하다는 뜻이다.

### 6-3. 처방: 로컬 HBM 슬라이스, NUMA 스타일

그래서 나온 구조가 **가속기마다 자기 몫의 로컬 HBM 슬라이스**를 붙이고, 전용 버스로 잇는 것이다. 효율이 높고 지연이 낮은 버스다. 발표에서는 이것을 NUMA 스타일 아키텍처라고 불렀다.

NUMA(non-uniform memory architecture, 비균일 메모리 구조)는 원래 다중 코어 CPU 쪽 용어다. 코어마다 메모리 일부를 떼어 붙여 두는 방식이라고 보면 된다. 같은 발상을 가속기에 옮긴 것이다.

```
  이전: 경합하는 자원으로서의 HBM
  ------------------------------------------
     [가속기]  [가속기]  [가속기]  [가속기]
         \        \        /        /
          \        \      /        /
           +----[ 공유 HBM 풀 ]---+
                   ^
                 경합. 줄을 서야 한다

  이후: 슬라이스로 갈라 붙인 HBM (NUMA 스타일)
  ------------------------------------------
     [가속기]   [가속기]   [가속기]   [가속기]
        |          |          |          |     <- 전용 버스, 저지연·고효율
     [HBM슬]    [HBM슬]    [HBM슬]    [HBM슬]

     각자 자기 차선에서 계속 달린다. HBM 경합이 사라진다
```

통신 계층은 세 겹으로 정리된다.

```
  1층  가속기 <-> 자기 로컬 HBM 슬라이스
       가장 빠르다. 전용 버스

  2층  집합 통신망(collective network)
       고대역폭·저지연. 가속기들 사이의 협업

  3층  일반 NoC(칩 내부 연결망)
       2층만큼 빠르지 않다. 대신 아무 데나 말을 걸 수 있는 유연성
```

이 구조에는 대가가 따른다. 어느 데이터를 어느 슬라이스에 둘 것인지, 워크로드를 이 구조에 어떻게 사상(mapping)할 것인지를 새로 풀어야 한다. 발표 팀의 판단은 **그 복잡도를 푸는 편이 낫다**였다. 사용자 경험과 성능이 그만큼 좋아지기 때문이다.

### 6-4. 같은 원리의 다른 얼굴: KV 캐시 지역성

디코드 단계의 최대 난점은 KV 캐시다. 토큰 하나를 낼 때마다 이 데이터를 앞뒤로 옮겨야 한다. 발표 팀의 장기적 주장은 **KV 캐시를 옮기지 마라, 어떻게든 로컬에 두라**는 것이다. 옮기지 않아도 되면 따라오던 문제들이 한꺼번에 사라진다. 6-3의 슬라이스 구조와 같은 뿌리에서 나온 처방이다.

## 7. 스케일업 망 — 2계층, ESUN 위에서

칩 하나의 이야기에서 시스템 이야기로 넘어가는 지점이다.

```
  1계층 스케일업 도메인
  +---------------------------------------------------+
  |  Jalapeño 128개                                    |
  |  Broadcom Tomahawk 6 스위치                        |
  |  칩당 600Gb/s로 통신                                |
  |  (랙 하나 안에 들어가는 것으로 본다)                  |
  +---------------------------------------------------+
                       |
                       | 200Gb/s 인터커넥트 (레인당 200Gb/s)
                       v
  2계층 스케일업 도메인
  +---------------------------------------------------+
  |  Jalapeño 2,048개 = 랙 16개                         |
  +---------------------------------------------------+

  프로토콜: ESUN (스케일업 이더넷 브리지 계열, Broadcom이 주도)
            UALink와는 다른 규격이다
  토폴로지: 절반 평탄화된 2단 Clos (half flattened two-level Clos)
```

토폴로지 이름은 회차에서도 소화되지 않은 채로 남는다. 하루도 안 지난 시점이라 무엇을 뜻하는지 더 생각해 봐야겠다고 Vik이 그대로 말한다. 여기서는 이름만 기록해 둔다.

**용어 정리가 하나 붙는다.** 흔히 스케일업은 랙 안, 스케일아웃은 랙과 랙 사이라고 말한다. Jalapeño의 스케일업 도메인은 랙 16개에 걸쳐 있다. 그 통념은 특정 시점의 사정이었을 뿐이고, **스케일업의 정의는 메모리를 공유하는 가속기들의 범위**라는 것이 이 시스템이 다시 보여 주는 바다.

## 8. 다크 실리콘이 노는 가속기보다 싸다

이 회차의 표제 격 문장이다. 설계 철학이 가장 압축된 자리이기도 하다.

### 8-1. 문제: 워크로드 비율이 계속 변한다

추론 워크로드는 프리필, 드래프팅(투기적 디코딩), 검증으로 나뉘고, 그 비율은 모델 크기와 상황에 따라 계속 바뀐다. 고정된 비율이 없다.

투기적 디코딩(speculative decoding)이 무엇인지부터.

```
  일반 디코딩
   큰 모델이 토큰 하나를 낸다 -> 다음 토큰 -> 다음 토큰 ...

  투기적 디코딩
   [드래프팅]  작은 드래프트 모델이 한 번에 여러 토큰을 뱉는다
               예: 8개를 한꺼번에. 똑똑하지 않은 모델이라 틀릴 수 있다
                   8개 중 맞는 것이 1개일 수도 있다
        |
        v
   [검증]     그 8개 중 어디까지가 맞는지를 확인한다

  손잡이가 있다
   드래프트 모델이 똑똑하다 -> 2개만 뱉어도 된다 -> 검증 부담이 작다
   드래프트 모델이 작다     -> 토큰을 많이 뿌린다 -> 검증 쪽으로 일이 쏠린다

  즉 드래프트와 검증의 비율은 고정이 아니다.
  그 비율에 따라 칩이 해야 할 일의 성격이 달라진다
```

### 8-2. GPU 진영의 해법과 그 대가

```
  GPU 방식: 역할을 나눈다
  +-----------------+     +-----------------+
  | 프리필 전용 GPU  |     | 디코드 전용 GPU  |
  +-----------------+     +-----------------+
        바쁘다                  놀고 있다
        (워크로드 비율이 한쪽으로 기울면
         반대편 랙이 통째로 유휴 상태가 된다)
```

### 8-3. Jalapeño의 해법: 균형 잡힌 한 칩 + 파워 게이팅

```
  균형 칩 방식
  +-------------------------------------------+
  | 칩 하나에                                  |
  |   충분한 연산 + 충분한 메모리 대역폭 + 충분한 IO |
  +-------------------------------------------+
        |
        v
  워크로드가 프리필 쪽이면 -> 안 쓰는 구역을 꺼 둔다(게이팅)
  워크로드가 디코드 쪽이면 -> 반대쪽 구역을 꺼 둔다

  꺼진 실리콘 = 다크 실리콘. 면적은 낭비지만 전력은 안 먹는다

  비교
   다크 실리콘        칩 안 일부 구역이 꺼져 있다
   유휴 가속기        가속기 한 대, 심하면 랙 한 줄이 통째로 논다
   -> 앞이 더 싸다
```

특정 시점의 알고리즘 구현 하나에 맞춰 설계하지 않겠다는 선언이기도 하다. 어떤 비율에도 영원히 묶이지 않겠다는 것이다.

### 8-4. 파생 효과: 실리콘의 유효 수명

같은 논리가 수명 이야기로 이어진다. Vera Rubin에 Groq LPU를 붙인 조합을 놓고 보면, 그 LPU는 특정 형태의 디코드에 맞춰져 있다. 워크로드의 성격이 바뀌면 새 워크로드에서 효율이 떨어지거나, 애초에 돌릴 수 있는 워크로드 집합이 좁게 고정된다. 균형 칩은 그 반대 방향을 노린다 — 2세대가 나온 뒤에도 오래 쓸 수 있는 실리콘.

## 10. 이 회차가 답하지 않은 것

기술 관점에서 남는 미확인 항목만 모은다.

- **긴 컨텍스트 거동**: 측정 조건이 입력 8K, 출력 1K였다. 100만 토큰급 입력에서 어떻게 되는지는 나오지 않았다. 두 진행자 모두 이것을 남은 손잡이로 지목한다.
- **에이전트 워크로드**: AgentX 기준 측정은 아직이다.
- **동세대 비교**: HBM4 대 HBM3E 비대칭이 있어 Vera Rubin·Helios와의 비교가 나와야 성능 위치가 확정된다.
- **절반 평탄화 2단 Clos**: 이름만 나왔고, 네트워킹 관점에서 무엇을 뜻하는지는 회차 안에서 정리되지 않았다.
- **Tomahawk 스위치 수량**: 랙 구성에서 스위치가 몇 개인지 세어 보려는 시도가 있었다는 언급만 있다.
- **양산·신뢰성**: 대규모 제조와 출하, 규모에서의 신뢰성은 이번 발표가 다루는 범위 밖이다.
- **AI를 어떻게 썼는지의 세부**: RTL 작성에 무엇을 어떻게 썼는지는 별도 한 편이 필요한 분량이라며 이 회차에서 다루지 않았다.
